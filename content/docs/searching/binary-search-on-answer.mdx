## কী শিখব

- Binary search শুধু array-এর জন্য না: যেকোনো monotonic পরিসরে চলে
- Monotonic শর্ত চেনার উপায়: true-গুলো একপাশে, false-গুলো আরেকপাশে
- বর্গমূলের floor বের করার পুরো dry run
- টেমপ্লেট: "সম্ভব হলে উত্তর মনে রাখো, আরও ভালোর খোঁজে যাও"
- কোন কোন বিখ্যাত সমস্যা এই প্যাটার্নে খোলে

## ধারণা

এ পর্যন্ত binary search দেখেছ sorted array-তে। এবার একটা ঘুরে যাওয়া প্রশ্ন: ধরো বললাম, ১ থেকে ১০০-এর মধ্যে একটা সংখ্যা ভেবেছি, তুমি অনুমান করবে, আমি বলব "বড়" না "ছোট"। কত চেষ্টায় ধরতে পারবে? সর্বোচ্চ ৭ বার, মাঝ দিয়ে অর্ধেক বাদ দিয়ে।

খেয়াল করো, এখানে কোনো array-ই নেই, আছে একটা **পরিসর** আর একটা **শর্ত**। এই দুটো থাকলেই binary search চলে। আনুষ্ঠানিকভাবে শর্তটা যে রূপ নেয়, তার নাম **monotonic**: সংখ্যা বাড়ার সঙ্গে শর্তটা একবার true থেকে false-এ (বা উল্টো) যায়, আর কখনও পাল্টায় না। যেমন বর্গমূলে: ছোট মান পর্যন্ত `mid² <= n` true, একটা দাগ পেরিয়ে গেলে সব false, আর ফেরে না।

```text
মান:     1   2   3   4   5   6 ...   (n = 17)
mid²≤17? T   T   T   T   F   F ...
                     ↑
             এই দাগটাই উত্তর: শেষ true
```

পুরো প্যাটার্নটা তিন পদে:

1. উত্তরের **পরিসর** ঠিক করো (low, high)।
2. একটা **শর্ত** লেখো যা monotonic।
3. Binary search চালিয়ে সেই **সীমার দাগটা** খুঁজে বের করো।

## Dry run: `sqrtFloor(17)`

শর্ত: `mid * mid <= 17`। চাই শেষ true, মানে বর্গমূলের floor।

| ধাপ | low | high | mid | mid² | &lt;= 17? | ans | সিদ্ধান্ত |
|-----|-----|------|-----|------|--------|-----|-----------|
| 1 | 1 | 17 | 9 | 81 | না | 1 | বেশি, high = 8 |
| 2 | 1 | 8 | 4 | 16 | হ্যাঁ | 4 | ans = 4, low = 5 |
| 3 | 5 | 8 | 6 | 36 | না | 4 | high = 5 |
| 4 | 5 | 5 | 5 | 25 | না | 4 | high = 4 |
| 5 | 5 | 4 | - | - | - | - | low > high, থামো |

ফেরত **4**, ঠিকই: 4² = 16 ≤ 17 < 25 = 5²। মনে দাও ধাপ ২-তে: mid=4 শর্ত মিটেছে, কিন্তু থামিনি। কারণ আমরা প্রথম true খুঁজছি না, **শেষ** true খুঁজছি, তাই উত্তর মনে রেখে ডানে আরও ভালোর খোঁজে গেছি। এটাই [Variants](./binary-search-variants.mdx)-এর "মিলেও থামি না" চেতনার আরেক রূপ।

## কোড: নিজে বানাও

```js
function sqrtFloor(n) {
  if (n < 2) return n;                  // 0 আর 1-এর বর্গমূল নিজেরাই

  let low = 1;
  let high = n;
  let ans = 1;

  while (low <= high) {
    const mid = Math.floor((low + high) / 2);

    if (mid * mid <= n) {
      ans = mid;                        // সম্ভব: মনে রাখো
      low = mid + 1;                    // আরও বড় আছে কিনা দেখো
    } else {
      high = mid - 1;                   // অসম্ভব: ছোটে নামো
    }
  }

  return ans;
}

console.log(sqrtFloor(17)); // 4
console.log(sqrtFloor(16)); // 4
console.log(sqrtFloor(24)); // 4, কারণ 5² = 25 > 24
```

## টেমপ্লেট: যেকোনো "search on answer"

কোডটা একটা ছাঁচে ঢেলে দাও, পরে প্রতিটা সমস্যায় শুধু তিন জায়গা বদলাবে:

```js
function searchAnswer(low, high) {
  let ans = /* ডিফল্ট */;

  while (low <= high) {
    const mid = Math.floor((low + high) / 2);

    if (possible(mid)) {     // (১) শর্ত: monotonic হতে হবে
      ans = mid;             // (২) উত্তর মনে রাখো
      low = mid + 1;         // (৩) কোন দিকে আরও ভালো: ডানে
    } else {
      high = mid - 1;
    }
  }

  return ans;
}
```

শুধু `possible(mid)` লেখা আর পরিসর ঠিক করাই আসল কাজ। "সর্বনিম্ন সম্ভাব্য" চাইলে দিকটা উল্টো হয় (true পেলে বামে যাও, `high = mid - 1`), শেষে `ans`-এর ডিফল্টও বদলায়। ভাবনা এক।

## কোড ব্রেকডাউন: sqrtFloor, লাইনে লাইনে

1. `if (n < 2) return n` : ছোট input-এর আলাদা পথ, কারণ পরিসর 1..n-এর বাইরে উত্তর চলে যায় না, এটা নিশ্চয়তা।
2. `low = 1, high = n` : উত্তরের পরিসর। উদার পরিসর নিলেও চলে, log n ধাপে সব কমে যায়।
3. `ans = 1` : ডিফল্ট, যাতে শর্ত একবারও না মিললেও কিছু ফেরত যায়।
4. `ans = mid; low = mid + 1` : দুই লাইন একসাথে, "মনে রাখো, তারপর আরও ভালো খুঁজো"। শুধু প্রথমটা রেখে থেমে গেলে প্রথম true, আমাদের চাই শেষ true।
5. `high = mid - 1` : অসম্ভব দিকে যাওয়া, স্বাভাবিক binary search-এর মতোই।

## Complexity

| দিক | খরচ | কেন |
|-----|------|-----|
| Time | O(log উত্তরের পরিসর) × O(শর্ত চেক) | পরিসর অর্ধেক হয় প্রতি ধাপে; sqrtFloor-এ চেক O(1), তাই মোট O(log n) |
| Space | O(1) | কয়েকটা ভেরিয়েবল |

বাস্তব সমস্যায় `possible(mid)` নিজেই O(n) হতে পারে (যেমন "এই গতিতে সব কাজ শেষ হবে কিনা" দেখতে পুরো array ঘোরা)। তখন মোট O(n log উত্তরপরিসর)। এটাও সাধারণত brute force-এর চেয়ে অনেক ভালো।

## সাধারণ ভুল আর edge case

**১. শর্ত monotonic কিনা না দেখে ঝাঁপ দেওয়া।**
শর্ত যদি true-false-true ঘুরে ফিরে আসে, binary search ভুল দাগে থামে। ছোট মানগুলোতে শর্ত ছাপিয়ে দেখো: true-গুলো একপাশে, false-গুলো একপাশে আটকে আছে তো?

**২. "শেষ true" না "প্রথম true", দিক গুলানো।**
বর্গমূলে শেষ true চাই, Koko-তে প্রথম true। দিক উল্টালে উত্তর এক ঘর সরে যায়। প্রশ্ন করো: সম্ভব হলে আমি উত্তরকে বড় করতে চাই, না ছোট?

**৩. পরিসরের সীমা অতি আঁটসাঁট বা ভুল।**
`high` কম ধরলে আসল উত্তর পরিসরের বাইরে পড়ে থাকে, ফল চুপচাপ ভুল। সন্দেহ হলে উদার পরিসর নাও: log n-এ অল্প কয় ধাপ বাড়ে, নিরাপত্তা অনেক।

**৪. `ans` আপডেট করা ভুলে যাওয়া।**
`possible(mid)` মিলেও `ans = mid` না লিখলে ফেরত যায় ডিফল্ট। দুই লাইন (`ans = mid`, তারপর এক দিকে সরা) একটা আচরণ, একটা ছাড়া অন্যটা অর্থহীন।

**৫. mid হিসাবে overflow বা ভগ্নাংশ।**
`mid * mid` বড় n-এ সংখ্যার সীমা টপকাতে পারে অন্য ভাষায়; JS-এ নিরাপদ, তবু বড় হলে `mid > n / mid` রূপে তুলনা নিরাপদ। আর `Math.floor` ভুললে আগের পেজের ফাঁদই।

## অনুশীলন

- **সহজ ১:** `sqrtFloor(50)`-এর dry run টেবিল বানাও: low, high, mid, ans প্রতি ধাপে।
- **সহজ ২:** একই ভাবনায় cube root-এর floor লেখো। কোন লাইন বদলাল, আর পরিসর কী রাখলে?
- **মাঝারি ১:** "প্রথম true" রূপে বদলাও: এমন সর্বনিম্ন x বের করো যাতে x² >= n। দিকটা কোথায় কোথায় উল্টাল, তালিকা করো।
- **মাঝারি ২:** বন্ধুকে বোঝাও: কেন monotonic না হলে এই প্যাটার্ন ভাঙে। একটা শর্ত বানাও যা monotonic না, আর দেখাও কোন দাগে search বিভ্রান্ত হয়।
- **কঠিন:** Koko Eating Bananas সমাধান করো (LeetCode 875): piles আর h ঘণ্টা দেওয়া, সর্বনিম্ন খাওয়ার গতি বের করো। (হিন্ট: `possible(k)` মানে প্রতি pile-এ `Math.ceil(pile / k)` ঘণ্টা, মোট ≤ h কিনা। পরিসর: 1 থেকে max(pile)।)

## সারসংক্ষেপ

- Binary search array-এর না, **monotonic পরিসরের** algorithm।
- তিন জিনিস চাই: উত্তরের পরিসর, monotonic শর্ত, আর কোন দিকে ভালো সেটা জানা।
- "সম্ভব হলে মনে রাখো, আরও ভালোর খোঁজে যাও": এই দুই লাইনের জোড়াই টেমপ্লেটের প্রাণ।
- শর্ত চেক যত দামি, মোট খরচ O(শর্ত × log পরিসর)।
- "minimum of maximum" শব্দযুগল দেখলেই এই প্যাটার্ন সন্দেহ করো।
