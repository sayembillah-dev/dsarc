## কী শিখব

- Odd-even sort (অনানুষ্ঠানিক নাম **brick sort**) আসলে [Bubble Sort](./bubble-sort.mdx)-এর phase-করা রূপ — একই adjacent তুলনা আর swap, ভিন্ন সময়সূচি
- কেন এক phase-এর সব তুলনা একসাথে চালানো যায়: জোড়াগুলো পরস্পর বিচ্ছিন্ন (disjoint)
- থামার নিয়ম: এক পূর্ণ iteration (odd phase + even phase) swap-মুক্ত হলে
- Serial-এ O(n²) হলেও সমান্তরালে wall-clock O(n) — **মোট কাজ** বনাম **চোখে দেখা সময়**-এর পার্থক্য
- কোন জগতে এটা জেতে, আর কেন CPU-এর built-in `sort()`-এ এটা নেই

## ধারণা

[Bubble Sort](./bubble-sort.mdx)-এর এক pass মনে করো: একটাই লোক সারির মাথা থেকে কুড়ি পর্যন্ত হেঁটে পাশাপাশি জোড়া ঠিক করে যায়। সব কাজ একাই, একে একে। এখন ধরো হাতে অনেকজন helper আছে — কেন সবাই একসাথে তুলনা করবে না? সমস্যা একটাই: জোড়া গাদাগাদি হলে ধাক্কা লাগে। (১,২) আর (২,৩) একই সঙ্গে ঠিক করতে গেলে ২ নম্বর দুই দিকে টানাটানিতে পড়ে।

সমাধানটা ইট গাঁথুনির কারিগরের কাছে আছে। দেয়ালের এক সারির ইট পরের সারির চেয়ে অর্ধেক সরে থাকে, তাই সব ফাঁক ঢাকা যায়। ঠিক তেমনি: **odd phase**-এ শুধু (১,২), (৩,৪), (৫,৬)… জোড়া দেখো — সবগুলো বিচ্ছিন্ন, কেউ কারও ঘরে হাত দেয় না; **even phase**-এ শুধু (০,১), (২,৩), (৪,৫)… — ইটের পরের সারির মতো অর্ধেক সরে। দুই phase পরপর চালাও, আবার odd, আবার even — যতক্ষণ না এক পুরো বার কোনো swap ছাড়াই পেরিয়ে যাচ্ছে। এই ইট-সারির ছবির জন্যই আরেক নাম **brick sort**, আর বিচ্ছিন্ন জোড়ার গ্যারান্টির জন্যই এর জন্ম হয়েছিল সমান্তরাল প্রসেসরের জগতে — এক phase-এর সব তুলনা আক্ষরিকভাবে একই মুহূর্তে চালানো যায়।

মনে রাখো, এটা খেলা-বদলানো algorithm নয় — [Counting](./counting-sort.mdx)-দের মতো তুলনা বাদ দেয়নি, তাই ওই O(n log n) দেয়াল এখানেও আছে। এটা bubble-এর কাজের **সময়সূচি** বদলায়: একই তুলনা, একই swap, শুধু এমনভাবে সাজানো যাতে অনেক হাত একসাথে লাগানো যায়।

## ধাপে ধাপে dry run

Array: `[4, 3, 5, 1]`। odd phase-এ জোড়া (১,২), even phase-এ জোড়া (০,১) আর (২,৩)। প্রতি phase-এর পর array-এর অবস্থা দেখি:

| ধাপ | Phase | জোড়াগুলোর দশা | Swap | array-এর অবস্থা |
|-----|-------|----------------|------|------------------|
| শুরু | - | - | - | `[4, 3, 5, 1]` |
| ১ | odd | (3,5): ঠিক আছে | ০ | `[4, 3, 5, 1]` |
| ২ | even | (4,3): swap; (5,1): swap | ২ | `[3, 4, 1, 5]` |
| ৩ | odd | (4,1): swap | ১ | `[3, 1, 4, 5]` |
| ৪ | even | (3,1): swap; (4,5): ঠিক | ১ | `[1, 3, 4, 5]` |
| ৫ | odd | (3,4): ঠিক | ০ | `[1, 3, 4, 5]` |
| ৬ | even | (1,3): ঠিক; (4,5): ঠিক | ০ | `[1, 3, 4, 5]` |

ধাপ ৫ আর ৬ মিলে এক পূর্ণ iteration (odd + even) swap-মুক্ত — এখানেই থামা।

টেবিলের দিকে তাকাও: `1` শুরুতে ছিল index 3-এ, তারপর প্রতি phase-এ হুবহু এক ঘর করে বামে এগিয়েছে (ধাপ ২ → index 2, ধাপ ৩ → index 1, ধাপ ৪ → index 0)। এটা কাকতাল নয় — এক phase-এ কোনো উপাদান সর্বোচ্চ একটা জোড়ায় থাকে, তাই এক ঘরের বেশি সরতেই পারে না। এই "এক ঘর" নিয়ম থেকেই worst case বেরোবে: সবচেয়ে দূরের যাত্রীকে n−1 ঘর যেতে হলে প্রায় n-টা phase-ই লাগবে।

আর একই টেবিলে সমান্তরাল ছবিটা খুঁজো: ধাপ ২-এর দুটো swap (৪↔৩ আর ৫↔১) পরস্পরের ঘর ছোঁয়নি — দুজন worker একই সেকেন্ডে দুটো করতে পারত। CPU-এর একক সুতোয় আমরা একে একে করি, কিন্তু যথেষ্ট worker থাকলে (GPU-র হাজারো thread-এ, যেমন) এক phase-এর সব জোড়া সত্যিই একসাথে চলে।

## কোড: পুরো implementation

```js
function oddEvenSort(arr) {
  if (arr.length < 2) return 0;          // খালি বা একঘর: আগেই sorted
  let sorted = false;
  let phases = 0;                        // কত phase লাগল — শেখার হিসাব

  while (!sorted) {
    sorted = true;                       // এই iteration swap-মুক্ত ধরে নিই

    // odd phase: (1,2), (3,4), (5,6)...
    for (let i = 1; i < arr.length - 1; i += 2) {
      if (arr[i] > arr[i + 1]) {
        [arr[i], arr[i + 1]] = [arr[i + 1], arr[i]];
        sorted = false;                  // swap হলেই আর থামা যাবে না
      }
    }
    phases++;

    // even phase: (0,1), (2,3), (4,5)...
    for (let i = 0; i < arr.length - 1; i += 2) {
      if (arr[i] > arr[i + 1]) {
        [arr[i], arr[i + 1]] = [arr[i + 1], arr[i]];
        sorted = false;
      }
    }
    phases++;
  }
  return phases;
}

const a = [4, 3, 5, 1];
console.log(oddEvenSort(a), a);        // 6, [1, 3, 4, 5]

const done = [1, 2, 3, 4, 5];
console.log(oddEvenSort(done));        // 2 — এক পূর্ণ iteration-ই বুঝে যায়

const rev = [5, 4, 3, 2, 1];
console.log(oddEvenSort(rev), rev);    // 8, [1, 2, 3, 4, 5]

const dup = [2, 1, 2, 1];
console.log(oddEvenSort(dup), dup);    // 6, [1, 1, 2, 2]

console.log(oddEvenSort([9]));         // 0
console.log(oddEvenSort([]));          // 0
```

## কোড ব্রেকডাউন, লাইনে লাইনে

1. `if (arr.length < 2) return 0;` : খালি বা এক-উপাদানের array আগেই sorted — একটাও phase নষ্ট নয়।
2. `let sorted = false;` আর `while (!sorted)` : bubble-এর `swapped` flag-এরই বড় ভাই — পার্থক্য, এখানে এক "বার" মানে দুটো phase।
3. `for (let i = 1; i < arr.length - 1; i += 2)` : odd phase। এই `i += 2`-ই সব — জোড়া (i, i+1) আর পরের জোড়া (i+2, i+3) কখনো ঘর ভাগ করে না। এই বিচ্ছিন্নতাই parallel নিরাপত্তা।
4. `i < arr.length - 1` : শেষ জোড়ায় `arr[i + 1]` যেন টেবিলের বাইরে না যায়।
5. `if (arr[i] > arr[i + 1])` : কঠোর `>` — সমান জোড়া কখনো swap হয় না, তাই bubble-এর মতো এটাও **stable**।
6. `sorted = false;` : যেকোনো একটা swap মানেই "এখনো sorted না" — পরের iteration আবার দুটো phase।
7. শেষ iteration-এর খালি দুই phase-ই থামার সাক্ষী; সেজন্য `phases` প্রায় সবসময় জোড় সংখ্যা।

## ভ্যারিয়েন্ট

**Even phase আগে, odd পরে?** ফল একই — ক্রম বদলালে শুধু phase-এর গণনা এক-আধটা এদিক-সেদিক হয়। গুরুত্বপূর্ণ হলো প্রতি iteration-এ দুটোই থাকা।

**সত্যিকারের parallel চাইলে:** এক phase-এর swap-গুলো আগে লিখে রেখে সব একসাথে apply করো — তাহলেই এক phase সত্যিকারের এক সমান্তরাল ধাপ। GPU বা vector hardware-এ এই ছাঁচেই brick sort আজও বেঁচে আছে।

**নামের বিভ্রান্তি সতর্কতা:** "odd-even mergesort" (Batcher-এর) শুনলে গুলিয়ো না — সেটা sorting network-ভিত্তিক আলাদা algorithm, [Merge Sort](./merge-sort.mdx)-এর আত্মীয়। একই "odd-even" শব্দ, একদম ভিন্ন খেলা।

## Complexity: serial-এ পরিচিত, parallel-এ অভাবনীয়

| দিক | মান | কেন |
|-----|-----|-----|
| Time (best) | O(n) | sorted input-এ এক পূর্ণ iteration-ই থামে (flag) |
| Time (average) | O(n²) | তুলনা মোটামুটি bubble-এর মতোই, শুধু সাজানো আলাদা |
| Time (worst) | O(n²) | সর্বোচ্চ প্রায় n phase × প্রতি phase-এ প্রায় n/2 তুলনা |
| Space | O(1) | পুরোপুরি in-place, বাড়তি শুধু কয়েকটা ভেরিয়েবল |
| Stable | হ্যাঁ | শুধু adjacent জোড়া, সমানদের কখনো swap নেই |
| Parallel time | O(n), যদি n/2 processor থাকে | এক phase-এর সব তুলনা একই মুহূর্তে; মোট phase প্রায় n |

Worst case-এর হিসাবটা dry run-এর "এক ঘর" নিয়ম থেকেই আসে: কোনো উপাদান এক phase-এ সর্বোচ্চ এক ঘর সরে; সবচেয়ে দূরের যাত্রীর (যেমন উল্টো array-র একদম শেষে থাকা সর্বনিম্ন) n−1 ঘর যেতে হয়, তাই প্রায় n phase। প্রতি phase-এ প্রায় n/2 তুলনা — গুণ করলেই O(n²)। উল্টো `[5, 4, 3, 2, 1]`-এ আমাদের dry run-ই বলে দিয়েছে: ৮ phase।

লক্ষ্য করার জিনিস: **মোট কাজ (work)** সমান্তরালে চালালেও O(n²)-ই থাকে; বদলায় **চোখে দেখা সময় (span)** — n/2 জোড়া একসাথে শেষ হলে প্রায় n phase-ই O(n) সময়ে পেরিয়ে যায়। CPU-এর এক সুতোয় span আর work এক জিনিস — সেখানে এটা চিহ্নিত bubble-ই, আর বড় ডেটায় [Merge](./merge-sort.mdx)/[Quick](./quick-sort.mdx)-এর O(n log n) ছুঁতে পারে না।

## সাধারণ ভুল আর edge case

**১. জোড়া overlap করিয়ে ফেলা (`i += 2`-এর বদলে `i++`)।**
একই phase-এ (i, i+1) আর (i+1, i+2) দুটোই চালালে একই উপাদান এক phase-এ দুবার নড়ে যায় — sequential-এ ফল হয়তো ঠিকই আসে (সেটা তখন অন্য algorithm), কিন্তু বিচ্ছিন্নতার গ্যারান্টি উধাও: parallel-এ চালালেই race। Brick-এর প্রাণই হলো জোড়া বিচ্ছিন্ন।

**২. এক phase দেখেই থামার সিদ্ধান্ত।**
`sorted` flag শুধু odd phase-এর পর চেক করলে এমন অবস্থায় থেমে যাবে যেখানে even phase-এ এখনো inversion বাকি। থামার একক হলো পূর্ণ iteration: odd + even দুটোই swap-মুক্ত হতে হবে।

**৩. Boundary-এর শর্ত ভুল।**
লুপ `i < arr.length` পর্যন্ত চালালে শেষ ঘরে `arr[i + 1]` হয় `undefined` — JS-এ চুপচাপ অদ্ভুত ফল, C/Java-তে সোজা out-of-bounds। শর্ত সবসময় `i < arr.length - 1`।

**৪. Single-core-এ গতির আশা।**
"Parallel-এর জন্য বানানো" শুনে CPU-তে merge/quick-এর প্রতিদ্বন্দ্বী ভাবা ভুল। এক সুতোয় এটা O(n²)-এর bubble-ঘরানার algorithm; এর রাজ্য অনেক-হাতের hardware। বাছাই টেবিলে জায়গাটা এভাবেই মনে রাখো — [সব Sort-এর তুলনা](./sorting-comparison.mdx)।

**৫. Early-exit flag বাদ দেওয়া।**
flag ছাড়া প্রতিবার পুরো ঘুরেই যাবে; sorted বা প্রায়-sorted input-এ O(n²) সময় জলে। flag-টুকুই best case-কে O(n)-এ নামায় — bubble-এর `swapped`-এর মতোই।

## অনুশীলন

- **সহজ ১:** `[5, 2, 9, 1, 7]`-এ হাতে পুরো dry run চালাও: প্রতি phase-এর পর array লেখো। মোট কয়টা phase, কয়টা swap? (কোড দিয়ে মিলিয়ে নিতে পারো।)
- **সহজ ২:** `[1, 2, 3, 4, 5]` আর `[5, 4, 3, 2, 1]` — দুটোতেই কত phase লাগে, কেন? দ্বিতীয়টায় সর্বনিম্ন `1`-এর যাত্রাপথ phase ধরে ধরে লিখে দেখাও।
- **মাঝারি ১:** যুক্তি দাও কেন কোনো উপাদান এক phase-এ এক ঘরের বেশি সরতে পারে না, আর সেখান থেকে দেখাও worst case-এ n phase-এর বেশি লাগে না। (হিন্ট: এক phase-এ এক উপাদান সর্বোচ্চ কয়টা জোড়ায় থাকতে পারে?)
- **মাঝারি ২:** `oddEvenSort`-এ swap counter যোগ করো; একই random input-এ [Bubble Sort](./bubble-sort.mdx) চালিয়ে দুটোর তুলনা আর swap-এর সংখ্যা মাপো। সংখ্যাগুলো কেন কাছাকাছি আসে, ব্যাখ্যা করো।
- **কঠিন:** কল্পনা করো n/2-টা worker আছে; প্রতি worker এক phase-এ ঠিক একটা জোড়া সামলায়, আর দুই phase-এর মাঝে একটা barrier আছে (সবাই শেষ না হলে কেউ এগোয় না)। এই মডেলে pseudocode লেখো। তারপর হিসাব করো: wall-clock সময় কত, মোট কাজ কত — আর দেখাও work-এর দিক থেকে এটা serial-এর চেয়ে এক ফোঁটাও সাশ্রয়ী নয়।

## সারসংক্ষেপ

- Odd-even (brick) sort = bubble sort-এর কাজকে disjoint জোড়ার দুই phase-এ সাজানো: odd phase-এ (১,২), (৩,৪)… তারপর even phase-এ (০,১), (২,৩)…
- জোড়া বিচ্ছিন্ন বলেই এক phase-এর সব তুলনা **একসাথে** চলতে পারে — algorithm-টা জন্মেছিলই সমান্তরাল প্রসেসরের জন্য।
- থামার শর্ত: এক পূর্ণ iteration (odd + even) swap-মুক্ত। Serial-এ O(n²) সময়, O(1) জায়গা, stable; best case O(n)।
- সমান্তরালের আসল পাঠ: **মোট কাজ** O(n²)-ই থাকে, বদলায় **wall-clock** — n/2 হাত থাকলে O(n)।
- CPU-এর বাস্তবে এটা bubble-এরই ভাই — ধারণা শেখার, production-এর নয়; বাছাইয়ের নিয়ম দেখো [তুলনা টেবিলে](./sorting-comparison.mdx)।
