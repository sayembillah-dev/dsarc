## কী শিখব

- দশটা algorithm-এর পাশাপাশি তুলনা: time, space, stability
- Comparison sort-এর তাত্ত্বিক সিলিং কেন O(n log n), আর অ-তুলনা দল কীভাবে তার বাইরে যায়
- পরিস্থিতি অনুযায়ী বাছাই: কখন কোনটা
- বাস্তব জগতের sort-গুলো (TimSort) আসলে কী করে

## ধারণা

একই সমস্যার দশটা সমাধান শেখা শেষ। এবার পাশাপাশি রাখি। মনে করো [Why Sorting](./why-sorting.mdx)-এর তিন মাপকাঠি: time, space, stability — সাথে এবার চতুর্থটাও: **খেলার নিয়ম**, অর্থাৎ তুলনা দিয়ে না তুলনা ছাড়া। এগুলো দিয়েই বিচার।

টেবিলটা মুখস্থ করার নয়, প্যাটার্ন দেখার:

- **O(n²) তুলনা-দল** (bubble, selection, insertion, odd-even, cycle): সরল, ছোট ডেটায় যথেষ্ট, ছোট constant factor। দলের ভেতরে দুজন বিশেষ প্রতিভা: odd-even-এর কাজ disjoint জোড়ায় সাজানো, তাই সমান্তরাল hardware-এ wall-clock O(n); আর cycle-এর লড়াই অন্য মেট্রিক্সে — মেমরিতে লেখা প্রায় n-এ নামানো।
- **O(n log n) দল** (merge, quick, heap): বড় ডেটার জন্য, প্রত্যেকের একটা করে স্বাগতিক দাম।
- **অ-তুলনা দল** (counting, bucket): খেলাই বদলে রৈখিকের কাছে — কিন্তু শর্তসাপেক্ষে। counting-এর range ছোট (k ≈ n) চাই, bucket-এর ডেটা সমানভাবে ছড়ানো চাই; শর্ত ভাঙলে bucket আবার O(n²)-এ ফিরে আসে।
- Best case-এ O(n) শুধু যারা **adaptive** (bubble-এর flag, insertion-এর early থামা, odd-even-এর flag): ডেটা প্রায় sorted হলে এঁরাই জেতে।

## O(n log n)-এর নিচে কেন যাওয়া যায় না

টেবিলের প্রথম আটটাই comparison-based, মানে সিদ্ধান্ত নেয় দুটো তুলনা দিয়ে। চিন্তাটা এমন: n-টা উপাদানের সম্ভাব্য সাজানো আছে n! রকম। প্রতি তুলনা একটা হ্যাঁ/না উত্তর দেয়, মানে সম্ভাব্য উত্তর অর্ধেক করে। তাহলে k-টা তুলনায় আলাদা করা যায় সর্বোচ্চ 2ᵏ রকম ফল। সব n! রকম আলাদা করতে 2ᵏ ≥ n!, মানে k ≥ log₂(n!) ≈ n log n। **কোনো comparison sort-ই গড়ে এর নিচে নামতে পারে না।**

তাহলে শেষ দুজন, [Counting](./counting-sort.mdx) আর [Bucket](./bucket-sort.mdx), কীভাবে রৈখিকের কাছে যায়? ওরা খেলাই বদলায়: তুলনা না করে সংখ্যার মান/পরিসর নিয়ে কাজ করে। মানে সিলিংটা খেলার নিয়মের, সার্বজনীন না — নিয়ম বদলালেই দেয়াল আর থাকে না, তবে নতুন নিয়মের নিজস্ব শর্ত (ডেটার গঠন) আর দাম (বাড়তি জায়গা) মেনে নিতে হয়।

## বাছাই-নিয়ম: পরিস্থিতি দেখে অস্ত্র

| পরিস্থিতি | পছন্দ | কেন |
|-----------|-------|-----|
| বাস্তব প্রোডাকশন | ভাষার built-in `sort()` | TimSort: tested, tuned, stable |
| ছোট array (n < ~50) | Insertion | constant factor ছোট, adaptive |
| প্রায় sorted ডেটা | Insertion | প্রায় O(n) |
| Stability জরুরি | Merge (বা built-in) | সমানদের ক্রম বজায় |
| Memory কঠোর + নিশ্চিততা চাই | Heap | in-place তবু worst case O(n log n) |
| গড় গতি, বড় random ডেটা | Quick (random pivot) | cache-বান্ধব, গড়ে দ্রুততম |
| ছোট পূর্ণসংখ্যা range (k ≈ n) | Counting | তুলনাই ছাড়া, সোজা রৈখিক |
| সমানভাবে ছড়ানো float ডেটা | Bucket | গড়ে রৈখিক, ভেতরে insertion |
| লেখা ব্যয়বহুল মেমরি (flash/EEPROM) | Cycle | প্রতি উপাদান একবারই লেখা, মোট প্রায় n |
| লেখা কম, তবে swap-ভিত্তিকই চাই | Selection | swap সর্বোচ্চ n−1 |
| সমান্তরাল hardware / GPU | Odd-Even | phase-ভিত্তিক disjoint জোড়া, wall-clock O(n) |
| শেখার ক্লাসরুম | Bubble | O(n²) কেমন লাগে, চোখে দেখা |

একটা লুকানো পাঠ: বাস্তবের সেরা sort-গুলো **hybrid**। TimSort ছোট টুকরোয় insertion চালায়, বড় টুকরো merge করে, আর ডেটায় আগে থেকে থাকা sorted দৌড় (run) কাজে লাগায়। মানে তুমি যে দশটা শিখলে, তার ধারণাগুলোই মিলে বানায় তোমাদের ব্রাউজারের `sort()`। ধারণা শেখাই আসল, নাম মুখস্থ নয়।

## Complexity-র দৃষ্টিতে শেষ কথা

- সাধারণ নিয়ম: O(n²) গোষ্ঠী n ≈ 10⁴-এর পর অব্যবহারযোগ্য (১০⁴ হলে 10⁸ তুলনা)।
- O(n log n) গোষ্ঠী n = 10⁶-ও সহজ (প্রায় ২ কোটি ধাপ)।
- অ-তুলনা দলের রৈখিক দাবি ডেটার শর্তের ওপর দাঁড়ানো: counting-এর k যদি n² হয়ে যায়, আর bucket-এর সব ডেটা এক বালতিতে গাদা হলে, দুটোই তাদের জাদু হারায়।
- কিন্তু constant factor-এর খেলা ছোট ডেটায় উল্টে যায়: n = 20-এ insertion, quick-কে হারায়। তাই বাস্তব engine-গুলো hybrid।

## সাধারণ ভুল আর edge case

**১. টেবিল মুখস্থ, কারণ না বোঝা।**
"Quick-এর worst O(n²)" মুখস্থ রাখলে interview-এর পরের প্রশ্নে আটকে যাবে: কেন? পার্থক্য হলো pivot-এর ভাগ্যে, যেটা [Quick Sort](./quick-sort.mdx)-এর dry run থেকে আসে। টেবিলের প্রতি ঘরের পেছনের গল্পটা জানো।

**২. "O(n log n) মানে সবসময় দ্রুততম" ভাবা।**
ছোট বা near-sorted ডেটায় insertion জেতে। Complexity বলে n বড় হলে কী হয়, ছোটে constant factor-ই রাজা।

**৩. Stability-এর প্রয়োজনীয়তা উপেক্ষা।**
Record-এর তালিকায় একাধিক নিয়মে sort করতে গিয়ে unstable algorithm বসালে আগের নিয়মের ক্রম নষ্ট। তখন merge বা built-in, অথবা key-গুলো এক comparator-এ মেলাও।

**৪. Space ভুলে যাওয়া।**
Merge-এর O(n) বাড়তি জায়গা ছোট ডেটায় তুচ্ছ, কিন্তু গিগাবাইট-ডেটা বা embedded সিস্টেমে সেটাই নির্ণায়ক। "In-place কিনা" প্রশ্নটা বাছাইয়ের আগে করো।

**৫. নিজের sort লেখার দুষ্টসাহস।**
Production-এ built-in `sort()` ব্যবহার করো। নিজেরটা শেখার জন্য, benchmark ছাড়া বদলাবে না। যে সমস্যায় আসলেই দরকার (বিশেষ ডেটা, বিশেষ সীমাবদ্ধতা), সেখানে জ্ঞানটা কাজে লাগবে।

## অনুশীলন

- **সহজ ১:** নিজের কথায় লেখো: কেন selection sort-এর best case আর worst case একই, অথচ insertion-এর না?
- **সহজ ২:** তোমাকে বলা হলো ৫০০টা record sort করতে, যেখানে সমান key-এর ক্রম বজায় রাখা জরুরি আর memory ঢের আছে। কোনটা নেবে, কেন?
- **মাঝারি ১:** Embedded যন্ত্রে ১০ লাখ সংখ্যা sort করতে হবে, RAM মাত্র কয়েক KB বাড়তি, আর worst case কখনও O(n²) যাবে না। টেবিল থেকে কে বাদ যায়, কে থাকে? যুক্তি দাও।
- **মাঝারি ২:** তিনটা array বানাও (random, sorted, সব-সমান), প্রতিটায় built-in `sort()` আর তোমার লেখা quick sort-এর সময় মাপো। সব-সমান array-তে কী ঘটল, কেন? (হিন্ট: সবাই pivot-এর সমান, ভাগ কেমন হয়?)
- **মাঝারি ৩:** দুই পরিস্থিতি লেখো — একটায় counting sort quick sort-কেও হারায়, আরেকটায় counting sort-ই অসম্ভব। প্রতিটার কারণ k আর n-এর সম্পর্ক দিয়ে ব্যাখ্যা করো।
- **কঠিন:** একটা নথি লেখো (আধা পৃষ্ঠা): "আমার ভাষার built-in sort ভেতরে কী চলে"। V8-এর TimSort নিয়ে খুঁজে দেখো, কোথায় insertion, কোথায় merge, run কী জিনিস। নিজের শেখা দশটার কোন কোনটার ছায়া পেলে?

## সারসংক্ষেপ

- দশটা sort, তিন দল: O(n²) সরল তুলনা-দল, O(n log n) বড় খেলার দল, আর শর্তসাপেক্ষে রৈখিক অ-তুলনা দল।
- Comparison sort-এর সিলিং O(n log n), কারণ n! রকম সাজানো আলাদা করতে তত তুলনা লাগেই; counting-bucket সেই দেয়াল টপকায় খেলার নিয়ম বদলে, শর্ত আর জায়গার বিনিময়ে।
- "সেরা" নেই, আছে পরিস্থিতি-ভিত্তিক পছন্দ: ছোট/near-sorted-এ insertion, stability-তে merge, in-place+নিশ্চয়তায় heap, গড় গতিতে quick, ছোট range-এ counting, ছড়ানো float-এ bucket, লেখা-সংকটে cycle, অনেক-হাতের hardware-এ odd-even।
- বাস্তবের sort hybrid: তোমার শেখা ধারণাগুলোই মিলে বানায়।
- Production-এ built-in `sort()`; নিজেরটা শেখার, নিয়তির না।
