## কী শিখব

- ছয়টা algorithm-এর পাশাপাশি তুলনা: time, space, stability
- Comparison sort-এর তাত্ত্বিক সিলিং কেন O(n log n)
- পরিস্থিতি অনুযায়ী বাছাই: কখন কোনটা
- বাস্তব জগতের sort-গুলো (TimSort) আসলে কী করে

## ধারণা

একই সমস্যার ছয়টা সমাধান শেখা শেষ। এবার পাশাপাশি রাখি। মনে করো [Why Sorting](./why-sorting.mdx)-এর তিন মাপকাঠি: time, space, stability। এগুলো দিয়েই বিচার।

## মূল টেবিল

| Algorithm | Best | Average | Worst | Space | Stable |
|-----------|------|---------|-------|-------|--------|
| [Bubble](./bubble-sort.mdx) | O(n) | O(n²) | O(n²) | O(1) | হ্যাঁ |
| [Selection](./selection-sort.mdx) | O(n²) | O(n²) | O(n²) | O(1) | না |
| [Insertion](./insertion-sort.mdx) | O(n) | O(n²) | O(n²) | O(1) | হ্যাঁ |
| [Merge](./merge-sort.mdx) | O(n log n) | O(n log n) | O(n log n) | O(n) | হ্যাঁ |
| [Quick](./quick-sort.mdx) | O(n log n) | O(n log n) | O(n²) | O(log n) | না |
| [Heap](./heap-sort.mdx) | O(n log n) | O(n log n) | O(n log n) | O(1) | না |

টেবিলটা মুখস্থ করার নয়, প্যাটার্ন দেখার:

- **O(n²) দল** (bubble, selection, insertion): সরল, ছোট ডেটায় যথেষ্ট, ছোট constant factor।
- **O(n log n) দল** (merge, quick, heap): বড় ডেটার জন্য, প্রত্যেকের একটা করে স্বাগতিক দাম।
- Best case-এ O(n) শুধু যারা **adaptive** (bubble-এর flag, insertion-এর early থামা): ডেটা প্রায় sorted হলে এঁরাই জেতে।

## O(n log n)-এর নিচে কেন যাওয়া যায় না

এই ছয়টাই comparison-based, মানে সিদ্ধান্ত নেয় দুটো তুলনা দিয়ে। চিন্তাটা এমন: n-টা উপাদানের সম্ভাব্য সাজানো আছে n! রকম। প্রতি তুলনা একটা হ্যাঁ/না উত্তর দেয়, মানে সম্ভাব্য উত্তর অর্ধেক করে। তাহলে k-টা তুলনায় আলাদা করা যায় সর্বোচ্চ 2ᵏ রকম ফল। সব n! রকম আলাদা করতে 2ᵏ ≥ n!, মানে k ≥ log₂(n!) ≈ n log n। **কোনো comparison sort-ই গড়ে এর নিচে নামতে পারে না।**

তাহলে counting sort, radix sort-এরা কী? ওরা খেলাই বদলায়: তুলনা না করে সংখ্যার অঙ্ক/পরিসর নিয়ে কাজ করে, বিশেষ ডেটায় O(n) পর্যন্ত নামে। মানে সিলিংটা খেলার নিয়মের, সার্বজনীন না।

## বাছাই-নিয়ম: পরিস্থিতি দেখে অস্ত্র

| পরিস্থিতি | পছন্দ | কেন |
|-----------|-------|-----|
| বাস্তব প্রোডাকশন | ভাষার built-in `sort()` | TimSort: tested, tuned, stable |
| ছোট array (n < ~50) | Insertion | constant factor ছোট, adaptive |
| প্রায় sorted ডেটা | Insertion | প্রায় O(n) |
| Stability জরুরি | Merge (বা built-in) | সমানদের ক্রম বজায় |
| Memory কঠোর + নিশ্চিততা চাই | Heap | in-place তবু worst case O(n log n) |
| গড় গতি, বড় random ডেটা | Quick (random pivot) | cache-বান্ধব, গড়ে দ্রুততম |
| লেখা ব্যয়বহুল মেমরি | Selection | swap সর্বোচ্চ n-1 |
| শেখার ক্লাসরুম | Bubble | O(n²) কেমন লাগে, চোখে দেখা |

একটা লুকানো পাঠ: বাস্তবের সেরা sort-গুলো **hybrid**। TimSort ছোট টুকরোয় insertion চালায়, বড় টুকরো merge করে, আর ডেটায় আগে থেকে থাকা sorted দৌড় (run) কাজে লাগায়। মানে তুমি যে ছয়টা শিখলে, তার তিনটাই আসলে একসাথে কাজ করে তোমাদের ব্রাউজারের `sort()`-এ। ধারণা শেখাই আসল, নাম মুখস্থ নয়।

## Complexity-র দৃষ্টিতে শেষ কথা

- সাধারণ নিয়ম: O(n²) গোষ্ঠী n ≈ 10⁴-এর পর অব্যবহারযোগ্য (১০⁴ হলে 10⁸ তুলনা)।
- O(n log n) গোষ্ঠী n = 10⁶-ও সহজ (প্রায় ২ কোটি ধাপ)।
- কিন্তু constant factor-এর খেলা ছোট ডেটায় উল্টে যায়: n = 20-এ insertion, quick-কে হারায়। তাই বাস্তব engine-গুলো hybrid।

## সাধারণ ভুল আর edge case

**১. টেবিল মুখস্থ, কারণ না বোঝা।**
"Quick-এর worst O(n²)" মুখস্থ রাখলে interview-এর পরের প্রশ্নে আটকে যাবে: কেন? পার্থক্য হলো pivot-এর ভাগ্যে, যেটা [Quick Sort](./quick-sort.mdx)-এর dry run থেকে আসে। টেবিলের প্রতি ঘরের পেছনের গল্পটা জানো।

**২. "O(n log n) মানে সবসময় দ্রুততম" ভাবা।**
ছোট বা near-sorted ডেটায় insertion জেতে। Complexity বলে n বড় হলে কী হয়, ছোটে constant factor-ই রাজা।

**৩. Stability-এর প্রয়োজনীয়তা উপেক্ষা।**
Record-এর তালিকায় একাধিক নিয়মে sort করতে গিয়ে unstable algorithm বসালে আগের নিয়মের ক্রম নষ্ট। তখন merge বা built-in, অথবা key-গুলো এক comparator-এ মেলাও।

**৪. Space ভুলে যাওয়া।**
Merge-এর O(n) বাড়তি জায়গা ছোট ডেটায় তুচ্ছ, কিন্তু গিগাবাইট-ডেটা বা embedded সিস্টেমে সেটাই নির্ণায়ক। "In-place কিনা" প্রশ্নটা বাছাইয়ের আগে করো।

**৫. নিজের sort লেখার দুষ্টসাহস।**
Production-এ built-in `sort()` ব্যবহার করো। নিজেরটা শেখার জন্য, benchmark ছাড়া বদলাবে না। যে সমস্যায় আসলেই দরকার (বিশেষ ডেটা, বিশেষ সীমাবদ্ধতা), সেখানে জ্ঞানটা কাজে লাগবে।

## অনুশীলন

- **সহজ ১:** নিজের কথায় লেখো: কেন selection sort-এর best case আর worst case একই, অথচ insertion-এর না?
- **সহজ ২:** তোমাকে বলা হলো ৫০০টা record sort করতে, যেখানে সমান key-এর ক্রম বজায় রাখা জরুরি আর memory ঢের আছে। কোনটা নেবে, কেন?
- **মাঝারি ১:** Embedded যন্ত্রে ১০ লাখ সংখ্যা sort করতে হবে, RAM মাত্র কয়েক KB বাড়তি, আর worst case কখনও O(n²) যাবে না। টেবিল থেকে কে বাদ যায়, কে থাকে? যুক্তি দাও।
- **মাঝারি ২:** তিনটা array বানাও (random, sorted, সব-সমান), প্রতিটায় built-in `sort()` আর তোমার লেখা quick sort-এর সময় মাপো। সব-সমান array-তে কী ঘটল, কেন? (হিন্ট: সবাই pivot-এর সমান, ভাগ কেমন হয়?)
- **কঠিন:** একটা নথি লেখো (আধা পৃষ্ঠা): "আমার ভাষার built-in sort ভেতরে কী চলে"। V8-এর TimSort নিয়ে খুঁজে দেখো, কোথায় insertion, কোথায় merge, run কী জিনিস। নিজের শেখা ছয়টার কোন কোনটার ছায়া পেলে?

## সারসংক্ষেপ

- ছয়টা sort, দুই দল: O(n²) সরল দল, O(n log n) বড় খেলার দল।
- Comparison sort-এর সিলিং O(n log n), কারণ n! রকম সাজানো আলাদা করতে তত তুলনা লাগেই।
- "সেরা" নেই, আছে পরিস্থিতি-ভিত্তিক পছন্দ: ছোট/near-sorted-এ insertion, stability-তে merge, in-place+নিশ্চয়তায় heap, গড় গতিতে quick।
- বাস্তবের sort hybrid: তোমার শেখা ধারণাগুলোই মিলে বানায়।
- Production-এ built-in `sort()`; নিজেরটা শেখার, নিয়তির না।
