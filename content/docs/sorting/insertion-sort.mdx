## কী শিখব

- Insertion sort-এর নিয়ম: বাম অংশ sorted রাখো, নতুনটা সেখানে ঢোকাও
- পুরো dry run: key তোলা, বড়দের ডানে সরানো, জায়গায় বসানো
- Swap না, shift: এই পার্থক্যই কার্ডের খেলার সঙ্গে মেলে
- Near-sorted ডেটায় কেন প্রায় O(n), আর কেন ছোট array-তে সবাই এটাই ব্যবহার করে
- Complexity-র পুরো হিসাব

## ধারণা

তাস খেলার কথা ভাবো। হাতে একটা একটা করে নতুন কার্ড আসছে। প্রতিবার তুমি নতুন কার্ডটা তুলে হাতের sorted কার্ডের সঙ্গে তুলনা করো, ডান থেকে বামে, যতক্ষণ না ঠিক জায়গা পাচ্ছ। বড় কার্ডগুলো এক ঘর সরে যায়, নতুনটা ফাঁকায় ঢুকে যায়।

Insertion Sort হুবহু এটাই। Array-র বাম অংশটাকে সবসময় sorted রাখে (তাসের হাত), আর ডান থেকে একটা একটা উপাদান তুলে (নতুন কার্ড) সেই sorted অংশে সরিয়ে সরিয়ে ঢোকায়।

[Bubble](./bubble-sort.mdx) আর [Selection](./selection-sort.mdx)-এর সঙ্গে পার্থক্য পরিষ্কার করো: bubble-এ প্রতি pass-এ **একজনের চূড়ান্ত জায়গা** হয়, selection-এও তাই। কিন্তু insertion-এ বাম অংশ sorted থাকলেও সেটা **চূড়ান্ত না**, পরে আরও ছোট কেউ এলে ওখানেও ঢুকবে। এই সূক্ষ্ম পার্থক্যটা মাথায় রাখো।

## Dry run: `[5, 2, 4, 6, 1, 3]`

শুরুতে বাম অংশে একটাই উপাদান `[5]`, যা একাই sorted:

| ধাপ | key | কে কে ডানে সরল | array-এর অবস্থা (বাম অংশ sorted) |
|-----|-----|------------------|-----------------------------------|
| 1 | 2 | 5 সরল | `[2, 5]` বাকি `[4, 6, 1, 3]` |
| 2 | 4 | 5 সরল | `[2, 4, 5]` বাকি `[6, 1, 3]` |
| 3 | 6 | কেউ না | `[2, 4, 5, 6]` বাকি `[1, 3]` |
| 4 | 1 | 6, 5, 4, 2 সবাই সরল | `[1, 2, 4, 5, 6]` বাকি `[3]` |
| 5 | 3 | 6, 5, 4 সরল | `[1, 2, 3, 4, 5, 6]` |

ধাপ ৪-এ দেখো, key=1-এর জন্য চারজনকে এক ঘর করে ডানে সরাতে হলো। আর ধাপ ৩-এ key=6 ইতিমধ্যে বড়, কেউ নড়ল না, তুলনা মাত্র একটা। এই "যতটুকু দরকার ততটুকুই সরানো" চরিত্রটাই এর শক্তি।

## কোড: নিজে বানাও insertionSort

```js
function insertionSort(arr) {
  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];            // নতুন কার্ড তুললাম
    let j = i - 1;

    while (j >= 0 && arr[j] > key) {
      arr[j + 1] = arr[j];         // বড়টা এক ঘর ডানে
      j--;
    }

    arr[j + 1] = key;              // ফাঁকা জায়গায় key বসল
  }
  return arr;
}

console.log(insertionSort([5, 2, 4, 6, 1, 3])); // [1, 2, 3, 4, 5, 6]
```

একটা সূক্ষ্ম ব্যাপার: এখানে swap হয় না, **shift** হয়। key আলাদা রেখে বড়গুলোকে এক ঘর করে ঠেলে দিই, শেষে key বসে। কার্ড সাজানোর সঙ্গে মিল ঠিক এখানেই: তুমিও তো কার্ড দুটো বদল করো না, জায়গা বানিয়ে ঢোকাও।

## কোড ব্রেকডাউন: লাইনে লাইনে

1. `for (let i = 1; ...)` : শুরু index 1 থেকে, কারণ index 0 একাই sorted মনে করা হয়।
2. `const key = arr[i]` : key আলাদা রাখা জরুরি, কারণ while-এ সরানো শুরু হলে `arr[i]`-এর ঘরে অন্যজন চলে আসে।
3. `while (j >= 0 && arr[j] > key)` : দুই শর্তের ক্রম জরুরি। আগে সীমা চেক, তারপর তুলনা, নইলে `arr[-1]` পড়তে গিয়ে গোলমাল। শর্ত উল্টো হলে (key ছোট হলেই থামো) stability নষ্ট হত, কারণ সমানদের সরিয়ে দিত।
4. `arr[j + 1] = arr[j]` : বড়টা ডানে সরল, আসল মান হারায় না, কারণ key আলাদা আছে।
5. `arr[j + 1] = key` : while থামার জায়গায় j এক ঘর পিছিয়ে থাকে, তাই বসতে হয় `j + 1`-এ। এই off-by-one জায়গাটা সবচেয়ে বেশি ভুল হয়।

## Complexity

| কেস | Time | কেন |
|-----|------|-----|
| Worst (উল্টো sorted) | O(n²) | প্রতিটা key-এর জন্য পুরো বাম অংশ সরে |
| Average | O(n²) | গড়ে অর্ধেক সরে |
| Best (ইতিমধ্যে sorted) | **O(n)** | প্রতি key-তে একটা তুলনা, শূন্য সরানো |
| Space | O(1) | in-place |
| Stable | হ্যাঁ | সমানদের কখনও সরায় না (`>` strict) |

Derivation: worst case-এ i-তম key-এর জন্য i-টা সরানো, মোট 1+2+...+(n-1) = n(n-1)/2, O(n²)। কিন্তু sorted ডেটায় প্রতি key-তে while একবারই তুলনা করে থেমে যায়, মোট n-1 তুলনা, O(n)। মানে এই algorithm-এর খরচ ডেটার "কতটা এলোমেলো" তার সঙ্গে সরাসরি জড়িত। এই বৈশিষ্ট্যের আনুষ্ঠানিক নাম **adaptive**।

এই কারণেই বাস্তব জগতের sort-গুলো (যেমন TimSort, JS-এর built-in-এর ভিত্তি) ছোট টুকরোগুলোতে insertion sort-ই চালায়: ছোট বা প্রায়-sorted ডেটায় এর constant factor এত কম যে O(n log n) algorithm-গুলোকেও হারায়।

## সাধারণ ভুল আর edge case

**১. `arr[j + 1] = key` লিখতে গিয়ে off-by-one।**
While শেষে j যেখানে থেমেছে, সেটা বসানোর ঘরের **এক ঘর বামে**। `arr[j] = key` লিখলে ঘর মুছে যায়। নিশ্চিত হতে ছোট উদাহরণে dry run করো।

**২. While-এর শর্তের ক্রম উল্টানো।**
`arr[j] > key && j >= 0` লিখলে j = -1-এ `arr[-1]` পড়তে যায়। JavaScript-এ error না দিয়ে `undefined` আসে, তুলনা false, ভুলটা নিঃশব্দ। সীমা আগে, তুলনা পরে।

**৩. key না রেখে সরাসরি `arr[i]` নিয়ে খেলা।**
While-এর প্রথম সরানোতেই `arr[i]`-এর জায়গায় অন্য মান চলে আসে। key আলাদা না রাখলে আসল মানটা হারিয়ে যায়, ফল গোলমাল।

**৪. `>=` লিখে stability নষ্ট করা।**
`arr[j] >= key` দিলে সমান মানও সরে যায়, সমানদের ক্রম উল্টে যায়। Strictly `>` রাখলে সমানেরা অক্ষত থাকে, sort stable থাকে।

**৫. বড় random ডেটায় insertion আশা করা।**
Insertion-এর জাদু শুধু ছোট বা near-sorted ডেটায়। বড় random ডেটায় O(n²) স্পষ্ট, সেখানে [Merge](./merge-sort.mdx) বা [Quick](./quick-sort.mdx)। অস্ত্র বাছাই ডেটার চরিত্র দেখে।

## অনুশীলন

- **সহজ ১:** `[9, 7, 5, 3]`-এ পুরো dry run কাগজে: প্রতি ধাপে key কে, কয়টা সরানো হলো, মোট কত।
- **সহজ ২:** ইতিমধ্যে sorted `[1, 2, 3, 4, 5]`-এ চালাও। মোট কয়টা তুলনা, কয়টা সরানো? এই সংখ্যা দুটোই কেন O(n)-এর প্রমাণ?
- **মাঝারি ১:** একই array-তে তিনটা sort (bubble, selection, insertion) কাগজে চালিয়ে তুলনা+সরানোর হিসাব তুলনা করো। কার চরিত্র কেমন, এক লাইনে লেখো।
- **মাঝারি ২:** Insertion sort দিয়ে descending (বড় থেকে ছোট) sort লেখো। কোন শর্ত বদলালে, আর dry run-এ কী বদলায়?
- **কঠিন:** Binary insertion sort বানাও: key-এর জায়গা খুঁজতে linear scan না, বামের sorted অংশে [Binary Search](../searching/binary-search.mdx) লাগাও। তুলনা কমে O(n log n)-এ আসে, কিন্তু মোট সময় কি তবু O(n²)? কেন? (হিন্ট: খোঁজা সস্তা হলেও সরানো তো লাগছেই।)

## সারসংক্ষেপ

- Insertion sort: বাম অংশ sorted রাখো, নতুন key সরিয়ে সরিয়ে ঢোকাও, কার্ড সাজানোর মতো।
- Swap না shift; key আলাদা রাখো; বসানোর ঘর `j + 1`।
- Worst/average O(n²), কিন্তু near-sorted-এ O(n) কাছাকাছি, এজন্যই adaptive।
- Stable, in-place, ছোট ডেটায় constant factor ছোট, তাই বাস্তব sort-গুলোর ভেতরে এরই জায়গা।
- বাম অংশ sorted হলেও চূড়ান্ত না, এই সূক্ষ্মতা bubble/selection থেকে আলাদা করে।
