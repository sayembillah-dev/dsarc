এই অধ্যায়ের বাকি পাতাগুলোতে আমরা complexity গণনা করতে শিখব। কিন্তু গণনায় যাওয়ার আগে একটা প্রশ্নের উত্তর দরকার: এই মাপাহাটিটা আসলে কেন? এখানেই সেই উত্তর।

## কী শিখব

- কেন "কত সেকেন্ড লাগল" দিয়ে algorithm মাপা যায় না
- input বড় হলে কাজ কত দ্রুত বাড়ে, এই বৃদ্ধির হার (growth rate) কেন আসল মাপকাঠি
- n, n² আর 2ⁿ বাস্তবে কত বিশাল ফারক, সংখ্যা দিয়ে
- ধাপ-কাউন্টার (operation counter) দিয়ে দুইটা সার্চ তুলনা করা, মেশিন-নিরপেক্ষভাবে
- `Date.now()` দিয়ে সময় মাপা কখন কাজে লাগে, আর কোথায় এর ফাঁদ

## ধারণা

ধরো, দুইটা অ্যাপ বানালে। দুটোর কাজ একই: দশ লক্ষ ফোন নম্বরের তালিকা থেকে একটা নম্বর খুঁজে বলা "আছে না নেই"। প্রথম অ্যাপটা চাপ দিলে পলকে উত্তর দেয়। দ্বিতীয়টা একটা পুরো ঘণ্টা ঘোরে, তারপর উত্তর দেয়।

দুটোর code-ই "ঠিক": দুটোই সঠিক উত্তর দেয়, কোনোটায় bug নেই। তাহলে ফারকটা কোথায়? ফারকটা algorithm-এ। আর সেই ফারকটা মাপার একটা ভাষা দরকার, সেই ভাষাটার নামই complexity।

প্রথমে যে মাপটা মাথায় আসে: "কত সেকেন্ড লাগল?" কিন্তু এই মাপটা তিন কারণে অকাজের:

1. **মেশিন বদলালেই সংখ্যা পাল্টায়।** তোমার gaming PC-তে ৩ সেকেন্ড নেওয়া code দাদুর ২০১২-এর ল্যাপটপে ৮ সেকেন্ড নেবে। কোনটা algorithm-এর "আসল" সংখ্যা?
2. **একই মেশিনেও ফল পাল্টায়।** Chrome-এ ৪০টা ট্যাব খোলা থাকলে, antivirus স্ক্যান চললে, এমনকি OS কীসে ব্যস্ত তার ওপরেও সময় ওঠানামা করে।
3. **সবচেয়ে বড়টা: এটা ভবিষ্যৎ বলতে পারে না।** ঘড়ি বলে শুধু এই input-এ, এই মেশিনে, এই মুহূর্তে কী হয়েছে। কাল input দশগুণ হলে কী হবে, ঘড়ি চুপ।

তাই আমরা অন্য একটা জিনিস মাপি: **input-এর সাইজ n বাড়লে কাজের পরিমাণ কীভাবে বাড়ে।** এই বৃদ্ধির হারটা মেশিন-নিরপেক্ষ আর ভবিষ্যৎ বলতে পারে। এর নামকরণের পুরো নিয়ম শিখবে [Asymptotic Notation](./asymptotic-notation.mdx)-এ; আজ শুধু অনুভূতিটা পরিষ্কার করি।

## ধাপে ধাপে: সংখ্যা দিয়ে ভয় দেখানো

ধরো একটা সাধারণ PC সেকেন্ডে প্রায় 10^9-টা ছোট ধাপ (operation) করতে পারে। এখন তিন রকম algorithm-এর কথা ভাবো: যার ধাপ লাগে n-টা, যার n²-টা, আর যার 2ⁿ-টা।

| n | n ধাপ | n² ধাপ | 2ⁿ ধাপ |
|------|-------|---------|------------|
| 10 | 10 | 100 | 1024 |
| 20 | 20 | 400 | 1048576 |
| 50 | 50 | 2500 | 1.1 × 10^15 |
| 100 | 100 | 10000 | 1.3 × 10^30 |

শেষ সারিটা সময়ে রূপান্তর করি (10^9 ধাপ প্রতি সেকেন্ডে):

- n²-এর জন্য n = 100 মানে 10000 ধাপ, অর্থাৎ প্রায় 0.00001 সেকেন্ড। চোখের পলকেরও কম।
- 2ⁿ-এর জন্য n = 100 মানে 1.3 × 10^30 ধাপ, অর্থাৎ প্রায় 1.3 × 10^21 সেকেন্ড, প্রায় 4 × 10^13 বছর। বিগ ব্যাং হয়েছে মাত্র 1.4 × 10^10 বছর আগে। অর্থাৎ এই একটা প্রোগ্রাম শেষ করতে ব্রহ্মাণ্ডের বয়সের প্রায় তিন হাজার গুণ সময় লাগবে।

খেয়াল করো, n মাত্র ১০০। কোনো কোটি-কোটি input-এর কথা বলছি না। এজন্যই complexity-এর প্রশ্নটা একদমই "অ্যাকাডেমিক" নয়: ভুল algorithm বেছে নিলে তোমার code শুধু ধীর হবে না, কার্যত চিরকালের জন্য আটকে যাবে।

আরেকটা দৃশ্য দেখি, এবার দুই রকম খোঁজার লড়াই। ধরো sorted তালিকা থেকে একটা সংখ্যা খুঁজতে হবে। লিনিয়ার সার্চ একে একে সব ঘর দেখে। বাইনারি সার্চ মাঝখানে উঁকি দিয়ে প্রতিবার অর্ধেক ফেলে দেয়:

```
শুরু:  [ _ _ _ _ _ _ _ _ _ _ _ _ _ _ _ _ ]    ১৬টা ঘর বাকি
ধাপ ১: [ _ _ _ _ _ _ _ _ ]                     মাঝে দেখে ডান অর্ধেক ফেললাম, বাকি ৮টা
ধাপ ২: [ _ _ _ _ ]                             বাকি ৪টা
ধাপ ৩: [ _ _ ]                                 বাকি ২টা
ধাপ ৪: [ _ ]                                   ১টা, খোঁজ শেষ
```

১৬টা ঘর, মাত্র ৪ ধাপে খোঁজ শেষ। কারণ প্রতি ধাপে সমস্যাটা অর্ধেক হয়ে যাচ্ছে: ১৬ → ৮ → ৪ → ২ → ১। এই "প্রতি ধাপে অর্ধেক" জিনিসটারই নাম log: 2⁴ = 16, তাই log₂(16) = 4।

দুই পদ্ধতির সবচেয়ে খারাপ অবস্থা পাশাপাশি রাখি:

| n | লিনিয়ার সার্চ | বাইনারি সার্চ |
|----------|-----------|----------|
| 10 | 10 | 4 |
| 1000 | 1000 | 10 |
| 100000 | 100000 | 17 |
| 1000000 | 1000000 | 20 |

দশ লক্ষ ঘরের মধ্যে বাইনারি সার্চ মাত্র ২০ ধাপে উত্তর দেয়। এটা কোনো অনুমান নয়: নিচের code-টা চালিয়ে নিজেই গুনে দেখবে।

## কোড: ধাপ গুনে লড়াইটা দেখি

ঘড়ির বদলে আমরা ধাপ গুনবো: প্রতিটা তুলনা মানে ১ ধাপ। এই counter-টা মেশিন-নিরপেক্ষ, তোমার PC আমার PC যাই হোক, সংখ্যা একই আসবে।

```js
// লিনিয়ার সার্চ: প্রথম ঘর থেকে একে একে সব দেখি
function linearSearch(arr, target) {
  let steps = 0;
  for (let i = 0; i < arr.length; i++) {
    steps++;                        // প্রতিটা তুলনা = ১ ধাপ
    if (arr[i] === target) return { index: i, steps };
  }
  return { index: -1, steps };
}

// বাইনারি সার্চ: প্রতিবার মাঝখানে দেখে অর্ধেক ফেলে দিই
// শর্ত: array-টা sorted হতে হবে
function binarySearch(arr, target) {
  let steps = 0;
  let lo = 0;
  let hi = arr.length - 1;
  while (lo <= hi) {
    steps++;                        // প্রতিটা তুলনা = ১ ধাপ
    const mid = (lo + hi) >> 1;
    if (arr[mid] === target) return { index: mid, steps };
    if (arr[mid] < target) lo = mid + 1;   // টার্গেট ডান অর্ধেকে
    else hi = mid - 1;                     // টার্গেট বাম অর্ধেকে
  }
  return { index: -1, steps };
}

const sizes = [10, 1000, 100000];
console.log("n".padEnd(10) + "linear".padEnd(10) + "binary");

for (const n of sizes) {
  const arr = Array.from({ length: n }, (_, i) => i); // [0, 1, 2, ..., n-1]
  const target = n;               // ইচ্ছে করে এমন সংখ্যা যা array-তে নেই, অর্থাৎ worst case
  const lin = linearSearch(arr, target);
  const bin = binarySearch(arr, target);
  console.log(String(n).padEnd(10) + String(lin.steps).padEnd(10) + String(bin.steps));
}
```

Output:

```
n         linear    binary
10        10        4
1000      1000      10
100000    100000    17
```

সংখ্যাগুলো নিজে বিশ্লেষণ করো। n প্রথমে ১০০ গুণ হলো (10 থেকে 1000): লিনিয়ারের ধাপও ঠিক ১০০ গুণ, বাইনারির মাত্র আড়াই গুণ। আবার ১০০ গুণ হলো (1000 থেকে 100000): লিনিয়ারের আবার ১০০ গুণ, বাইনারির এবার দেড় গুণেরও কম। এই আচরণটাই দুই পরিবারের পরিচয়: একটার ধাপ input-এর সমানুপাতিক, অন্যটার ধাপ কার্যত স্থিরের কাছাকাছি।

## ভ্যারিয়েন্ট ১: সত্যিকারের ঘড়ি ধরলে কী হয়

ঘড়ি পুরো বেকার নয়। বড় input-এ trend দেখতে `Date.now()` কাজে লাগে:

```js
function sumUpTo(n) {
  let sum = 0;
  for (let i = 1; i <= n; i++) sum += i;
  return sum;
}

for (let round = 1; round <= 5; round++) {
  const t0 = Date.now();
  sumUpTo(50000000);              // ৫ কোটি বার যোগ
  console.log("round " + round + ": " + (Date.now() - t0) + " ms");
}
```

আমার মেশিনে একটা sample run:

```
round 1: 46 ms
round 2: 46 ms
round 3: 45 ms
round 4: 46 ms
round 5: 44 ms
```

একই code, একই input, একই মেশিন: তবু সংখ্যা মিলিম্যাচ করে না। কখনও কখনও প্রথম round-টা সবচেয়ে ধীর হয়, কারণ JavaScript-এর engine (JIT) তখনও গরম হয়নি। এর ওপরে OS-এর background কাজ আর memory-র অবস্থা মিলে noise তৈরি হয়। তোমার মেশিনে সম্পূর্ণ অন্য সংখ্যা আসবেই, আর সেটাই আসল শিক্ষা: **ঘড়ি trend দেখায়, পরিচয় দেয় না।** ছোট input-এ (কয়েক মিলিসেকেন্ডের কাজ) এই noise-টাই আসল signal-কে ডুবিয়ে দেয়, তখন পরিমাপটাই অর্থহীন। ঘড়ি দিয়ে মাপলেই বড় input নাও, কয়েকবার চালাও, গড় নাও।

## ভ্যারিয়েন্ট ২: ধ্রুবকের জায়গাটা ঠিক কোথায়

একটা প্রশ্ন ঘাপটি মেরে থাকে: "দুটো algorithm-ই যদি n বার ঘোরে, কিন্তু একটা প্রতি ধাপে ১টা কাজ করে আর আরেকটা ৫০টা, দুটো কি সমান?" কাগজে হ্যাঁ, দুটোই একই পরিবারের (O(n))। প্র্যাকটিসে না, একটা আরেকটার ৫০ গুণ ধীর।

তাহলে ধ্রুবক কি গুরুত্বহীন? না। গুরুত্বের ক্রমটা হলো: আগে বৃদ্ধির হার ঠিক করো, তারপর দরকার হলে ধ্রুবক নিয়ে ভাবো। কারণ n যথেষ্ট বড় হলে যত বড় ধ্রুবকওয়ালা O(n)-ই হোক, সে শেষে যে-কোনো O(n²)-কে হারিয়ে দেবেই। কিন্তু দুটো O(n)-এর মধ্যে লড়াই হলে ধ্রুবকই সিদ্ধান্ত দেয়।

প্রতিযোগিতামূলক প্রোগ্রামিং আর ইন্টারভিউতে একটা চেনা rule of thumb আছে: সেকেন্ডে প্রায় 10^8-টা সাধারণ ধাপ ধরে নাও। তাহলে input-এর সাইজ দেখেই আন্দাজ করা যায় কোন পরিবারের algorithm লাগবে:

| input-এর সাইজ | যে complexity নিরাপদ |
|---------------|----------------------|
| n ≤ 20 | O(2ⁿ) পর্যন্ত চলে |
| n ≤ 500 | O(n³) পর্যন্ত |
| n ≤ 100000 | O(n log n) বা O(n) লাগবে |
| n ≤ 10000000 | প্রায় O(n)-ই একমাত্র পথ |

এজন্যই interviewer বা problem statement-এ "n সর্বোচ্চ কত হতে পারে?" প্রশ্নটা এত গুরুত্বপূর্ণ। উত্তরটা আসলে লক্ষ্য complexity-টাই বলে দিচ্ছে।

## কোড ব্রেকডাউন: মূল experiment-টা লাইনে লাইনে

মূল code-এর জরুরি লাইনগুলো আবার দেখি:

1. `let steps = 0` : আমাদের নিজস্ব কাউন্টার। ঘড়ি নয়, তাই মেশিন বদলালেও এই সংখ্যা বদলায় না।
2. `steps++` লুপের ভেতরে : প্রতিটা তুলনার সাথে কাউন্টার এক বাড়ে। "কতবার কাজের এককটা হলো" সেটাই গোনা হচ্ছে।
3. `if (arr[i] === target) return { index: i, steps }` : পেয়ে গেলে সাথে সাথে থামো। index আর ধাপ-সংখ্যা দুটোই ফেরত যায়, যাতে বাইরে থেকে তুলনা করা যায়।
4. `let lo = 0; let hi = arr.length - 1` : বাইনারি সার্চের জানালা। শুরুতে পুরো array-টাই সন্দেহভাজন।
5. `while (lo <= hi)` : জানালা খালি না হওয়া পর্যন্ত। খালি মানে টার্গেট নেই বলে নিশ্চিত।
6. `const mid = (lo + hi) >> 1` : মাঝের index। `>> 1` মানে ২ দিয়ে ভাগ, ভগ্নাংশ ফেলে দিয়ে।
7. `if (arr[mid] < target) lo = mid + 1` : মাঝেরটা ছোট হলে বাম অর্ধেক পুরো ফেলে দাও, সন্দেহভাজন এক ধাপে অর্ধেক হয়ে গেল।
8. `else hi = mid - 1` : মাঝেরটা বড় হলে ডান অর্ধেক ফেলে দাও।
9. `Array.from({ length: n }, (_, i) => i)` : [0, 1, 2, ..., n-1] বানায়। sorted, তাই বাইনারি সার্চের শর্ত পূরণ হয়।
10. `const target = n` : ইচ্ছে করে এমন সংখ্যা যা তালিকায় নেই। তাই দুই সার্চই সবচেয়ে খারাপ পথ দিয়ে যায়, আমরা worst case মাপছি।
11. `padEnd(10)` : শুধু ছাপা সাজানোর জন্য। algorithm-এর সাথে সম্পর্ক নেই, কিন্তু টেবিল পড়তে সুবিধা হয়।

## Complexity: এই পাতার হিসাবটা নিজে গেঁথে দেখি

**লিনিয়ার সার্চ কেন O(n)?** প্রতিটা উপাদানের সাথে সর্বোচ্চ একবার তুলনা হয়। টার্গেট না থাকলে (বা শেষ ঘরে থাকলে) ঠিক n-বার তুলনা। input দ্বিগুণ করলে ধাপও দ্বিগুণ: এই সমানুপাতিক সম্পর্কটাই O(n)। সেরা ক্ষেত্রে (টার্গেট প্রথম ঘরে) মাত্র ১ ধাপ, কিন্তু সেটা ভাগ্যের ব্যাপার, নকশার নয়। তাই পরিচয় লেখা হয় worst case দিয়ে।

**বাইনারি সার্চ কেন O(log n)?** প্রতি ধাপে সন্দেহভাজন অংশ অর্ধেক হয়। k ধাপ পরে বাকি থাকে n / 2^k-টা। থামার সময় সেটা ১-এ নেমে আসে:

```
n / 2^k = 1   =>   2^k = n   =>   k = log₂(n)
```

অর্থাৎ ধাপ লাগে log₂(n)-এর কাছাকাছি। n দশ লক্ষ হলেও log₂(1000000) ≈ 20, output-এও আমরা 17 ধাপ দেখেছি (n = 100000-এ)। log-এর ভিত্তি (2 নাকি 10) এখানে অগুরুত্বপূর্ণ, কারণ ভিত্তি বদলানো মানে শুধু একটা ধ্রুবক দিয়ে গুণ: log₂(n) = log₁₀(n) × log₂(10)।

**Space?** দুই সার্চই কয়েকটা ভেরিয়েবল ছাড়া কিছু জমায় না, input যত বড়ই হোক। তাই দুটোর বাড়তি মেমরি O(1)। এই "বাড়তি মেমরি কত" প্রশ্নটার পুরো গল্প পরের পাতায়: [Time vs Space](./time-vs-space.mdx)।

ধাপ গোনার পুরো পদ্ধতিটা শেখো [How to Calculate](./how-to-calculate.mdx)-এ, আর সবচেয়ে বেশি দেখা পরিবারগুলোর তালিকা পাবে [Common Runtimes](./common-runtimes.mdx)-এ। বাইনারি সার্চের নিজস্ব পাতাও আছে: [Binary Search](../searching/binary-search.mdx)।

## সাধারণ ভুল আর edge case

**১. ছোট input দেখে সিদ্ধান্ত নেওয়া।**
n = ১০-এ O(n²) আর O(n)-এর ফারক প্রায় টেরই পাওয়া যায় না, দুটোই পলকে শেষ। ফারক ধরা পড়ে n বড় হলে। "আমার মেশিনে তো ঠিকঠাক চলছে" বাক্যটা production-এ কোটি input এলে বিপজ্জনক হয়ে ওঠে। test-এ ছোট input ঠিকই আছে, কিন্তু সিদ্ধান্তের জন্য growth দেখো।

**২. `Date.now()`-কে চোখ বুজে বিশ্বাস করা, বিশেষত ছোট n-এ।**
উপরের variant-টাই দেখলে: একই run-এও সংখ্যা মিলে না। কয়েক মিলিসেকেন্ডের কাজ মাপতে গেলে noise-ই signal খেয়ে ফেলে। আর লুপের ভেতরে `console.log` রেখে timing করলে তো কথাই নেই: ছাপার খরচেই সব ডুবে যায়।

**৩. best case-কে algorithm-এর পরিচয় ভাবা।**
লিনিয়ার সার্চে টার্গেট প্রথম ঘরে থাকলে ১ ধাপেই শেষ। কিন্তু সেটা ভাগ্য, নকশা নয়। পরিচয় লেখা হয় worst case দিয়ে, কারণ ব্যবহারকারী তোমাকে সবচেয়ে খারাপ input-টাই একদিন দেবেই।

**৪. ধ্রুবক নিয়ে দুই চরমে যাওয়া।**
একদল ভাবে Big-O-তে ধ্রুবক নেই মানে ধ্রুবকই নেই: না, দুটো O(n)-এর একটা আরেকটার দশগুণ ধীর হতে পারে। আরেকদল 2n বনাম 3n নিয়ে ঘণ্টার পর ঘণ্টা তর্ক করে, অথচ পরিবার একই। ঠিকানাটা মাঝখানে: আগে পরিবার (growth) ঠিক করো, সমপরিবারের লড়াইয়ে তখন ধ্রুবক দেখো।

**৫. বাইনারি সার্চের লুকানো শর্ত ভুলে যাওয়া।**
বাইনারি সার্চের সব শর্ত একটাই: input sorted হতে হবে। unsorted array-তে চালালে কোনো error দেবে না, চুপচাপ ভুল উত্তর ফেরত দেবে। আর মনে রাখো, একবারই খুঁজতে হলে sort করে (O(n log n)) তারপর বাইনারি চালানো সরাসরি লিনিয়ার (O(n)) থেকে খারাপ; sort-টা তখনই সার্থক যখন বারবার খোঁজা হবে। শূন্য edge case-টাও দেখো: খালি array-তে দুই সার্চই ০ ধাপে "নেই" বলে দেয়, ভাঙে না।

## অনুশীলন

- **সহজ ১:** কাগজে কাগজে হিসাব করো: n = 500000 হলে লিনিয়ার সার্চের worst case-এ কত ধাপ? বাইনারির? হিন্ট: বাইনারির জন্য এমন k খোঁজো যাতে 2^k প্রথমবার n-কে ছাড়িয়ে যায়। (উত্তর: 500000 আর 19।)
- **সহজ ২:** উপরের experiment-এ `sizes`-এ 1000000 যোগ করে চালাও। তারপর `target`-কে 0 করে আবার চালাও। হিন্ট: 0 মানে টার্গেট প্রথম ঘরে, লিনিয়ারের best case; রেসের ছবি পুরো বদলে যাবে, কেন বদলাল ভেবে লেখো।
- **মাঝারি ১:** Two Sum (LeetCode 1) দুইভাবে লিখো: nested loop (প্রতি জোড়া দেখো) আর hash table (দেখা সংখ্যাগুলো মনে রাখো)। দুটোতেই ধাপ-কাউন্টার বসিয়ে বড় input-এ তুলনা করো। হিন্ট: দ্বিতীয় পদ্ধতির আইডিয়াটা [Hash Table Intro](../hash-tables/hash-table-intro.mdx)-তে আছে।
- **মাঝারি ২:** Binary Search (LeetCode 704) নিজে লিখো, প্রতি ধাপে কতটা অংশ বাদ পড়ল সেটাও print করো। হিন্ট: এই পাতার `binarySearch`-টাই প্রায়, শুধু পাওয়ার পরে থামার জায়গাটা আলাদা।
- **কঠিন:** First Bad Version (LeetCode 278): n-টা ভ্যার্সনের মধ্যে এক জায়গা থেকে সব খারাপ; API যত কমবার কল হয় তত ভালো, প্রথম খারাপটা খুঁজবে। হিন্ট: শর্তটা "সমান কিনা" নয়, "খারাপ কিনা": খারাপ পেলে বামে যাও (তুমিই হতে পারো উত্তর, তাই নিজেকে ফেলো না), ভালো পেলে ডানে।

## সারসংক্ষেপ

- সেকেন্ড দিয়ে algorithm মাপা যায় না: মেশিন, লোড আর input বদলালেই সংখ্যা পাল্টায়। যেটা পাল্টায় না, সেটা হলো বৃদ্ধির হার।
- ছোট n-এ n² আর 2ⁿ নির্দোষ দেখায়; কিন্তু n = 100-এ 2ⁿ-এর ধাপ শেষ করতে ব্রহ্মাণ্ডের বয়সের হাজার হাজার গুণ সময় লাগবে।
- ঘড়ির বদলে ধাপ গোনো: counter-টা মেশিন-নিরপেক্ষ, তাই তুলনার আসল ভিত্তি।
- লিনিয়ার সার্চ O(n): input দ্বিগুণ, ধাপ দ্বিগুণ। বাইনারি সার্চ O(log n): দশ লক্ষেও মাত্র ২০ ধাপ, কারণ প্রতি ধাপে অর্ধেক ফেলে দেয়।
- ঘড়ি বেকার নয়, বড় input-এ trend দেখতে কাজে লাগে; কিন্তু algorithm-এর পরিচয় দেয় growth rate।
- এবার সময়ের পাশে দ্বিতীয় খরচটা: [Time vs Space](./time-vs-space.mdx)।
