আগের পাতায় [Big O কী জিনিস](./asymptotic-notation.mdx) আর [হাতে হাতে হিসাব করার নিয়ম](./how-to-calculate.mdx) শিখেছ। এই পাতায় সেই হিসাবটা জেগে উঠবে: সবচেয়ে বেশি দেখা ছয়টা runtime class-কে একই টেবিলে, একই কোডবেসে পাশাপাশি রেখে দেখব কে কত দ্রুত ফুলে ওঠে।

## কী শিখব

- ছয়টা দরকারি runtime class: O(1), O(log n), O(n), O(n log n), O(n^2), O(2^n), ভালো থেকে খারাপ ক্রমে
- n বাড়ার সাথে সাথে প্রতিটার অপারেশন সংখ্যা কীভাবে ফেটে পড়ে, সংখ্যা দিয়ে
- প্রতিটা class-এর একটা করে আসল algorithm: কে কোন class-এ পড়ে আর কেন
- এক সেকেন্ডের বাজেটে কোন class কত বড় n সামলাতে পারে, rule of thumb
- কোডের গঠন (shape) দেখেই runtime আন্দাজ করার quick reference
- O(sqrt n) আর O(n!) ঠিক কোন কোন জায়গায় মাথা তোলে

## ধারণা

ভাবো তো, বাড়িতে দাওয়াত। n জন অতিথি আসবে। এখন কাজটা কোনটা, তার ওপর খরচটা পুরোপুরি নির্ভর করছে:

- দরজায় চাবি টাঙানো আছে, যে আগে আসুক নিয়ে যাবে। অতিথি ১০ জন হোক আর দশ লক্ষ, এই কাজটা **একটাই**। এটা O(1)।
- সাজানো তালিকায় নাম খুঁজে সিট খোঁজা: মাঝখানে উঁকি দিলে অর্ধেক তালিকা ফেলে দিতে পারো, আবার অর্ধেক। দশ লক্ষ নামেও মাত্র কুড়ি উঁকি। এটা O(log n), [binary search](../searching/binary-search.mdx)-এর গতি।
- প্রত্যেক অতিথিকে একটা করে কাপ চা দেওয়া। অতিথি দ্বিগুণ হলে কাজ হুবহু দ্বিগুণ। এটা O(n)।
- সবাইকে বয়সের সাজানো ক্রমে বসানো। বোকার মতো করলে না, চালাকির মতো ভাগ করে মিলিয়ে করলে খরচ n-এর একটু বেশি। এটা O(n log n), ভালো [sorting](../sorting/why-sorting.mdx)-এর গতি।
- প্রত্যেক অতিথি প্রত্যেকের সাথে করমর্দন করছে। ১০ জনে ১০০টা, ১০০ জনে দশ হাজার হ্যান্ডশেক। অতিথি দ্বিগুণ হলে কাজ **চার গুণ**। এটা O(n^2)।
- ফ্রিজে n রকম খাবার, প্রতিটার জন্য "রাখব না রাখব না" দুটো সিদ্ধান্ত। সব সম্ভাব্য মেনু বানাতে গেলে ২ গুণ ২ গুণ ২... n বার। এটা O(2^n)। দশ রকমে হাজারখানেক, কুড়ি রকমে দশ লাখ, তিরিশ রকমে শত কোটি।

খেয়াল করো শেষ দুটোতে: অতিথি বাড়ছে সামান্য, কাজ বাড়ছে বিস্ফোরণের মতো। এই অনুভূতিটাই এই পাতার আসল শিক্ষা। Complexity class মানে শুধু "ধীর না দ্রুত" নয়, মানে **n বড় হলে কে টিকবে আর কে মরে যাবে**।

## ধাপে ধাপে: বৃদ্ধির টেবিল

কথা বাদ, সংখ্যা দেখি। প্রতিটা class ঠিকঠাক মতো কাজ করলে n-এর বিভিন্ন মানে কতটা অপারেশন লাগে:

| রানটাইম | n = 10 | n = 100 | n = 1000 | n = 10^6 |
|---------|--------|---------|----------|----------|
| O(1) | 1 | 1 | 1 | 1 |
| O(log n) | 3 | 7 | 10 | 20 |
| O(n) | 10 | 100 | 1000 | 1000000 |
| O(n log n) | 33 | 664 | 9966 | 19931569 |
| O(n^2) | 100 | 10000 | 1000000 | 1000000000000 |
| O(2^n) | 1024 | প্রায় 10^30 | প্রায় 10^301 | লেখার উপায় নেই |

শেষ সারিটা আবার পড়ো। n = 1000-এ O(2^n) মানে ১-এর পরে ৩০১টা শূন্য। ধরো তোমার মেশিন সেকেন্ডে 10^8 (দশ কোটি) অপারেশন করে:

- O(n^2) দিয়ে n = 10^6 সামলাতে লাগবে 10^12 অপারেশন, মানে প্রায় আড়াই ঘণ্টা।
- O(2^n) দিয়ে n = 100 সামলাতে লাগবে মহাবিশ্বের বয়সের চেয়ে অনেক বেশি সময়।
- অথচ O(n log n) দিয়ে n = 10^6 হচ্ছে মাত্র ০.২ সেকেন্ডে। একই সমস্যা, শুধু algorithm বদলেছ।

টেবিলের প্রতিটা class-এর একটা করে প্রতিনিধি algorithm চিনিয়ে দিই:

- **O(1), constant:** index দিয়ে array access (`arr[0]`), `Map.get()`। input-এর আকারের সাথে কাজের সম্পর্কই নেই।
- **O(log n), logarithmic:** [binary search](../searching/binary-search.mdx)। প্রতি ধাপে খোঁজার জায়গা অর্ধেক ফেলে দেয়, তাই দশ লক্ষে মাত্র ২০ ধাপ।
- **O(n), linear:** একবার পুরো loop, যেমন sum বা max বের করা। প্রতিটা element-কে ঠিক একবার ছোঁয়।
- **O(n log n), linearithmic:** [merge sort](../sorting/merge-sort.mdx)-এর মতো চালাক sort। n-টা কাজ, log n-টা স্তরে।
- **O(n^2), quadratic:** nested loop, সব জোড়া একবার করে। দুটো পুরো loop একটার ভেতর একটা।
- **O(2^n), exponential:** [recursion](../recursion/recursion-intro.mdx) যেখানে প্রতি call থেকে দুইটা call। naive Fibonacci আর subset তৈরির [backtracking](../problem-solving/backtracking.mdx) এই দলে।

## কোড: ছয়টা class, ছয়টা algorithm, আসল পরিমাপ

নিচের প্রোগ্রামটা প্রতিটা class-এর একটা algorithm চালায়, ভেতরে একটা কাউন্টার রাখে, আর প্রিন্ট করে আসলে কতবার কাজ হলো বনাম formula কত বলেছিল। ফাইল বানিয়ে `node runtime-classes.js` দিয়ে চালাতে পারো:

```js
// runtime-classes.js
// ছয়টা runtime class-এর প্রতিনিধি, প্রত্যেকের ভেতরে অপারেশন কাউন্টার

let ops = 0; // গ্লোবাল কাউন্টার; report() প্রতিবার শূন্য করে শুরু করে

// O(1): index দিয়ে সরাসরি access
function constantLookup(arr) {
  ops++;
  return arr[0];
}

// O(log n): sorted array-তে binary search
function binarySearch(arr, target) {
  let lo = 0;
  let hi = arr.length - 1;
  while (lo <= hi) {
    ops++; // প্রতি ধাপে একটা তুলনা, আর বাকি অর্ধেক ফেলে দেওয়া
    const mid = (lo + hi) >> 1;
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

// O(n): পুরো array একবার ঘুরে sum
function linearSum(arr) {
  let total = 0;
  for (const x of arr) {
    ops++;
    total += x;
  }
  return total;
}

// O(n log n): merge sort (অর্ধেক ভাগ, মিলিয়ে সাজানো)
function mergeSort(arr) {
  if (arr.length <= 1) return arr;
  const mid = arr.length >> 1;
  const left = mergeSort(arr.slice(0, mid));
  const right = mergeSort(arr.slice(mid));
  const merged = [];
  let i = 0;
  let j = 0;
  while (i < left.length && j < right.length) {
    ops++; // দুই পাশের সামনেরটা তুলনা
    merged.push(left[i] <= right[j] ? left[i++] : right[j++]);
  }
  return merged.concat(left.slice(i), right.slice(j));
}

// O(n^2): সব জোড়া একবার করে দেখা
function pairLoops(arr) {
  let small = 0;
  for (const a of arr) {
    for (const b of arr) {
      ops++;
      if (a < b) small++;
    }
  }
  return small;
}

// O(2^n): naive Fibonacci
// সতর্কতা: n একটা বাড়ালেই call সংখ্যা প্রায় দ্বিগুণ। তাই ডেমো n <= 20-এ রাখা;
// n = 50 দিলে এই ল্যাপটপও ঘণ্টার পর ঘণ্টা ব্যস্ত থাকত।
function fib(n) {
  ops++; // একটা recursive call
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}

function report(label, n, run, formula) {
  ops = 0;
  run();
  const row = label.padEnd(10)
    + " n=" + String(n).padEnd(8)
    + " measured=" + String(ops).padEnd(12)
    + " formula~ " + Math.round(formula);
  console.log(row);
}

// সস্তা class-গুলো বড় n পর্যন্ত চালানো যায়
for (const n of [10, 100, 1000, 1000000]) {
  const arr = Array.from({ length: n }, (_, i) => i + 1); // [1..n], sorted
  report("O(1)", n, () => constantLookup(arr), 1);
  report("O(log n)", n, () => binarySearch(arr, -1), Math.log2(n)); // -1 নেই: worst case
  report("O(n)", n, () => linearSum(arr), n);
  report("O(n log n)", n, () => mergeSort([...arr].reverse()), n * Math.log2(n));
}

// O(n^2) দশ লক্ষে চালালে 10^12 অপারেশন, বসে থাকতে হবে; তাই ছোট n
for (const n of [10, 100, 1000, 10000]) {
  const arr = Array.from({ length: n }, (_, i) => i + 1);
  report("O(n^2)", n, () => pairLoops(arr), n * n);
}

// O(2^n) একেবারে ছোট n-এ: fib-এর call গুনি
for (const n of [5, 10, 15, 20]) {
  report("O(2^n)", n, () => fib(n), Math.pow(2, n));
}
```

চালালে এমন output আসবে (কয়েকটা সারি দেখাচ্ছি):

```text
O(log n)   n=1000000  measured=19           formula~ 20
O(n)       n=1000000  measured=1000000      formula~ 1000000
O(n log n) n=1000000  measured=10066432     formula~ 19931569
O(n^2)     n=10000    measured=100000000    formula~ 100000000
O(2^n)     n=20       measured=21891        formula~ 1048576
```

দুটো জায়গায় measured আর formula মিলছে না হুবহু, আর সেটাই শেখার জিনিস:

- merge sort-এ measured অর্ধেকের কাছাকাছি, কারণ merge করতে গিয়ে এক পাশ শেষ হয়ে গেলে বাকি পাশ আর তুলনা ছাড়াই কপি হয়। n log n হলো upper bound, আসল কাজ তার কম।
- fib-এ measured অনেক কম, কারণ recursion tree-টা পূর্ণ binary নয় (এক ডিকে n-1, আরেক ডিকে n-2, দুই দিক সমান গভীর নয়)। 2^n হলো নিরাপদ upper bound। গুরুত্বপূর্ণ ব্যাপার হলো n: 15 থেকে 20-তে measured 1973 থেকে 21891, মানে ৫ বাড়াতেই এগারো গুণ। exponential-এর সেই চরিত্রটা অক্ষুণ্ণ আছে।

## ভ্যারিয়েন্ট

### ভ্যারিয়েন্ট ১: কত বড় n সামলাতে পারবা?

প্র্যাকটিক্যাল নিয়ম: ধরো মেশিন সেকেন্ডে 10^8-এর কাছাকাছি সহজ অপারেশন করে, আর তোমার হাতে ১ সেকেন্ড। তাহলে:

| রানটাইম | ১ সেকেন্ডে সামলানো যায় (মোটামুটি) |
|---------|-----------------------------------|
| O(log n) | প্রায় যেকোনো n |
| O(n) | 10^8 পর্যন্ত |
| O(n log n) | 10^6 থেকে 10^7 পর্যন্ত |
| O(n^2) | প্রায় 10^4 পর্যন্ত |
| O(2^n) | প্রায় 25 পর্যন্ত |
| O(n!) | প্রায় 11 পর্যন্ত |

এই টেবিলটা competitive programming-এ অর্ধেক সমস্যা সমাধান করে দেয়। Constraint দেখো: n = 10^5 লেখা থাকলে O(n^2) দিয়ে গেলে TLE খাবেই, লাগবে O(n) বা O(n log n)। আবার n = 20 দেখলে বুঝবে [backtracking](../problem-solving/backtracking.mdx)-এর O(2^n)-ই আশা করা হচ্ছে।

### ভ্যারিয়েন্ট ২: কোডের গঠন দেখে runtime চেনা

ইন্টারভিউতে বা নিজের কোড রিভিউতে এই ছোট ম্যাপটা প্রায় প্রতিদিন কাজে লাগে:

| কোডের গঠন | সম্ভাব্য runtime |
|-----------|------------------|
| index access, Map.get, push/pop | O(1) |
| প্রতি ধাপে range অর্ধেক ফেলে দেওয়া | O(log n) |
| একটা loop, শুরু থেকে শেষ | O(n) |
| অর্ধেক করে ভাগ, প্রতি স্তরে পুরো array ছোঁয়া | O(n log n) |
| loop-এর ভেতরে loop, দুটোই n পর্যন্ত | O(n^2) |
| প্রতি recursive call থেকে দুইটা call | O(2^n) |
| সব permutation বানানো | O(n!) |

একটা সাবধানবাণী: nested loop দেখেই O(n^2) ধরে নিও না। ভেতরের pointer যদি প্রতিবার শুরু থেকে না এসে একদিকে এগোতেই থাকে ([two pointer](../problem-solving/two-pointer.mdx) কৌশল), দুটো loop মিলেও মোট কাজ O(n)। গঠন দেখো, কিন্তু আসলে কতবার কাজ হচ্ছে সেটাও গোনো।

### ভ্যারিয়েন্ট ৩: O(sqrt n) আর O(n!) কোথায়?

দুটো class উপরের বড় তালিকায় নেই, কিন্তু জানা জরুরি:

- **O(sqrt n):** সংখ্যা prime কিনা দেখতে n পর্যন্ত সব divisor চেক করার দরকার নেই। divisor জোড়ায় জোড়ায় আসে (২৪ = ৩×৮ হলে ৮ = ২৪/৩), তাই sqrt(n) পর্যন্ত চেক করলেই উত্তর পেয়ে যাও। n = 10^12-এর জন্য 10^12-টা চেকের বদলে মাত্র 10^6-টা। sqrt decomposition নামের কৌশলেও এই গতি আসে।
- **O(n!):** সব সম্ভাব্য বিন্যাস (permutation) ঘেঁটে দেখা। n শহরের traveling salesman brute force-এ n! পথ। 10! মানে ৩৬ লাখ, 15! মানে ১.৩ লাখ কোটি। তাই ১১-১২টা জিনিসের বেশি হলে এই রাস্তা বন্ধ, সেখানে লাগবে dynamic programming বা heuristic।

## কোড ব্রেকডাউন

মূল প্রোগ্রামের গুরুত্বপূর্ণ লাইনগুলো, কোনটা কেন:

1. `let ops = 0` : একটা গ্লোবাল কাউন্টার। প্রতিটা algorithm নিজের "এক ইউনিট কাজ" হলে এটা বাড়ায়। measured কলাম পুরোটাই এর থেকে আসে।
2. `constantLookup`-এ `ops++` একবার, যাই নিয়ে আসুক। return-ও সরাসরি। n-এর নাম-গন্ধ এখানে নেই, এটাই O(1)-এর সংজ্ঞা।
3. `binarySearch`-এ `while (lo <= hi)` : প্রতিবার mid দেখে এক পাশ ফেলে দেওয়া হচ্ছে, মানে খোঁজার জায়গা অর্ধেক। `ops++` while-এর একেবারে উপরে, প্রতি ধাপে একবার।
4. `(lo + hi) >> 1` : bit-shift দিয়ে integer division, মাঝের index। `Math.floor((lo + hi) / 2)` লিখলেও চলে।
5. `binarySearch(arr, -1)` : ইচ্ছে করে এমন target দেওয়া যেটা array-তে নেই। তাহলে কখনো আগে return করতে পারে না, পুরো log n ধাপ চলতে বাধ্য হয়। এটাই worst case পরিমাপ।
6. `linearSum`-এ loop n বার চলে, প্রতিবার একটা `ops++`। measured হুবহু n, এটাই formula-র সাথে সবচেয়ে নিখুঁত মিল।
7. `mergeSort` নিজেকে দুইবার ডাকে, অর্ধেক ভাগ করে। ভাগ হয় log n স্তর গভীর, আর প্রতি স্তরে merge-এর তুলনাগুলো মিলে n-এর কাছাকাছি। তুলনাটাই `ops++`।
8. `[...arr].reverse()` : sort-এর জন্য উল্টো ক্রমের input দিলাম, যাতে merge-এ সত্যিকারের কাজ হয় (sorted input দিলে মজাটা কমে যায়)।
9. `pairLoops`-এ ভেতরের loop বাইরের প্রতি ধাপে পুরো n বার। মোট n × n, তাই measured হুবহু n^2 মেলে।
10. `fib(n)`-এ `ops++` মানে একটা recursive call। call-ই এখানে আসল খরচ, তাই সেটাই গোনা হচ্ছে।
11. `report()` : প্রতি রানের আগে `ops = 0` রিসেট করে, তারপর চালায়, তারপর measured আর `Math.round(formula)` পাশাপাশি প্রিন্ট করে। `padEnd` শুধু কলাম সাজানোর জন্য।
12. তিনটা আলাদা size তালিকা কেন? সস্তা চারটা class 10^6 পর্যন্ত চলে, কিন্তু O(n^2) সেখানে 10^12 অপারেশন চাইত আর O(2^n) কালেভদ্রে শেষ হত না। নিজের কম্পিউটারেই টেবিলের ভয়াবহতা প্রমাণ হয়ে গেল: দামি দুটোকেই ছোট n-এ আটকে রাখতে হলো।

## Complexity: প্রতিটা class-এর হিসাব হাতে

প্রতিটা algorithm তার class-এ পড়ে কেন, একবার করে derive করি। নিয়মগুলো [how-to-calculate](./how-to-calculate.mdx) পাতারই:

- **constantLookup, O(1):** একটা array access। n দশ হোক বা দশ লক্ষ, লাইন একটাই, কাজ একটাই। n-এর ফাংশন নয়, তাই constant।
- **binarySearch, O(log n):** প্রতি ধাপে জায়গা অর্ধেক। k ধাপে ১-টা element থাকে, মানে n / 2^k = 1, সমাধানে k = log2(n)। n = 10^6 হলে k = 20, টেবিলের সাথে মিলে গেছে।
- **linearSum, O(n):** n-টা element, প্রত্যেকটায় ঠিক একবার, প্রতিবার constant কাজ। মোট n × O(1) = O(n)।
- **mergeSort, O(n log n):** দুইটা গুণ। ভাগের গভীরতা: প্রতিবার অর্ধেক, তাই log2(n)-টা স্তর। প্রতি স্তরে সব merge মিলে n-টা element ছোঁয়। স্তর × স্তরপ্রতি কাজ = n log n।
- **pairLoops, O(n^2):** বাইরের loop n বার, ভেতরেরটা প্রতিবার n বার। n × n = n^2। এমনকি ভেতরেরটা অর্ধেক চললেও (j = i থেকে শুরু) কাজ n^2 / 2, আর Big O-তে constant গুণক বাদ পড়ে, থাকে O(n^2)।
- **fib, O(2^n):** T(n) = T(n-1) + T(n-2) + O(1)। ছোট করে ধরো T(n) > 2 × T(n-2), মানে দুই ধাপে দ্বিগুণ। তাহলে T(n) > 2^(n/2), নিচ থেকে exponential। উপর থেকে T(n) < 2^n। সঠিক গোনায় fib(n)-এর মোট call হলো 2 × F(n+1) - 1, যেখানে F হলো Fibonacci সংখ্যা নিজেই। ক্লাস? O(2^n), কোনো সন্দেহ নেই। (এই একই ফাংশন [memoization](../recursion/memoization.mdx) দিলে নেমে আসে O(n)-এ, সেই গল্প recursion section-এ।)

Space-এর খবর এক লাইনে: `constantLookup`, `binarySearch`, `linearSum`, `pairLoops` O(1) অতিরিক্ত জায়গা নেয়, `mergeSort` মোট O(n) অতিরিক্ত array বানায়, আর `fib` recursion stack-এ সর্বোচ্চ O(n) গভীর যায়। এই খরচের পুরো তত্ত্ব [time vs space](./time-vs-space.mdx) পাতায়।

## সাধারণ ভুল আর edge case

**১. ছোট input-এ টেস্ট করে ধীর algorithm-কে "যথেষ্ট দ্রুত" ভেবে বসা।**
n = 100-এ O(n^2) মাত্র 10^4 অপারেশন, চোখের পলকে শেষ। ডেমোতে সব ঠিকঠাক, প্রোডাকশনে n = 10^6 ঢুকতেই আড়াই ঘণ্টার লোড। নিয়ম: সবসময় আসল বা সম্ভাব্য সবচেয়ে বড় n দিয়ে ভাবো, ভ্যারিয়েন্ট ১-এর টেবিল দিয়ে।

**২. built-in মেথডের লুকানো খরচ ভুলে যাওয়া।**
`arr.sort()` ডাকলেই তুমি O(n log n) খরচ করেছ, loop-এর ভেতরে ডাকলে O(n^2 log n)। `shift()`, `slice()`, string concatenation loop-এ, `includes()` array-তে, সব O(n) কাজ। নিঃশব্দে nested হয়ে গেলে মোট বিল O(n^2)। [যেকোনো কোডে complexity গুনতে গিয়ে](./how-to-calculate.mdx) এই লুকানো লাইনগুলোই সবচেয়ে বেশি ফাঁকি দেয়।

**৩. "অর্ধেক কাজ হলো, তাহলে complexity অর্ধেক" ভাবা।**
`for i`, তার ভেতরে `for j` শুরু `i` থেকে: মোট কাজ n(n-1)/2, মানে প্রায় অর্ধেক। কিন্তু Big O-তে ½ গুণক বাদ, থাকে O(n^2)। Big O মাপে বৃদ্ধির হার, সেকেন্ড বা ঘড়ির সময় নয়। হার কমাতে চাইলে গঠন বদলাতে হবে, অর্ধেক loop না।

**৪. O(log n)-এর base নিয়ে মাথা ঘামানো।**
log2(n) আর log10(n)-এর পার্থক্য শুধু একটা constant গুণক (log2(n) = log10(n) × log2(10))। Big O-তে গুণক বাদ পড়ে, তাই দুটোই O(log n)। base ২ হবে যখন প্রতিবার অর্ধেক ফেলো; তিন ভাগ করলে base ৩, কিন্তু class একই।

**৫. খালি আর একটা element-এর edge case চেক না করা।**
`binarySearch([], x)` ঠিকই -1 দেয় কিন্তু `arr[0]`-টাইপ কোড খালি array-তে `undefined` ফেরত দেয় নিঃশব্দে। `fib(0)` আর `fib(1)` base case না থাকলে recursion থামতই না। প্রতিটা algorithm লিখেই n = 0 আর n = 1 দিয়ে একবার মাথায় চালাও।

## অনুশীলন

- **সহজ ১:** পাঁচটা ছোট কোড খণ্ড লেখো (একটা loop, nested loop, অর্ধেক-ফেলা loop, sort + loop, দুই-ডাক-ওয়ালা recursion) আর বন্ধুকে বা নিজেকে class বলতে দাও। হিন্ট: আগে খোঁজো range কি প্রতিবার অর্ধেক হচ্ছে, তারপর nested loop, তারপর recursion-এর ডাক গোনো।
- **সহজ ২:** Contains Duplicate (LeetCode 217)। দুইবার solve করো: একবার sort করে পাশাপাশি মিলিয়ে (O(n log n)), একবার Set দিয়ে (O(n))। হিন্ট: Set-এ add আর has দুটোই O(1), তাই পুরো loop মিলে O(n)।
- **মাঝারি ১:** Two Sum (LeetCode 1)। আগে brute force লেখো (দুইটা nested loop, O(n^2)), তারপর Map দিয়ে এক পাসে নামাও (O(n))। হিন্ট: প্রতি সংখ্যা x-এর জন্য জিজ্ঞেস করো target - x আগে দেখেছ কিনা।
- **মাঝারি ২:** Maximum Subarray (LeetCode 53)। তিন স্তরে লেখো: সব subarray (O(n^3)), তারপর শুরুর index ঠিক রেখে (O(n^2)), তারপর Kadane's algorithm (O(n))। হিন্ট: প্রতি ঘরে শুধু দুটো জিনিস ট্র্যাক করো, "এখানে শেষ হওয়া সেরা sum" আর "এখন পর্যন্ত সেরা"।
- **কঠিন:** Subsets (LeetCode 78)। n-টা element-এর সব subset বানাও। ভেবে দেখো এটা কমানো যায় কিনা। হিন্ট: output-এই 2^n-টা জিনিস আছে, তাই O(2^n) এখানে দুর্বলতা নয়, সমস্যার প্রকৃতি। প্রতি element-এ দুইটা branch: নেব, নেব না।

## সারসংক্ষেপ

- ছয়টা class মুখস্থ নয়, ক্রমটা মুখস্থ: O(1) < O(log n) < O(n) < O(n log n) < O(n^2) < O(2^n) < O(n!)।
- n = 10^6 হলে O(n log n) ০.২ সেকেন্ড, O(n^2) আড়াই ঘণ্টা, O(2^n) মহাবিশ্বের বয়স। পার্থক্য সময়ের নয়, টিকে থাকার।
- ১ সেকেন্ডের বাজেটে: O(n) সামলায় 10^8, O(n log n) সামলায় 10^6-10^7, O(n^2) মাত্র 10^4, O(2^n) মাত্র ২৫।
- কোডের গঠনই সন্ধানদাতা: অর্ধেক ফেলা মানে log n, nested loop মানে n^2, দুই-ডাক recursion মানে 2^n। তবে গঠন দেখার পর আসল কাজও গুণে নিশ্চিত হও।
- measured আর formula পুরোপুরি মিলবে না সবসময়, constant আর বাদ পড়া কাজের কারণে। Big O upper bound, আর সেটাই দরকার।
- পরের ধাপ: প্রতিটা class-এর প্রতিনিধিদের গভীরে, [binary search](../searching/binary-search.mdx) আর [merge sort](../sorting/merge-sort.mdx) দিয়ে শুরু করো।
