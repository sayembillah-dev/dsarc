কোড দেখে ১০ সেকেন্ডে Big-O বলে দেওয়ার দক্ষতাটাই এই পাতার লক্ষ্য।

## কী শিখব

- কোনো কোড দেখে ধাপে ধাপে step count T(n) দাঁড় করানো
- হিসাবের পাঁচটা নিয়ম: dominant loop, যোগ, গুণ, অর্ধেক মানে log, ধ্রুবক বাদ
- counter বসিয়ে measured count আর predicted formula মিলিয়ে যাচাই করা
- তিনটা ভ্যারিয়েন্টের স্বাদ: recursion-এর recurrence, amortized হিসাব, best/average/worst case
- সবচেয়ে বেশি হওয়া পাঁচটা ভুল কী আর কেন

## ধারণা

ভাবো তো, বিয়ে বাড়ির দাওয়াতে তুমি খাবারের প্যাকেট বিলাচ্ছো। প্রতি অতিথিকে একটা করে প্যাকেট দিলে কাজটা অতিথির সংখ্যার সমানুপাতিক: অতিথি দ্বিগুণ, কাজ দ্বিগুণ। কিন্তু যদি প্রতি অতিথিকে বাকি সবার সাথে একবার করে হাত মেলাতে বলো? অতিথি দ্বিগুণ হলে হাতমেলানো হবে চারগুণ। আর বিশাল ফোনবুক থেকে নাম খুঁজতে গেলে তুমি প্রতিবার অর্ধেক পাতা ফেলে দাও: পাতা দ্বিগুণ হলেও খোঁজা বাড়ে মাত্র এক ধাপ।

তিনটা ঘটনাতেই প্রশ্ন একটাই: ইনপুট বাড়লে কাজ কীভাবে বাড়ে? কেন এই প্রশ্নটা গুরুত্বপূর্ণ, সেটা [কেন Complexity দরকার](./why-complexity.mdx)-এ দেখে এসেছ। এই পাতায় শিখব উত্তরটা বের করার কায়দা: কোড দেখে ছক্কর না মেরে, নিয়ম ধরে Big-O বলে দেওয়া।

নিয়ম পাঁচটা। ক্রমটা মাথায় রাখো:

1. **Dominant loop-টা গোনো।** পুরো ফাংশনে যে লুপটা সবচেয়ে বেশি কাজ করায়, হিসাব ওকে ঘিরেই।
2. **পাশাপাশি ব্লক যোগ হয়, তারপর বড়টা টিকে।** একটার পর একটা দুটো O(n) লুপ থাকলে মোট O(n + n) = O(n)।
3. **Nested loop গুণ হয়।** বাইরেরটা n বার, প্রতিবার ভেতরেরটা n বার, মোট n × n।
4. **প্রতিবার অর্ধেক (বা দ্বিগুণ) মানে log n।** n থেকে 1-এ নামতে log₂ n ধাপ লাগে।
5. **ধ্রুবক আর ছোট term ফেলে দাও।** O(2n) মানে O(n); n² + n + 5 মানে O(n²)।

এই পাঁচটা দিয়েই বাস্তবের প্রায় সব হিসাব হয়ে যায়। চলো, একটা ফাংশনের ওপর পুরো প্রক্রিয়াটা চালিয়ে দেখি।

## ধাপে ধাপে: T(n) দাঁড় করানো

এই ফাংশনটা ধরো। একটার মধ্যেই আছে সাধারণ লুপ, nested লুপ, আর অর্ধেক লুপ:

```js
function mystery(n) {
  let s = 0;                          // অংশ A
  for (let i = 0; i < n; i++) {       // অংশ B
    s += i;
  }
  for (let a = 0; a < n; a++) {       // অংশ C (বাইরে)
    for (let b = 0; b < n; b++) {     // অংশ D (ভেতরে)
      s += a * b;
    }
  }
  while (n > 1) {                     // অংশ E
    n = Math.floor(n / 2);
  }
  return s;                           // অংশ F
}
```

প্রতি অংশ কতবার চলে, সেটা গুনে T(n) বানাই:

| ধাপ | অংশ | কতবার চলে | T(n)-এ যোগ |
|-----|------|-----------|------------|
| 1 | A: `let s = 0` | 1 | 1 |
| 2 | B: একটা লুপ | n | + n |
| 3 | D: nested লুপের ভেতরের কাজ | n × n | + n² |
| 4 | E: প্রতিবার অর্ধেক | log₂ n | + log₂ n |
| 5 | F: `return` | 1 | + 1 |
| | **মোট** | | **T(n) = n² + n + log₂ n + 2** |

ধাপ ৩-টা একটু থামিয়ে দেখো। C লুপটা n বার ঘোরে, আর C-এর প্রতি ঘুরেপে D-এর ভেতরের কাজটা পুরো n বার চলে। মোট n-টা দলা, প্রতি দলায় n-টা, অর্থাৎ n × n। এটাই নিয়ম ৩-এর গুণ।

এবার T(n) সরল করো, এক ধাপে একটা term বাদ:

1. T(n) = n² + n + log₂ n + 2
2. log₂ n আর 2 বাদ: n²-এর পাশে ওরা ধুলো (n = 1024-এ n² = 1048576, অথচ log₂ n মাত্র 10)
3. বাকি n² + n; এবার n-ও বাদ: n = 1024-এ n হলো n²-এর মাত্র 0.1%
4. থাকে n², সামনে কোনো ধ্রুবক নেই

উত্তর: **O(n²)**। খেয়াল করো, নিয়ম ২ (যোগ) আর নিয়ম ৫ (বাদ দেওয়া) দুটোই কাজ করল; আর n²-টা এসেছিল নিয়ম ৩ (গুণ) দিয়ে।

পুরো প্রক্রিয়ায় এক লাইন গুরুত্বপূর্ণ: আমরা প্রতিটা statement আলাদা আলাদা গুনিনি। গুনতেই হবে, এমন কোনো নিয়ম নেই: dominant অংশটা ঠিকঠাক ধরলেই উত্তর ঠিক আসে। এটা অলসতা নয়, এটাই পদ্ধতি।

## কোড: গোনা বনাম prediction

কথায় কথায় বিশ্বাস না করে গুনে দেখি। চারটা ছোট ফাংশনে counter বসিয়ে দিলাম; প্রতিটার পাশে আমাদের predicted formula। n = 8, 64, 1024-এ চালিয়ে দেখো দুটো মিলে কিনা:

```js
// প্রতিটা ফাংশনে শুধু counter বসানো; আসল কাজ একটা করে চিহ্নিত statement
function sumLoop(n) {
  let ops = 0;
  let sum = 0;
  for (let i = 0; i < n; i++) {
    sum += i;              // প্রতি iteration-এ একবার
    ops++;
  }
  return { sum, ops };
}

function pairPrint(n) {
  let ops = 0;
  let last = -1;
  for (let a = 0; a < n; a++) {
    for (let b = 0; b < n; b++) {
      last = a * n + b;    // ভেতরের কাজ: মোট n × n বার
      ops++;
    }
  }
  return { last, ops };
}

function halvingCounter(n) {
  let ops = 0;
  while (n > 1) {
    n = Math.floor(n / 2); // প্রতিবার অর্ধেক
    ops++;
  }
  return { end: n, ops };
}

function doublingCounter(n) {
  let ops = 0;
  let i;
  for (i = 1; i < n; i *= 2) { // উল্টো দিক: প্রতিবার দ্বিগুণ
    ops++;
  }
  return { stoppedAt: i, ops };
}

const pad = (s, w) => String(s).padEnd(w);
console.log(pad("n", 6) + pad("sumLoop ~ n", 18) + pad("pairPrint ~ n^2", 20)
  + pad("halving ~ log2 n", 20) + "doubling ~ log2 n");

for (const n of [8, 64, 1024]) {
  const a = sumLoop(n).ops,        pa = n;             // prediction: n
  const b = pairPrint(n).ops,      pb = n * n;         // prediction: n^2
  const c = halvingCounter(n).ops, pc = Math.log2(n);  // prediction: log2 n
  const d = doublingCounter(n).ops, pd = Math.log2(n); // prediction: log2 n
  const row = (m, p) => m + "/" + p + (m === p ? " মিলল" : " মিলেনি!");
  console.log(
    pad(n, 6) + pad(row(a, pa), 18) + pad(row(b, pb), 20)
    + pad(row(c, pc), 20) + row(d, pd)
  );
}
```

চালালে দেখবে প্রতি সারিতে measured আর predicted হুবহু মিলছে: 8/8, 64/64, 3/3, আর n = 1024-এ pairPrint-এর 1048576/1048576 পর্যন্ত।

আরেকটা জিনিস চোখে পড়ল? n কে 8 থেকে 64 করলে (আটগুণ) sumLoop-এর count-ও আটগুণ, pairPrint-এর চৌষট্টিগুণ, আর halving-এর মাত্র দ্বিগুণ। এটাই আসল স্বাক্ষর: **n দ্বিগুণ করে count কতগুণ হলো দেখলেই growth চেনা যায়**, কোড না পড়েও। লিনিয়ার হলে দ্বিগুণ, কোয়াড্রাটিক হলে চারগুণ, log হলে এক ধাপ বাড়ে।

n-গুলো ইচ্ছে করে 2-এর power নেওয়া, যাতে log₂ হিসাব কাটাকুটি ছাড়া মিলে যায়। মাঝখানের সংখ্যা নিলে halving-এর count হবে floor(log₂ n), prediction-ও তখন সেভাবেই করতে হবে।

## ভ্যারিয়েন্ট ১: recursion মানে recurrence

Loop না থেকে recursion থাকলে লুপ গোনা যায় না; তখন হিসাবটা একটা সমীকরণে দাঁড়ায়। [Binary Search](../searching/binary-search.mdx) ধরো: প্রতি ধাপে সমস্যা অর্ধেক, সাথে একটা তুলনা:

```
T(n) = T(n/2) + 1
     = T(n/4) + 2
     = T(n/8) + 3
     = ...
     = T(1) + log₂ n
```

মানে T(n) = log₂ n + ধ্রুবক, অর্থাৎ O(log n)। এই ধরনের সমীকরণকে বলে **recurrence**। খোলার কৌশল সহজ: বারবার ভেতরের T-এর জায়গায় তার নিজের সূত্র বসিয়ে যাও, প্যাটার্ন নিজেই বেরিয়ে আসবে। Recursion-এর বেসিক মনে করতে হলে [Recursion Intro](../recursion/recursion-intro.mdx) দেখে এসো।

## ভ্যারিয়েন্ট ২: amortized হিসাব (এক চিলতে)

কিছু অপারেশন মাঝে মাঝে দামি, বাকি সময় সস্তা; তখন প্রতি অপারেশনের **গড়** খরচকে বলে amortized। JavaScript array-তে push ধরো: ভেতরের capacity ভরে গেলে দ্বিগুণ জায়গা নিয়ে সব copy হয়:

| কততম push | নতুন capacity | ওই ধাপে copy |
|-----------|---------------|--------------|
| 1 | 1 | 0 |
| 2 | 2 | 1 |
| 3 | 4 | 2 |
| 4 | 4 | 0 |
| 5 | 8 | 4 |
| 6, 7, 8 | 8 | 0 |
| 9 | 16 | 8 |

8-টা push-এ মোট copy = 1 + 2 + 4 = 7, অর্থাৎ n-এর কম। তাই n-টা push-এর মোট খরচ O(n), ভাগ করে দিলে প্রতি push = **O(1) amortized**। কোনো একটা push মাঝে মাঝে O(n) খরচ করলেও বিলটা সবার ঘাড়ে ভাগ করে দিলে সবাই সস্তা। Array-এর ভেতরের এই গল্প [Array Operations](../arrays-strings/array-operations.mdx)-এ আছে।

## ভ্যারিয়েন্ট ৩: best, average, worst

একই কোডের হিসাব ইনপুট ভেদে বদলায়। [Linear Search](../searching/linear-search.mdx) ধরো:

```js
function linearSearch(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i; // পেলেই থাম: early exit
  }
  return -1;
}
```

- **Best case:** target প্রথম ঘরে, 1-টা তুলনা।
- **Average case:** target array-তে আছে আর যেকোনো জায়গায় সমান সম্ভাবনা, গড়ে (1 + 2 + ... + n) / n = (n + 1) / 2-টা তুলনা।
- **Worst case:** target নেই বা শেষ ঘরে, পুরো n-টা তুলনা।

রিপোর্ট করার সময় আমরা worst case-টাই বলি: O(n)। গড়ের (n + 1) / 2-ও আসলে একই হারে বাড়ে, কিন্তু "গড়ে ভালো" এই ভরসায় সিস্টেম বানানো যায় না। কোনটা upper bound, কোনটা tight, এই ভাষাগুলো পরের পাতা [Asymptotic Notation](./asymptotic-notation.mdx)-এ পরিষ্কার হবে।

## কোড ব্রেকডাউন: counter যন্ত্রটা

1. প্রতিটা ফাংশনে `ops` নামে counter রাখা; আমরা ফলাফল নয়, **কতবার** dominant কাজ হলো সেটা গুনছি।
2. `sumLoop`-এ লুপের body প্রতি iteration-এ একবার, লুপ n বার, তাই ops = n।
3. `pairPrint`-এ ভেতরের লুপ বাইরের প্রতি iteration-এ পুরো n বার ঘোরে: n-টা দলা, প্রতি দলায় n-টা, মোট n × n।
4. `halvingCounter`-এ শর্ত `n > 1`; প্রতি ধাপে n অর্ধেক, তাই log₂ n ধাপে 1-এ নেমে থামে।
5. `doublingCounter` তার উল্টো দিক: i এক থেকে দ্বিগুণ হতে হতে n ছাড়িয়ে যায়; একই log₂ n ধাপ। দিক যেদিকেই হোক, দ্বিগুণ-অর্ধেক মানে log।
6. হারনেসে n = 8, 64, 1024: তিনটাই 2-এর power, ফলে `Math.log2(n)` ঠিকঠাক পূর্ণসংখ্যা আসে আর মিলটা পরিষ্কার দেখা যায়।
7. প্রতি সারিতে `measured/predicted` পাশাপাশি; `row()` ফাংশন দুটো সমান হলে "মিলল" লিখে দেয়।
8. এই যন্ত্র শেখার জন্য; বাস্তব কোডে কখনো counter লেখা হয় না, মাথায় মাথায় নিয়ম পাঁচটাই চলে।

## Complexity

পাতার নিজের উদাহরণগুলোর হিসাব এক নজরে:

- **sumLoop:** T(n) = n, অর্থাৎ O(n)।
- **pairPrint:** T(n) = n², অর্থাৎ O(n²)।
- **halvingCounter:** n, n/2, n/4, ... k ধাপে 1-এ পৌঁছায়, যেখানে 2^k ≈ n, তাই k = log₂ n, অর্থাৎ O(log n)।
- **doublingCounter:** একই হিসাব উল্টো দিকে, O(log n)।
- **mystery:** T(n) = n² + n + log₂ n + 2, dominant term n², অর্থাৎ O(n²)।

Space-এর দিকটা বাদ পড়ল না: চারটা ফাংশনই মাত্র কয়েকটা variable ব্যবহার করে, input যত বড়ই হোক extra জায়গা লাগে না, তাই সবার space O(1)। Time আর space-এর এই দুই রকম হিসাবের পার্থক্য নিয়ে [Time vs Space](./time-vs-space.mdx)-এ আলাদা কথা আছে। আর এই runtime-গুলোর পুরো ম্যাপ, কোনটা কার চেয়ে দ্রুত বাড়ে, [Common Runtimes](./common-runtimes.mdx)-এ পাবে।

## সাধারণ ভুল আর edge case

**১. Nested লুপকে যোগ করে ফেলা।**
দুটো O(n) লুপ **পাশাপাশি** থাকলে n + n, কিন্তু **ভেতরে** থাকলে n × n। `pairPrint`-কে O(2n) বললে n = 1024-এ তুমি 2048 আশা করবে, হবে 1048576। পার্থক্য মারাত্মক।

**২. প্রতিটা statement নিখুঁত গুনতে গিয়ে আটকে যাওয়া।**
T(n) = 3n + 2 নাকি 4n + 1, এই লড়াইয়ের কোনো মূল্য নেই: দুটোই O(n)। Exact count নয়, dominant term-ই লক্ষ্য। যতটুকু গুনলে ছবিটা পরিষ্কার হয়, ততটুকুই যথেষ্ট।

**৩. log-এর base নিয়ে মাথা ঘামানো।**
log₂ n আর log₁₀ n-এর পার্থক্য একটা ধ্রুবক গুণক মাত্র (log₁₀ n = log₂ n / log₂ 10)। Big-O ধ্রুবক গিলে ফেলে, তাই base যাই হোক উত্তর O(log n)-ই। `i *= 3` হলেও তাই।

**৪. Average-এর হিসাব দিয়ে worst case-এর জায়গা পূরণ করা।**
Linear search-এ গড়ে (n + 1) / 2-টা তুলনা লাগে ঠিকই, কিন্তু রিপোর্ট হয় worst case: O(n)। "গড়পড়তা অর্ধেক" বলে আশ্বাস দিলে এমন ইনপুট পড়বেই যেখানে পুরোটা ঘুরতে হবে, আর তুমি দায় সারতে পারবে না।

**৫. Early exit দেখে ভাবা complexity কমে গেছে।**
`if` পড়ে থামার সুবিধা best case-কে সুন্দর করে, worst case একই থাকে: target-টা না-ই থাকতে পারে, তখন পুরো array ঘুরতেই হবে। Worst-case Big-O early exit-এ বদলায় না।

## অনুশীলন

- **সহজ ১:** একটা ফাংশনে দুটো আলাদা লুপ পাশাপাশি, দুটোই 1 থেকে n পর্যন্ত। Complexity কত? হিন্ট: যোগ হয়, তারপর বড়টা টিকে।
- **সহজ ২:** `for (i = 0; i < n; i++)`-এর ভেতরে `for (j = 0; j < i; j++)`। ভেতরের কাজ মোট কতবার? হিন্ট: 1 + 2 + ... + (n - 1) = n(n - 1) / 2।
- **মাঝারি ১:** `for (i = 1; i < n; i *= 3)`-এর complexity কত? হিন্ট: base বদলালেও উত্তর বদলায় না; ভুল ৩-টা আবার পড়ো।
- **মাঝারি ২:** Maximum Subarray (LeetCode 53)। Brute force-এ সব subarray-এর যোগফল দেখা যায়; সেটা O(n²) না O(n³), নিজে গুনে ঠিক করো। হিন্ট: সব (i, j) জোড়া কয়টা, আর প্রতি জোড়ার যোগফল বের করতে আরেকটা লুপ লাগে কিনা।
- **কঠিন:** Merge sort-এর recurrence T(n) = 2T(n/2) + n খুলে Big-O অনুমান করো। হিন্ট: প্রতি level-এ মোট n-টা কাজ, level আছে log₂ n-টা; ভ্যারিয়েন্ট ১-এর খোলার কায়দা লাগবে। উত্তর [Merge Sort](../sorting/merge-sort.mdx)-এ মিলিয়ে নিতে পারো।

## সারসংক্ষেপ

- কোড থেকে Big-O: dominant loop ধরো, পাশাপাশি যোগ, nested গুণ, অর্ধেক মানে log, ধ্রুবক আর ছোট term বাদ।
- T(n) দাঁড় করিয়ে একে একে term ফেললে উত্তর নিজেই বেরিয়ে আসে।
- Counter বসিয়ে measured বনাম predicted মিলিয়ে নিলে নিজের হিসাবে ভরসা পাবে; n দ্বিগুণের পরীক্ষাটা মনে রাখো।
- Recursion-এ recurrence, push-এ amortized, আর রিপোর্টে সবসময় worst case।
- পরের পাতা: এই উত্তরগুলো কঠোর ভাষায় লেখার নিয়ম, [Asymptotic Notation](./asymptotic-notation.mdx)।
