## কী শিখব

- Greedy আসলে কী: প্রতি ধাপে ওই মুহূর্তের সেরা, পিছনে ফিরে তাকানো নয়
- কখন সেটা globally সেরা থাকে: exchange argument দিয়ে প্রমাণের ভাবনা
- Activity selection-এ একটা পুরো dry run: sort থেকে pick/skip টেবিল
- Coin change-এ greedy কখন নিখুঁত, কখন চুপিচুপি ভুল উত্তর দেয়
- Fractional বনাম 0/1 knapsack: একটাতে greedy জেতে, আরেকটায় হারে

## ধারণা

ভাবো তো, তুমি দোকানে ৯৩ টাকা ফেরত পাবে। দোকানদার কী করে? আগে ৫০-র নোটটা দেয়, তারপর ২০, আবার ২০, তারপর ২ আর ১। সে কি বসে বসে সব সম্ভাব্য কম্বিনেশন হিসাব করে? একদমই না। প্রতি ধাপে সে শুধু দেখে: এখন সবচেয়ে বড় কোন নোটটা দেওয়া যায়। এই মুহূর্তের সেরা সিদ্ধান্তটাই নিয়ে নেয়, পরেরটা পরে দেখবে।

এই কৌশলের নামই **greedy**: প্রতি ধাপে locally সেরা বাছাই, এই বিশ্বাসে যে ধাপগুলো মিলে globally সেরাটাই বের হবে। আর মজার ব্যাপার হলো, মাঝে মাঝে বিশ্বাসটা সত্যিই ঠিক থাকে, আবার মাঝে মাঝে চুপিচুপি ভুল প্রমাণ হয়। এই পাতার আসল লড়াইটা ওই "কখন"টা নিয়ে।

কাজ করার জন্য দুটো শর্ত লাগে:

1. **Greedy choice property:** locally সেরাটা নিলেও globally সেরা সমাধানে পৌঁছানো সম্ভব থাকে। মানে প্রথম সেরা বাছাইটা নিয়ে কোনো ক্ষতি হয় না।
2. **Optimal substructure:** একটা সিদ্ধান্তের পর বাকিটা আবার একই ধরনের ছোট সমস্যা, যার optimal সমাধান মিলেই বড়টার optimal।

প্রমাণটা সাধারণত **exchange argument** দিয়ে হয়: ধরো optimal সমাধানটা তোমার greedy-র প্রথম বাছাই নেয়নি। দেখাও যে ওটাকে বাদ দিয়ে তোমার বাছাইটা বসালে সমাধান খারাপ হয় না। তারপর একই যুক্তি বাকি ধাপগুলোতেও। নিচের activity selection-এ এটা হাতে ধরে দেখাব।

আর যেখানে এই প্রমাণ দাঁড়ায় না, সেখানে greedy সাজানো উত্তরের বদলে সাজানো **ভুল** উত্তর দেয়, একদম নিঃশব্দে। সেটাও দেখাব, coin change দিয়ে।

## ধাপে ধাপে ড্রাই রান: কোন কাজ নেব, কোনটা বাদ

সমস্যাটা হলো ক্লাসিক activity selection। একটা হলরুম, একদিন, আর একঢল্লাই কাজের আবেদন:

(1,4), (3,5), (0,6), (5,7), (3,9), (5,9), (6,10), (8,11), (8,12), (2,14), (12,16)

প্রতিটা জোড়া (শুরু, শেষ)। দুটো কাজ overlap করলে দুটোই নেওয়া যাবে না। লক্ষ্য: যত বেশি পারো কাজ করা। (কাজগুলো কাকতাল করে আগেই শেষের সময়ে সাজানো; তোমার ইনপুটে এমন না হলে আগে sort করতে হবে, greedy-র প্রথম ধাপ এটাই।)

Greedy-র নিয়ম: **যে কাজটা সবচেয়ে আগে শেষ হয়, সেটাই নাও।** যুক্তিটা সোজা: কাজ যত তাড়াতাড়ি শেষ, হলরুম তত তাড়াতাড়ি খালি, পরের কাজগুলোর জন্য তত বেশি জায়গা থাকে।

আগে ছবিটা দেখো। প্রতি কলাম এক ঘণ্টা, ০ থেকে ১৬ (দুই অঙ্কের সময়ের শুধু এককের অঙ্ক দেখানো):

```
        01234567890123456
(1,4)   .###.............
(3,5)   ...##............
(0,6)   ######...........
(5,7)   .....##..........
(3,9)   ...######........
(5,9)   .....####........
(6,10)  ......####.......
(8,11)  ........###......
(8,12)  ........####.....
(2,14)  ..############...
(12,16) ............####.
```

এবার উপর থেকে নিচে (শেষের সময়ের ক্রমে) একটা একটা করে দেখি। `lastEnd` মানে শেষ বাছাই করা কাজ কখন শেষ হয়েছে; নতুন কাজের শুরু তার আগে হলে বাদ।

| কাজ | শুরু | শেষ | lastEnd | শুরু >= lastEnd? | সিদ্ধান্ত |
|-----|------|------|---------|------------------|-----------|
| (1,4) | 1 | 4 | - | প্রথমটা, সবসময় নেই | নেব, lastEnd = 4 |
| (3,5) | 3 | 5 | 4 | 3 < 4 | বাদ |
| (0,6) | 0 | 6 | 4 | 0 < 4 | বাদ |
| (5,7) | 5 | 7 | 4 | 5 >= 4 | নেব, lastEnd = 7 |
| (3,9) | 3 | 9 | 7 | না | বাদ |
| (5,9) | 5 | 9 | 7 | 5 < 7 | বাদ |
| (6,10) | 6 | 10 | 7 | 6 < 7 | বাদ |
| (8,11) | 8 | 11 | 7 | 8 >= 7 | নেব, lastEnd = 11 |
| (8,12) | 8 | 12 | 11 | 8 < 11 | বাদ |
| (2,14) | 2 | 14 | 11 | না | বাদ |
| (12,16) | 12 | 16 | 11 | 12 >= 11 | নেব, lastEnd = 16 |

উত্তর: **৪টা কাজ**, (1,4), (5,7), (8,11), (12,16)। ছবিতে মেলাও, এদের কোনোটাই আরেকটার সারিতে ঢোকেনি।

কেন এটাই সর্বোচ্চ? Exchange argument দিয়ে দেখো। ধরো কোনো optimal সমাধান আছে, যার প্রথম কাজটা আমাদের বাছাই করা (1,4) নয়। ওর প্রথম কাজটা অবশ্যই ৪ বা তার পরে শেষ হয়, কারণ (1,4)-ই সবার আগে শেষ। তাহলে ওটা সরিয়ে জায়গায় (1,4) বসাও: বাকি কাজগুলোর কোনো ক্ষতি নেই, রুম তো অন্তত ঐ সময়েই খালি পেল, বরং আরও আগে। মানে (1,4) নিয়েও optimal সমাধান আছে। এবার বাকি কাজগুলো নিয়ে একই যুক্তি। প্রতি ধাপে greedy-র বাছাইকে optimal-এ ঢুকিয়ে দেওয়া যায়, কোনো ক্ষতি ছাড়াই। এটাই প্রমাণ।

একটা প্রশ্ন মাথায় রাখো: প্রমাণটা দাঁড়াল কারণ "আগে শেষ" মানে "পরেরদের জন্য বেশি জায়গা"। এমন সমস্যা যেখানে একটা locally সেরা বাছাই পরের সুযোগগুলোকে **বদলে দেয়**, সেখানে এই যুক্তি ভেঙে যায়। কয়েনের ব্যাপারটা ঠিক এমনই, একটু পরেই আসছে।

## কোড: পুরো implementation (এক ফাইলে)

```js
// ---- Activity selection: শেষের সময়ে sort, তারপর greedy বাছাই ----
function activitySelection(activities) {
  const sorted = [...activities].sort((a, b) => a.end - b.end);
  const picked = [];
  let lastEnd = -Infinity;          // এখনো কিছু নিইনি

  for (const act of sorted) {
    if (act.start >= lastEnd) {     // আগেরটা শেষ হওয়ার পরে শুরু?
      picked.push(act);             // নেব
      lastEnd = act.end;            // রুম এখন act.end পর্যন্ত ব্যস্ত
    }
  }
  return picked;
}

// ---- Coin change (canonical মুদ্রা): বড় থেকে ছোট ----
function minCoins(amount, coins) {
  const sorted = [...coins].sort((a, b) => b - a);  // বড়টা আগে
  const used = [];

  for (const coin of sorted) {
    while (amount >= coin) {        // এই কয়েন যতবার যায়
      used.push(coin);
      amount -= coin;
    }
  }
  return amount === 0 ? used : null;  // বানানোই না গেলে null
}

// ---- ডেমো ----
const tasks = [
  { start: 1, end: 4 }, { start: 3, end: 5 }, { start: 0, end: 6 },
  { start: 5, end: 7 }, { start: 3, end: 9 }, { start: 5, end: 9 },
  { start: 6, end: 10 }, { start: 8, end: 11 }, { start: 8, end: 12 },
  { start: 2, end: 14 }, { start: 12, end: 16 },
];

const chosen = activitySelection(tasks);
console.log("বাছাই:", chosen.map(a => `(${a.start},${a.end})`).join(" "));
// বাছাই: (1,4) (5,7) (8,11) (12,16)
console.log("মোট কাজ:", chosen.length); // 4

// বাংলাদেশি নোট দিয়ে 1270 ভাঙানো
console.log(minCoins(1270, [1000, 500, 100, 50, 20, 10, 5, 2, 1]));
// [ 1000, 100, 100, 50, 20 ]

console.log(minCoins(93, [50, 20, 10, 5, 2, 1]));
// [ 50, 20, 20, 2, 1 ]

console.log(minCoins(5, [3, 4])); // null: বানানোই যায় না
```

দুটো ফাংশনেরই ছন্দ এক: আগে sort, তারপর একটা loop-এ প্রতিবার locally সেরাটা তুলে নেওয়া। Greedy-র কোড দেখতে প্রায় সবসময় এত সরল যে বিপদটা সরলতাতেই: মনে হয় সব জায়গায় লাগানো যাবে।

## ভ্যারিয়েন্ট ১: যেখানে greedy ফেল করে (coin change counterexample)

ওপরের coin change ঠিকঠাক চলল কারণ বাংলাদেশি (আর মার্কিন) মুদ্রার সেটগুলো **canonical**: বড় নোট নেওয়াটা কখনো ভুল সিদ্ধান্ত হয় না। কিন্তু মুদ্রার সেটটা একটু এলোমেলো হলেই ছবি পাল্টায়।

ধরো কয়েন [1, 3, 4], বানাতে হবে 6। Greedy বলবে: সবচেয়ে বড়টা নাও, 4। বাকি 2, তাই 1 আর 1। মোট ৩টা কয়েন: 4 + 1 + 1। কিন্তু চোখ বুলালেই দেখা যায় 3 + 3 দিয়েই 6 হয়, মাত্র ২টা কয়েন। Greedy চুপিচুপি ভুল উত্তর দিয়ে বসল, কোনো error ছাড়াই।

```js
console.log(minCoins(6, [1, 3, 4])); // [ 4, 1, 1 ] -> 3টা কয়েন
// optimal: [3, 3] -> 2টা! greedy হারল
```

কেন হারল? 4 নেওয়ার locally সেরা সিদ্ধান্তটা বাকি অংকের (2) গঠন বদলে দিল: 2 আর কোনো ভালো কয়েনে ভাঙা যায় না। Exchange argument এখানে দাঁড়ায় না। এমন অবস্থায় সব সম্ভাব্য ভাঙ্গন দেখতে হয়, আর সেটাই [Dynamic Programming](./dynamic-programming.mdx)-এর কাজ। মুদ্রার সেট দেখে আগে সিদ্ধান্ত নেবে: canonical হলে greedy, না হলে DP।

## ভ্যারিয়েন্ট ২: fractional knapsack (greedy জেতে) বনাম 0/1 knapsack (greedy হারে)

তোমার ব্যাগে ৫০ কেজি ঢোকে। গুদামে চাল, ডাল, চিনি: প্রতি কেজির দাম আলাদা। **Fractional** knapsack-এ তুমি যেকোনো জিনিস ভেঙে নিতে পারো, আধা কেজি চিনিও চলে। তখন নিয়ম পরিষ্কার: প্রতি কেজির দাম (ratio) অনুযায়ী sort, সবচেয়ে দামি ratio-টা আগে যতটুকু যায় ততটুকু নাও।

```js
function fractionalKnapsack(items, capacity) {
  // items: { weight, value }; ratio বড় থেকে ছোট
  const byRatio = [...items].sort((a, b) => b.value / b.weight - a.value / a.weight);
  let total = 0;

  for (const item of byRatio) {
    if (capacity <= 0) break;
    const take = Math.min(item.weight, capacity); // ভাগ করে নেওয়া যায়
    total += take * (item.value / item.weight);
    capacity -= take;
  }
  return total;
}
```

কিন্তু **0/1 knapsack**-এ জিনিস ভাগা যায় না: টিভি, ল্যাপটপ, ক্যামেরা, হয় পুরো নেবে নয় ছাড়বে। সেখানে ratio-তে greedy লাগালেই ফেল। দেখো: capacity 50, জিনিস (ওজন, দাম) = (10,60), (20,100), (30,120)। Ratio যথাক্রমে 6, 5, 4। Greedy নেবে 10 আর 20, মোট দাম 160, আর ব্যাগে 20 কেজি ফাঁকা পড়ে থাকবে যেখানে কিছুই ঢোকে না। আসল optimal: 20 আর 30, দাম 220। ভাগ করার অনুমতিটুকুই greedy-কে বাঁচিয়েছিল; অনুমতি উঠে গেলে আবার [Dynamic Programming](./dynamic-programming.mdx)।

## ভ্যারিয়েন্ট ৩: gas station (প্রমাণটা চালাকের)

গোলাকার রাস্তায় n-টা পাম্প। i-তম পাম্পে gas[i] পরিমাণ তেল পাবে, পরের পাম্পে যেতে cost[i] খরচ। কোন পাম্প থেকে শুরু করলে পুরো চক্কর ঘুরে ফিরে আসা যায়?

Greedy: শুরু 0 থেকে, tank-এ তেল জমাতে থাকো। কোনো পাম্পে গিয়ে tank negative হলে বুঝবে এই stretch-এর কেউই শুরু হতে পারে না, তাই শুরু সরাও পরের পাম্পে।

```js
function canCompleteCircuit(gas, cost) {
  let total = 0, tank = 0, start = 0;

  for (let i = 0; i < gas.length; i++) {
    const diff = gas[i] - cost[i];
    total += diff;                 // পুরো চক্করের হিসাব
    tank += diff;                  // চলতি stretch-এর হিসাব
    if (tank < 0) {                // এখানে আটকে গেলাম
      start = i + 1;               // start..i কেউই উত্তর নয়
      tank = 0;
    }
  }
  return total >= 0 ? start : -1;  // মোট তেলই কম হলে অসম্ভব
}
```

প্রমাণের মূল পয়েন্ট: যদি start থেকে i-এর মাঝের কেউ শুরু হতে পারত, তাহলে ওখান থেকে শুরু করে tank শূন্যের বদলে positive জমা নিয়ে এগোত, অথচ আমরা ওই পথ দিয়েই এসে i-তে আটকেছি। তাই ওরাও আটকত। একটা pass-ই উত্তর, O(n)।

## কোড ব্রেকডাউন: দুটো মূল ফাংশন, লাইনে লাইনে

আগে `activitySelection`:

1. `[...activities].sort(...)` : মূল array নষ্ট না করে কপি নিয়ে sort। Key হলো শেষের সময়, কারণ প্রমাণটা দাঁড়িয়েছে "আগে শেষ"-এর ওপর।
2. `let lastEnd = -Infinity` : কোনো কাজ নেওয়া হয়নি, তাই প্রথম যেকোনো কাজের শুরুই `>= lastEnd` মেনে যাবে। প্রথমটা ফ্রি-তে নেওয়া, আর সেটাই প্রমাণের ভিত্তি।
3. `if (act.start >= lastEnd)` : overlap চেক। এখানে `>=` কারণ একটা কাজ শেষ হওয়ার মুহূর্তেই আরেকটা শুরু হতে পারে (সমস্যাভেদে `>` হতে পারে, নিচের ভুলগুলো দেখো)।
4. `picked.push(act)` : locally সেরাটা নিলাম। এই নেওয়ার সিদ্ধান্তটাই greedy choice।
5. `lastEnd = act.end` : রুম এখন এই সময় পর্যন্ত ব্যস্ত। পরের সব সিদ্ধান্ত এই একটা সংখ্যা দেখেই হবে, greedy-র state এতটুকুই।

তারপর `minCoins`:

6. `sort((a, b) => b - a)` : বড় কয়েন আগে। Greedy-র প্রথম ধাপ প্রায় সবসময় একটা sort, কিন্তু **কোন key-এ**, সেটাই আসল প্রশ্ন।
7. `while (amount >= coin)` : একই কয়েন যতবার যায় ততবার। `if` নয়, `while`।
8. `amount -= coin` : সিদ্ধান্ত চূড়ান্ত, ফিরে তাকানো নেই। এই no-look-back-টাই greedy-র শক্তি আর দুর্বলতা দুটোই।
9. `return amount === 0 ? used : null` : কয়েনের সেটে 1 না থাকলে amount বানানো নাও যেতে পারে। চুপচাপ ভুল array ফেরত দেওয়ার চেয়ে null অনেক ভদ্র।

## Complexity: হিসাবটা কোথা থেকে আসে

**Activity selection: সময় O(n log n), জায়গা O(n)।** ভেঙে দেখো:

- sort: n-টা কাজ, O(n log n)।
- তারপর একটাই loop, প্রতি কাজে O(1) চেক: O(n)।
- মিলে O(n log n + n) = **O(n log n)**। Sort-ই bottleneck। ইনপুট আগে থেকেই sorted হলে (আজকের উদাহরণের মতো) শুধু O(n)।
- জায়গা: sort-এর কপি O(n); in-place sort করলে অতিরিক্ত O(1), বাকি শুধু output।

**Coin change: O(k log k + m), যেখানে k = কয়েনের ধরন, m = উত্তরে কয়েনের সংখ্যা।**

- sort: O(k log k)।
- while-গুলো মিলে মোট যতবার চলে, উত্তরে ততগুলো কয়েন যায়: m-বার। সবচেয়ে খারাপে m প্রায় amount / সবচেয়ে ছোট কয়েন।
- মোটামুটি ধরলে O(amount)। লক্ষ্য রাখো, এটা amount-এর **মান**-এর ওপর নির্ভর করে, ইনপুটে সংখ্যাটা যত বড় তত ধীর; DP সংস্করণেরও একই দশা।

প্র্যাকটিক্যাল কথা: greedy-র চার্মই এর সস্তা। যেখানে প্রমাণ দাঁড়ায়, সেখানে brute force বা DP-র তুলনায় অনেক কমে আসে, প্রায়ই একটা pass-ই যথেষ্ট। তাই আগে greedy ভাবো, তারপর প্রমাণ খোঁজো; প্রমাণ না পেলে তবেই DP-তে নামো।

## সাধারণ ভুল আর edge case

**১. ভুল key-এ sort করা।**
Activity selection-এ শুরুর সময় বা duration-এ sort করলে উত্তর ভেঙে যাবে। শুরু অনুযায়ী নিলে (0,6) প্রথমে উঠে আসে, নিলে পুরো সকাল আটকে যায়। Duration-এ sort-ও ভুল: একটা ছোট কাজ যা সবার সঙ্গে overlap করে, আগে নিলে বাকিদের পথ বন্ধ। প্রমাণ যে key-এর ওপর দাঁড়িয়েছে, sort ঠিক সেই key-এই।

**২. প্রমাণ ছাড়া greedy লাগানো।**
কোড সরল দেখে মনে হয় সবসময় কাজ করবে। [1,3,4] দিয়ে 6 বানাতে বললে greedy নিঃশব্দে ভুল দেয় (ভ্যারিয়েন্ট ১ দেখো)। অভ্যাস করো: greedy লেখার আগে একটা ছোট counterexample খোঁজার চেষ্টা করো। না পেলে তবেই এগোও; পেলে সোজা [Dynamic Programming](./dynamic-programming.mdx)।

**৩. `>` বনাম `>=` গুলিয়ে ফেলা।**
এক কাজ শেষ হওয়ার মুহূর্তেই অন্যটা শুরু হতে পারে, এমন হলে `>=` লাগে; না পারলে `>`। ভুল চিহ্ন দিলে উত্তর ঠিক একটা বেশি বা কম আসবে, আর ছোট টেস্টে ধরাও পড়বে না। সমস্যার শর্তটা আগে পড়ো।

**৪. অসম্ভব amount হ্যান্ডেল না করা।**
minCoins(5, [3, 4]) চালালে while-গুলো শেষে amount = 5-ই থাকে। `null` চেক না করলে caller ভাববে খালি array মানে "কিছুই লাগে না", অথচ আসল মানে "বানানোই যায় না"। এই দুটো এক নয়।

**৫. fractional আর 0/1 গুলিয়ে ফেলা।**
দুটোর নামই knapsack, কিন্তু একটায় জিনিস ভাগা যায়, আরেকটায় যায় না। Ratio-greedy শুধু fractional-এ ঠিক। 0/1-এ লাগালে ভ্যারিয়েন্ট ২-র counterexample-এর মতোই ব্যাগের এক চিলতে কোণা ফাঁকা থেকে গিয়ে optimal হারাবে।

## অনুশীলন

- **সহজ ১:** Assign Cookies (LeetCode 455)। হিন্ট: বাচ্চাদের greed factor আর কুকির size, দুটোই sort করো; প্রতি বাচ্চাকে মানানসই **সবচেয়ে ছোট** কুকি দাও, না মিললে পরের কুকিতে যাও।
- **সহজ ২:** Lemonade Change (LeetCode 860)। হিন্ট: ২০ ডলারের নোট এলে আগে ১০ + ৫ দিয়ে ভাঙাও, না পারলে তিনটা ৫; ৫ ডলারের নোটই তোমার আসল সম্পদ, অযথা খরচ নয়।
- **মাঝারি ১:** Jump Game (LeetCode 55)। হিন্ট: maxReach ট্র্যাক করো; কোনো index i যদি maxReach ছাড়িয়ে যায়, সেখানেই false। পৌঁছানো যায় এমন সব index থেকে maxReach বাড়াতে থাকো।
- **মাঝারি ২:** Jump Game II (LeetCode 45)। হিন্ট: currentEnd আর farthest, এই দুটো রাখো; i যখন currentEnd ছুঁয়ে যায়, jump বাড়াও আর currentEnd = farthest। [BFS](../graphs/bfs.mdx)-এর স্তর-ব্যবস্থার সঙ্গে মিল খুঁজে পাবে।
- **কঠিন:** Non-overlapping Intervals (LeetCode 435)। হিন্ট: এটাই আজকের activity selection, উল্টোদিক থেকে পড়া: যত বেশি overlap-মুক্ত কাজ রাখা যায়, মোট থেকে বাদ দাও। sort-টা [merge intervals](./merge-intervals.mdx) পড়ে থাকলে চেনা লাগবে।

## সারসংক্ষেপ

- Greedy = প্রতি ধাপে locally সেরা, আর ফিরে তাকানো নেই। কাজ করার শর্ত: greedy choice property আর optimal substructure।
- প্রমাণের হাতিয়ার exchange argument: তোমার বাছাইটা optimal-এ বসিয়েও ক্ষতি হয় না, এটা দেখাতে হয়।
- প্রথম ধাপ প্রায় সবসময় sort; আর আসল সিদ্ধান্ত হলো **কোন key-এ**।
- Activity selection O(n log n), coin change মোটামুটি O(amount): যেখানে greedy দাঁড়ায়, সেখানে DP-র চেয়ে অনেক সস্তা।
- [1,3,4] দিয়ে 6: এই ছোট্ট counterexample-টা মাথায় রাখো। Greedy মানেই ঠিক, এমন নয়; ঠিক, তবেই greedy।
- আরেকটা জায়গায় greedy নিখুঁত: cache eviction-এ ভবিষ্যৎ জানা থাকলে "সবচেয়ে দূরে যেটা লাগবে সেটাই নামাও" (LFD) প্রমাণিত optimal - [Online Algorithms](./online-algorithms.mdx)।
