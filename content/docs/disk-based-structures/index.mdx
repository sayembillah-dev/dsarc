ভাবো তো, তোমার হাতে এমন ডেটা এসেছে যেটা পুরোটা memory-তেই ঢোকে না। তখন কী করবে? এই chapter-এর কাঠামোগুলো ঠিক সেই পরিস্থিতির জন্যই বানানো। এখানে লক্ষ্য একটাই: disk থেকে যত কম পড়া যায়। আগের section-গুলোর বিশেষায়িত কাঠামো memory-তে দারুণ চলত, কিন্তু ডেটা disk-এ চলে গেলে খেলাটাই বদলে যায়। প্রতিটা disk read দামি, তাই কাঠামোকেই disk-বান্ধব ভাবতে হয়। আর এরা শুধু তত্ত্বের জন্য নয়, তোমার চেনা MySQL, Redis সবাই এদেরই উপর দাঁড়িয়ে।

**Section Roadmap:** 2-3 Tree, B-Tree/B+ Tree, Skip List, ISAM, Indexing (Linear, Tree-Based)।

## এই Chapter-এ যা যা আছে

1. [2-3 Tree](./two-three-tree.mdx): split/merge দিয়ে সবসময় balanced multi-way search tree
2. [B-Tree ও B+ Tree](./b-plus-tree.mdx): database ও file system-এর মূল index, কম height মানে কম disk read
3. [Skip List](./skip-list.mdx): linked list-এ express lane বসিয়ে গড়ে O(log n) search
4. [ISAM](./isam.mdx): static index-ভিত্তিক পুরনো কিন্তু শিক্ষণীয় disk indexing পদ্ধতি
5. [Indexing (Linear ও Tree-Based)](./indexing.mdx): hash (equality O(1)) বনাম tree (equality ও range)

## সারাংশ

ধরো পুরো chapter-টা এক নিঃশ্বাসে। 2-3 Tree হলো split/merge দিয়ে balanced থাকা গাছ, B-Tree-র বীজ এটাই। B/B+ Tree height কম রাখে, মানে কম disk read; B+ Tree-র leaf গুলো পরস্পর linked, তাই range query-তে ওটাই database-এর default। Skip List? linked list-এ express lane বসিয়ে দাও, গড়ে O(log n)। ISAM হলো static index, read-heavy কাজে দারুণ কিন্তু write-heavy-তে পড়ে যায়। আর Indexing-এ আসল প্রশ্ন একটাই: hash নাকি tree? equality-তে hash O(1), কিন্তু equality আর range দুটোই চাইলে tree।
