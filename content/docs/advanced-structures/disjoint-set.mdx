## কী শিখব

- Disjoint Set (Union-Find) কী জিনিস: representative বা parent pointer দিয়ে গোষ্ঠী ট্র্যাক করা
- find আর union দুটো অপারেশন আসলে কী করে
- দুটো ছোট কৌশল: path compression আর union by rank, আর এদের জোড়ে কেন সব প্রায় O(1)
- হাতে হাতে পুরো dry run: ৭ জন সদস্য, চারটা union, একটা connected প্রশ্ন
- Complexity-র হিসাব: কেন α(n), আর optimization ছাড়া কী দুর্দশা
- আসল ব্যবহার: Kruskal MST, number of provinces, cycle detection

## ধারণা

ভাবো তো কলেজের ক্লাবগুলোর কথা। ফটোগ্রাফি ক্লাবের আলাদা দল, ডিবেট ক্লাবের আলাদা দল। হঠাৎ ফেস্টের জন্য দুইটা ক্লাব একত্র হলো, এখন থেকে সবাই একই দলের। কাল আবার তোমার বন্ধু জিজ্ঞেস করল, "তুই আর রাফি কি এখন একই দলে?" উত্তরটা এক সেকেন্ডে দিতে হবে।

খাতা-কলমে করলে কী করতে হতো? প্রতিবার প্রশ্ন এলে দুজনের দলের পুরো তালিকা মিলিয়ে দেখতে হতো। দল বড় হলে সেটাই কষ্ট। কিন্তু যদি প্রতিটা দলের একজন **সদস্য-প্রতিনিধি** (representative) ঠিক করে রাখো, আর সবাই শুধু জানে "আমার প্রতিনিধি কে", তাহলে প্রশ্নটা সহজ হয়ে যায়: দুজনের প্রতিনিধি একই কিনা দেখলেই চলে।

Disjoint Set (অনেক জায়গায় **Union-Find** নামেই চেনা যায়) ঠিক এটাই করে। প্রতিটা উপাদানের একটা **parent pointer** থাকে। যার parent সে নিজেই, সে-ই দলের প্রতিনিধি, তাকে বলে **root**। হাতে থাকে দুটো অপারেশন:

- **find(x):** x-এর দলের root কে? parent ধরে ধরে উপরে উঠতে থাকো, যার parent সে নিজে সেখানেই থামো।
- **union(a, b):** দুটো দল এক করে দাও, মানে এক দলের root-কে আরেক দলের root-এর নিচে ঢুকিয়ে দাও।

শুরুতে সবাই আলাদা আলাদা দল, প্রত্যেকে নিজের parent। এখানেই টুইস্ট। না-বুঝে union করতে থাকলে গাছ লম্বা চেইন হয়ে যায়, আর find চলতে থাকে O(n)-এ। কিন্তু দুটো ছোট্ট কৌশল, **path compression** (find চলার সময় পথের সবাইকে সরাসরি root-এর নিচে ঝুলিয়ে দেওয়া) আর **union by rank** (ছোট গাছকে বড় গাছের নিচে ঢোকানো), এই দুটো জোড়ে প্রতি অপারেশন প্রায় ধ্রুবক সময়ে নেমে আসে। এই "প্রায় ধ্রুবক"-টা কী, সেটা Complexity অংশে হাতে গুনে দেখাবো।

কেন এই পাতাটা জরুরি? [Kruskal MST](../graphs/minimum-spanning-tree.mdx), cycle detection, [connected component](../graphs/connected-components.mdx) গোনা, grid-এ island জোড়া, সব জায়গায় Union-Find কাজে লাগে। Graph-এর অনেক প্রশ্নের উত্তর আসলে DSU-ই।

## ধাপে ধাপে ড্রাই রান

কোডে যাওয়ার আগে হাতে হাতে চালিয়ে দেখি। ৭ জন সদস্য: 0 থেকে 6। শুরুতে সবাই নিজের দলের root:

```
0   1   2   3   4   5   6      (সবাই নিজের parent)
```

parent array: index-টা সদস্য, ভেতরের মান তার parent। শুরুতে `[0, 1, 2, 3, 4, 5, 6]`।

দুটো অপ্টিমাইজেশনই চালু রেখে ধারাবাহিকভাবে চালাই: `union(0,1)`, `union(1,2)`, `union(3,4)`, `union(2,4)`, তারপর প্রশ্ন `connected(0, 4)?`

| ধাপ | অপারেশন | root-গুলো | parent array (পরে) | মন্তব্য |
|-----|---------|-----------|--------------------|---------|
| শুরু | - | সবাই নিজে | [0,1,2,3,4,5,6] | ৭টা আলাদা দল, সব rank 0 |
| ১ | union(0,1) | 0, 1 | [0,0,2,3,4,5,6] | rank সমান, 1 ঢুকল 0-এর নিচে, rank[0]=1 |
| ২ | union(1,2) | find(1)=0, find(2)=2 | [0,0,0,3,4,5,6] | rank[0]=1 > rank[2]=0, 2 ঢুকল 0-এর নিচে |
| ৩ | union(3,4) | 3, 4 | [0,0,0,3,3,5,6] | rank সমান, 4 ঢুকল 3-এর নিচে, rank[3]=1 |
| ৪ | union(2,4) | find(2)=0, find(4)=3 | [0,0,0,0,3,5,6] | rank[0]=rank[3]=1, 3-এর দল ঢুকল 0-এর নিচে, rank[0]=2 |
| ৫ | connected(0,4) | find(0)=0, find(4)=0 | [0,0,0,0,0,5,6] | true! find(4) চলতে গিয়ে compression: 4 সরাসরি 0-এর নিচে |

খেয়াল করো ধাপ ২-তে। union(1,2) বললেও 1 আর 2-কে সরাসরি জোড়াই না। আগে দুজনের root বের করি, 1-এর root তো 0, তারপর root-দের জোড়া লাগাই। এটাই সবচেয়ে গুরুত্বপূর্ণ অভ্যাস: **union সবসময় root-দের নিয়ে**, সদস্যদের নিয়ে নয়। ধাপ ৪-এর পর গাছটা দাঁড়াল এরকম:

```
        0
      / | \
     1  2  3
           |
           4
```

আর ধাপ ৫-এ find(4) চলার সময় 4 → 3 → 0 পথে উঠে গেল, আর compression পথের সবাইকে সরাসরি root-এর নিচে ঝুলিয়ে দিল:

```
        0
     / / \ \
    1 2   3 4
```

parent array আগে `[0,0,0,0,3,5,6]`, পরে `[0,0,0,0,0,5,6]`। শুধু 4-এর parent বদলেছে, কিন্তু পরের সব find(4) এখন এক লাফে শেষ।

**optimization ছাড়া কী হতো?** এবার কল্পনা করো, একই চারটা union যদি না-বুঝে করতাম: rank দেখা নেই, প্রথমটার root-কে দ্বিতীয়টার নিচে ঢুকিয়ে দিলাম, compression-ও নেই।

| অপারেশন | parent array (না-বুঝে) | গাছের চেহারা |
|---------|----------------------|--------------|
| union(0,1) | [1,1,2,3,4,5,6] | 0 → 1 |
| union(1,2) | [1,2,2,3,4,5,6] | 0 → 1 → 2 |
| union(3,4) | [1,2,2,4,4,5,6] | 3 → 4 |
| union(2,4) | [1,2,4,4,4,5,6] | 0 → 1 → 2 → 4 |
| connected(0,4) | find(0) চলে ৩ লাফে | true, কিন্তু দাম বেশি |

দুইটা গাছ পাশাপাশি রাখি:

```
  না-বুঝে:            কৌশলসহ:
    4                    0
    |                 / / \ \
    2                1 2   3 4
    |
    1
    |
    0
```

একই প্রশ্নের উত্তর, কিন্তু না-বুঝে গাছে find(0)-এ ৩টা লাফ, কৌশলসহ গাছে ১টা। ৭ জনে পার্থক্য ছোট, কিন্তু একটা সুন্দর ক্রমে union করলে না-বুঝে গাছ n-লম্বা চেইন হয়ে যায়, আর সেখানে find চলে O(n)-এ। এই পার্থক্যের জন্যই দুটো কৌশল।

## কোড

একটাই পুরো runnable ফাইল। DSU class, আর নিচে আমাদের dry run-টাই demo হিসেবে:

```js
class DSU {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
    this.components = n;          // শুরুতে সবাই আলাদা দল
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(a, b) {
    const ra = this.find(a);
    const rb = this.find(b);
    if (ra === rb) return false;  // আগে থেকেই একই দলে, কিছু করার নেই

    if (this.rank[ra] < this.rank[rb]) {
      this.parent[ra] = rb;       // ছোট গাছ বড় গাছের নিচে
    } else if (this.rank[ra] > this.rank[rb]) {
      this.parent[rb] = ra;
    } else {
      this.parent[rb] = ra;       // rank সমান, যেকোনো একটা বেছে
      this.rank[ra]++;            // নতুন গাছ এক ধাপ লম্বা
    }
    this.components--;
    return true;                  // সত্যিই দুটো দল মিশল
  }

  connected(a, b) {
    return this.find(a) === this.find(b);
  }

  count() {
    return this.components;
  }
}

// --- ডেমো: পাতার dry run-টাই ---
const dsu = new DSU(7);
console.log("শুরুতে component:", dsu.count());          // 7

dsu.union(0, 1);
dsu.union(1, 2);
dsu.union(3, 4);
console.log("তিনটা union-এর পর component:", dsu.count()); // 4
console.log("connected(0, 2)?", dsu.connected(0, 2));  // true
console.log("connected(0, 4)?", dsu.connected(0, 4));  // false

dsu.union(2, 4);
console.log("union(2,4)-এর পর parent:", dsu.parent.join(" ")); // 0 0 0 0 3 5 6
console.log("এখন connected(0, 4)?", dsu.connected(0, 4));      // true
console.log("find চলার পর parent:", dsu.parent.join(" "));     // 0 0 0 0 0 5 6
console.log("শেষে component:", dsu.count());            // 3
```

চালিয়ে দেখবে: শেষ দুই লাইনের parent array-এ পার্থক্যটাই path compression-এর জীবন্ত প্রমাণ। union(2,4) শেষে 4-এর parent ছিল 3, find(4) চলার পর সরাসরি 0।

`union`-এর return মানটা ছোট কিন্তু দারুণ কাজের। false মানে দুই প্রান্ত আগে থেকেই একই দলে, মানে এই জোড়াটা একটা cycle তৈরি করত। [Cycle detection](../graphs/cycle-detection.mdx) আর Kruskal-এ এই return মানটাই কাজে লাগে।

## ভ্যারিয়েন্ট

### ১. union by rank বনাম union by size

rank-এর বদলে গাছের আসল সদস্য সংখ্যা (size) দেখেও ছোট-বড় ঠিক করা যায়। দুটোই একই গ্যারান্টি দেয়। size-ভিত্তিকটা অনেকের কাছে স্বজ্ঞাত, কারণ "ছোট দল বড় দলে মিশুক" শুনতেই সহজ:

```js
class DSUBySize {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.size = new Array(n).fill(1);
  }
  find(x) {
    if (this.parent[x] !== x) this.parent[x] = this.find(this.parent[x]);
    return this.parent[x];
  }
  union(a, b) {
    let ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false;
    if (this.size[ra] < this.size[rb]) [ra, rb] = [rb, ra]; // ra যেন বড়টা
    this.parent[rb] = ra;
    this.size[ra] += this.size[rb];
    return true;
  }
}

const s = new DSUBySize(5);
s.union(0, 1); s.union(2, 3); s.union(1, 3);
console.log(s.size[s.find(3)]); // 4, চারজনের একটাই দল
```

পার্থক্যটা সূক্ষ্ম: rank হলো উচ্চতার অনুমান, compression-এর পর আর আসল উচ্চতা থাকে না। size হলো আসল গোনা, তাই "দলটায় কতজন" জানতে হলে size-ই লাগে।

### ২. Kruskal MST-তে DSU

[Minimum Spanning Tree](../graphs/minimum-spanning-tree.mdx) পাতায় দেখেছ, Kruskal-এর অ্যালগরিদম edge-গুলো weight-এর ক্রমে sort করে একে একে নেয়, আর প্রতিবার জিজ্ঞেস করে, "এই edge-টা নিলে cycle হবে তো?" এই প্রশ্নের উত্তরটাই DSU দেয়, `union`-এর return মান দিয়ে:

```js
function kruskal(n, edges) {
  edges.sort((a, b) => a[2] - b[2]); // weight অনুযায়ী sort
  const dsu = new DSU(n);
  let weight = 0, used = 0;

  for (const [u, v, w] of edges) {
    if (dsu.union(u, v)) {        // false মানে cycle হতো, বাদ
      weight += w;
      used++;
      if (used === n - 1) break;  // n-1 edge মানেই tree পুরো
    }
  }
  return weight;
}

console.log(kruskal(4, [[0,1,10],[0,2,6],[0,3,5],[1,3,15],[2,3,4]]));
// 19 (edge 2-3, 0-3, 0-1)
```

sort-এ লাগে O(E log E), তারপর E-টা union-find চলে প্রায় O(E)-তে। তাই পুরো Kruskal-এর bottleneck sort, DSU নয়।

### ৩. Number of provinces (adjacency matrix-এ)

একটা শহর-সংযোগের matrix দেওয়া আছে, `isConnected[i][j] = 1` মানে i আর j সরাসরি জোড়া। ক-টা আলাদা province (connected group)? এটা DSU-এর textbook ব্যবহার, প্রতিটা জোড়ায় union, শেষে count:

```js
function findCircleNum(isConnected) {
  const n = isConnected.length;
  const dsu = new DSU(n);

  for (let i = 0; i < n; i++) {
    for (let j = i + 1; j < n; j++) {  // উপরের ত্রিভুজটুকুই যথেষ্ট
      if (isConnected[i][j] === 1) dsu.union(i, j);
    }
  }
  return dsu.count();
}

console.log(findCircleNum([[1,1,0],[1,1,0],[0,0,1]])); // 2
console.log(findCircleNum([[1,0,0],[0,1,0],[0,0,1]])); // 3
```

মনে করো ম্যাট্রিক্সটা symmetric, তাই `j = i + 1` থেকে শুরু করলে প্রতিটা জোড়া একবারই দেখা হয়। একই প্রশ্ন [connected components](../graphs/connected-components.mdx)-এ BFS দিয়েও করেছ, কিন্তু ইনপুট edge-এর ধারা হিসেবে এলে DSU অনেক স্বাভাবিক।

## কোড ব্রেকডাউন

মূল DSU-টা আবার দেখি, কোন লাইন কেন আছে:

1. `this.parent = Array.from({ length: n }, (_, i) => i)` : শুরুতে সবাই নিজের parent, মানে n-টা আলাদা দল। `i` মানে index-টাই value হয়ে গেল।
2. `this.rank = new Array(n).fill(0)` : সবার rank শূন্য। rank শুধু root-এর জন্য অর্থবহ, অন্যদেরটা পুরনো হয়ে যায়, সেটা দেখে ঘাবড়ার কিছু নেই।
3. `this.components = n` : দল সংখ্যা ট্র্যাক করছি, প্রতিবার সফল union-এ এক কমবে।
4. `if (this.parent[x] !== x)` : x নিজে root কিনা চেক। root না হলে উপরে উঠো।
5. `this.parent[x] = this.find(this.parent[x])` : এটাই path compression। recursion ফেরার পথে পথের প্রতিটা node-এর parent সরাসরি root বসে যায়। একটাই লাইন, কিন্তু এর জাদুতেই গাছ চ্যাপ্টা থাকে।
6. `const ra = this.find(a); const rb = this.find(b)` : union সবসময় root-দের নিয়ে। সদস্য নয়, প্রতিনিধি নিয়ে কথা বলি।
7. `if (ra === rb) return false` : দুটো root একই মানে আগে থেকেই একই দল। false ফেরালে ডাকার জায়গায় বোঝা যায় এই জোড়া cycle বানাত।
8. `if (this.rank[ra] < this.rank[rb]) ...` : union by rank। ছোট rank-এর গাছ বড় rank-এর নিচে ঢোকে, ফলে গাছ লম্বা হয় না।
9. `this.rank[ra]++` : শুধু তখনই, যখন দুটো সমান rank-এর গাছ মিশে। এটা ভুলে গেলে rank-এর গ্যারান্টি ভেঙে যায় (নিচে ভুল নম্বর ৩-এ আছে)।
10. `this.components--` : দুটো দল এক হলো, দল সংখ্যা এক কমল।
11. `return this.find(a) === this.find(b)` : connected মানে দুজনের প্রতিনিধি একই কিনা। find ছাড়া সরাসরি parent তুলনা করলে ভুল হবে, কারণ parent তখনো root নাও হতে পারে।

## Complexity

হিসাবটা ধাপে ধাপে গড়ি।

**কোনো optimization ছাড়া:** union যদি সবসময় এক দিকে ঝুঁকে, গাছ হয়ে যায় n-লম্বা চেইন (আমাদের "না-বুঝে" উদাহরণটা বড় করে ভাবো)। তখন find চলে **O(n)**-এ, আর m-টা অপারেশনে O(mn)।

**শুধু union by rank:** এখানে একটা গুণগত কথা প্রমাণ করা সহজ। rank r-এর কোনো root-এর নিচে অন্তত 2^r জন সদস্য থাকে। কেন? rank শুধু তখনই এক বাড়ে যখন দুটো সমান rank-এর গাছ মিশে, মানে rank r-এ পৌঁছাতে দুটো rank r-1-এর গাছ লাগে, সদস্য সংখ্যা দ্বিগুণ। তাই সবচেয়ে লম্বা গাছের rank হতে পারে সর্বোচ্চ log n, find চলে **O(log n)**-এ।

**দুটো কৌশল একসাথে:** এখানেই জাদু। path compression find চলার সময় পথের সবাইকে root-এর কাছে টেনে আনে, ফলে পরের find-গুলো আরও সস্তা হয়। সব মিলিয়ে m-টা অপারেশনের গড় খরচ পড়ে **O(α(n))** প্রতি অপারেশনে, যেখানে α হলো inverse Ackermann ফাংশন।

α(n) কতটা ধীরে বাড়ে? একটা স্বজ্ঞাত আত্মীয় হলো log*, "n-কে কতবার log নিলে 1-এ নামবে", সেই সংখ্যাটা। 65536-এর জন্য log* মাত্র 4 (65536 → 16 → 4 → 2 → 1)। inverse Ackermann এর চেয়েও অনেক ধীর, বাস্তবে সম্ভব যেকোনো n-এর জন্য (যেমন n = 10^80, মহাবিশ্বের পরমাণুর সংখ্যা) α(n) ≤ 4। মানে ব্যবহারে এটা ধ্রুবকের মতোই।

সৎ থেকে বলি: α(n)-এর পুরো প্রমাণটা (Tarjan-এর বিখ্যাত বিশ্লেষণ) এই কোর্সের নাগালের বাইরে, সেখানে পথগুলোকে স্তরে ভাগ করে জটিল হিসাব লাগে। কিন্তু intuition-টা তোমার হাতে আছে: rank গাছকে log n-এর মধ্যে আটকে রাখে, compression প্রতিটা find-কে পরেরবারের জন্য প্রায় ফ্রি করে দেয়। দুটো মিলে ফল প্রায় O(1)।

**Space: O(n)।** parent আর rank, দুটোই n-লম্বা array। recursion-এর find এক মুহূর্তে O(n) stack নিতে পারে খারাপ ক্ষেত্রে, চাইলে loop দিয়ে iterative find লেখা যায়।

## সাধারণ ভুল আর edge case

**১. find ছাড়া সরাসরি parent তুলনা করা।**
`parent[0] === parent[4]` দেখে connected বলে দিলে ভুল উত্তর আসবেই, কারণ parent মানে আসল root নয়, parent মানে শুধু "এক ধাপ উপরে কে"। আমাদের dry run-এর ধাপ ৪-এ parent[0] = 0 কিন্তু parent[4] = 3, তবু তারা একই দলে। নিয়ম একটাই: তুলনা করতে হলে আগে দুজনেরই find ডাকো।

**২. union-এ সদস্যকে জোড়া লাগানো, root-কে নয়।**
`parent[a] = parent[b]` লিখে দিলে যা হয়: মাঝের কোনো node-এর parent বদলে গেল, কিন্তু তার নিচের পুরো শাখা এখনো পুরনো দলের দিকে তাকিয়ে। দল দুই টুকরো হয়ে তোমার জানা ছাড়াই ভুল connectivity দেখাবে। সবসময় `find(a)` আর `find(b)` বের করে, root-দের জোড়া লাগাও।

**৩. rank কখন বাড়ে, সেটা ভুল করা।**
rank বাড়ে একমাত্র তখন, যখন দুটো **সমান rank-এর** root মিশে। বেশি rank-এর নিচে ছোটটা ঢুকলে rank বাড়ে না, কারণ নতুন গাছ আগের চেয়ে লম্বা হয়নি। প্রতিবার union-এ rank বাড়িয়ে দিলে rank আসল উচ্চতার সাথে সম্পর্ক হারাবে, আর O(log n) গ্যারান্টিও হারাবে। আরেকটা জিনিস: compression-এর পর non-root-দের rank পুরনো হয়ে যায়, সেটা স্বাভাবিক, rank শুধু root-এর জন্য অর্থবহ।

**৪. 0-indexed বনাম 1-indexed ইনপুট।**
LeetCode-এ অনেক প্রশ্নে node-গুলো 1 থেকে n পর্যন্ত। অভ্যাসবশত `new DSU(n)` বানালে node n-এর জন্য জায়গাই থাকে না, index out of bounds খাবে নিঃশব্দে। সমাধান: `new DSU(n + 1)` বানাও আর 0 নম্বরটাকে ব্যবহার না করেই থাকো, নয়তো ইনপুটের প্রতিটা সংখ্যা থেকে 1 বিয়োগ করে নাও। ইনপুট ফরম্যাট পড়ার সময়ই ঠিক করে ফেলো।

**৫. component সংখ্যা বারবার গোনা।**
"এখন ক-টা দল?" প্রশ্ন এলে n-টা উপাদানের সবার find চালিয়ে আলাদা root গুনলে চলবে, কিন্তু প্রতিবার O(n)। যেখানে constructor-এ `components = n` রেখে প্রতি সফল union-এ এক কমালেই উত্তর O(1)-এ পাওয়া যায়। খেয়াল রাখো, ব্যর্থ union-এ (return false) কমাবে না, তখন তো দল মিশেইনি।

আরেকটা ছোট edge case: `union(x, x)`। নিজের সাথে নিজে মেলানো অবশ্যই false ফেরাবে, আর components অক্ষত থাকবে। আমাদের কোডে `ra === rb` চেকটাই এটা সামলে দেয়, আলাদা কিছু লাগে না।

## অনুশীলন

- **সহজ ১:** Number of Provinces (LeetCode 547)। হিন্ট: উপরের `findCircleNum` না দেখে নিজে লেখো; প্রতি জোড়ায় union, শেষে count।
- **সহজ ২:** Redundant Connection (LeetCode 684)। edge-গুলো একে একে দেওয়া হচ্ছে, কোন edge-টা বাদ দিলে tree থাকে? হিন্ট: যে edge-এ union false ফেরায়, সেই প্রথমটাই উত্তর।
- **মাঝারি ১:** Number of Operations to Make Network Connected (LeetCode 1319)। ক-টা cable সরালে সব কম্পিউটার এক জালে আসবে? হিন্ট: দল c-টা হলে জোড়া লাগাতে লাগে c-1-টা cable; আগে দেখো মোট cable যথেষ্ট আছে কিনা।
- **মাঝারি ২:** Smallest String With Swaps (LeetCode 1202)। কিছু index-জোড়া দেওয়া, ওদের ভেতরে অক্ষর অবাধে বদলানো যায়, lexicographically সবচেয়ে ছোট string বানাও। হিন্ট: index-গুলোকে union করো, প্রতি দলের অক্ষর sort করে আবার বসাও। (বিকল্প চ্যালেঞ্জ: Evaluate Division, LeetCode 399, ভগ্নাংশ-সমীকরণের প্রশ্নটাও DSU দিয়ে হয়, প্রতিটা pointer-এ weight রেখে।)
- **কঠিন:** Accounts Merge (LeetCode 721)। কয়েকটা account-এর email তালিকা দেওয়া, যেগুলোর email মিলে যায় সেগুলো একই মানুষের। হিন্ট: প্রতিটা email-কে map-এ রেখে তার প্রথম account-এর index-এ union করো; শেষে root অনুযায়ী email-গুলো জড়ো করো।

## সারসংক্ষেপ

- Disjoint Set = প্রতিটা উপাদানের parent pointer; root-ই দলের প্রতিনিধি। find মানে root খোঁজা, union মানে দুই root-এর জোড়া।
- দুটো কৌশল মনে রাখো: path compression (find-এর পথ চ্যাপ্টা করা) আর union by rank বা size (ছোট গাছ বড় গাছের নিচে)।
- দুটো মিলে প্রতি অপারেশন O(α(n)), বাস্তবে ধ্রুবকের মতো; optimization ছাড়া চেইন গাছে find চলে O(n)।
- union সবসময় root-দের নিয়ে, connected চেক সবসময় find দিয়ে। union-এর false return মানে cycle।
- Kruskal MST, provinces, accounts merge, যেখানেই "দুজনে কি একই দলে?" প্রশ্ন আসে, উত্তর DSU।
