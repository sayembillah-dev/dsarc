## কী শিখব

- Traversal মানে কী, আর তিনটা DFS ক্রমের একটাই পার্থক্য
- একই গাছে pre, in, post: তিনটা dry run, পাশাপাশি
- Recursion-এর call stack দিয়ে in-order হাতে trace করা
- কোন ক্রম কোন কাজে লাগে, কেন
- Complexity আর iterative রূপের দিকে প্রথম পা

## ধারণা

Tree-র সব node একবার করে ঘুরে আসার নাম **traversal**। Linear কাঠামোয় ঘোরার রাস্তা একটাই, কিন্তু গাছে শাখা আছে, তাই প্রশ্ন জাগে: **root-কে কখন পড়বে?** এই এক প্রশ্নের তিনটা উত্তরেই তিন ক্রম:

- **Pre-order:** Root → Left → Right। নিজে আগে।
- **In-order:** Left → Root → Right। নিজে মাঝে।
- **Post-order:** Left → Right → Root। নিজে শেষে।

[Recursion Intro](./../recursion/recursion-intro.mdx)-এ দেখেছিলে, কাজটা call-এর আগে না পরে সেটাই ক্রম ঠিক করে। এখানে হুবহু সেটাই: `visit(node)` লাইনটা কোথায় বসল, তিন জায়গার তিনটাই একেক ক্রম। তিনটা algorithm মুখস্থ নয়, একটা কঙ্কালের তিন রূপ।

## পরীক্ষার গাছ

পুরো অধ্যায়জুড়ে আমরা এই রিপোজিটরিরই একটা ছোট ফোল্ডার-গাছ ব্যবহার করব:

```text
        dsarc/
        /     \
     src/      content/
     /   \
  app/   components/
```

## Dry run: তিন ক্রম পাশাপাশি

ছোট subtree-এ নিয়মটা আগে পাকা করো: ধরো কোনো node X, তার বামে L, ডানে R:

- pre: **X**, L..., R...
- in: L..., **X**, R...
- post: L..., R..., **X**

এবার পুরো গাছে, প্রতি node-এ একই নিয়ম:

| ক্রম | ফল | কীভাবে এল |
|------|-----|-----------|
| Pre | `dsarc, src, app, components, content` | dsarc আগে; তারপর src-এর অংশ (src, app, components); শেষে content |
| In | `app, src, components, dsarc, content` | dsarc-এর বাম অংশ আগে (app, src, components), তারপর dsarc, তারপর ডান অংশ (content) |
| Post | `app, components, src, content, dsarc` | dsarc-এর দুই অংশ আগে (app, components, src), (content), শেষে dsarc |

লক্ষ করো, প্রতিটা ক্রমে subtree-গুলো এক টুকরো থাকে: src-এর অংশ (app, components সহ) সবসময় পাশাপাশি। পার্থক্য শুধু node নিজে কোথায় বসল।

তিনটা ক্রম একই গাছে ঘুরে দেখো — চিপ বদলে pre / in / post তুলনা করো:

## কোড: এক কঙ্কাল, তিন রূপ

```js
function preOrder(node, out = []) {
  if (!node) return out;
  out.push(node.value);     // root: আগে
  preOrder(node.left, out);
  preOrder(node.right, out);
  return out;
}

function inOrder(node, out = []) {
  if (!node) return out;
  inOrder(node.left, out);
  out.push(node.value);     // root: মাঝে
  inOrder(node.right, out);
  return out;
}

function postOrder(node, out = []) {
  if (!node) return out;
  postOrder(node.left, out);
  postOrder(node.right, out);
  out.push(node.value);     // root: শেষে
  return out;
}
```

তিনটার কোড হুবহু এক, শুধু `push`-এর জায়গা বদলায়। এটাই বলেছিলাম, তিন algorithm না, একটার তিন রূপ।

## Call stack দিয়ে হাতে trace: in-order

[Call Stack](../recursion/call-stack.mdx) মনে রেখো। `inOrder(dsarc)` চলছে, প্রতিটা call-এর পর কী হচ্ছে:

| ধাপ | ঘটনা | output এ পর্যন্ত |
|-----|------|-------------------|
| 1 | inOrder(dsarc) → বামে যাও: inOrder(src) | `[]` |
| 2 | inOrder(src) → বামে: inOrder(app) | `[]` |
| 3 | inOrder(app) → বামে null, ফিরে; **push app**; ডানে null | `[app]` |
| 4 | ফিরে inOrder(src)-এ: **push src**; ডানে inOrder(components) | `[app, src]` |
| 5 | inOrder(components): বাম-ডান null, **push components** | `[app, src, components]` |
| 6 | ফিরে inOrder(dsarc)-এ: **push dsarc**; ডানে inOrder(content) | `[app, src, components, dsarc]` |
| 7 | inOrder(content): **push content** | `[app, src, components, dsarc, content]` |

চেনা কথা: প্রতি call নিজের জায়গায় ফিরে আসে, আর push হয় **বাম ডল শেষ হওয়ার পর**, ডান ডলের আগে। Recursion-এর call stack নিজেই গভীরতা মনে রাখে, আলাদা stack লাগে না।

## কোন ক্রম কোন কাজে

- **Pre-order:** ফোল্ডার-গাছ **কপি** করা বা `tree`-স্টাইলে ছাপা — parent আগে বানাতে/দেখাতে হয়, তারপর ভেতরেরগুলো। prefix expression লেখাও এই ক্রম।
- **In-order:** [BST](./binary-search-tree.mdx)-তে এটা **sorted ক্রম** দেয়। এক লাইনে BST-র পরিচয়পত্র।
- **Post-order:** `du -sh`-এর হিসাব (ফোল্ডারের মোট size জানতে আগে ভেতরের ফাইলগুলোর size চাই), `rm -rf` (ভেতরের জিনিস আগে মুছে তবে ফোল্ডার মোছা যায়) — এক কথায়, child-এর কাজ শেষ না হলে parent-এর কাজ করা যায় না এমন সব জায়গায়।

## ভ্যারিয়েন্ট: দুটো গাছ একেবারে একই কিনা

দুটো binary tree ঠিক তখনই একই, যখন গঠনও এক, প্রতি ঘরের মানও এক। recursion-এর ছাঁচ মিলে যায় সোজাসুজি: দুটোই খালি হলে একই; একটা খালি আরেকটা নয়, বা মান মিলল না — আলাদা; নইলে বাম জোড়া আর ডান জোড়া, দুই দিকেই একই চাই:

```js
function sameTree(p, q) {
  if (p === null && q === null) return true;   // দুজনেই শেষ, এ পর্যন্ত সব মিলেছে
  if (p === null || q === null) return false;  // একটা শেষ, আরেকটা নয়: গঠন আলাদা
  if (p.value !== q.value) return false;       // মান মিলল না
  return sameTree(p.left, q.left) && sameTree(p.right, q.right);
}
```

লক্ষ করো, এটা আসলে দুটো গাছের ওপর **যুগল pre-order**: দুজনের root একসাথে দেখা, তারপর দুই ডানায় একই ক্রমে নামা। সময় O(n), প্রতি জোড়া node ঠিক একবার; জায়গা O(h), call stack। এটাই LeetCode 100 (Same Tree)।

## Complexity

| দিক | খরচ | কেন |
|-----|------|-----|
| Time | O(n) | প্রতি node-এ ঠিক একবার push, ঠিক দুইবার child-ডাক (null-ও মিলিয়ে) |
| Space | O(h) | call stack-এর গভীরতা = গাছের height; ভারসাম্যপূর্ণ হলে log n, হেলানো হলে n |

Space-টা গুরুত্বপূর্ণ: "recursion ফ্রি" না, গাছ হেলানো হলে stack-এ O(n) frame জমে। সেই হিসাব [Recursion vs Iteration](../recursion/recursion-vs-iteration.mdx)-এ গিয়েছিল।

## সাধারণ ভুল আর edge case

**১. তিন ক্রমের নাম মুখস্থ, জায়গা বোঝা না।**
"Pre মানে আগে" মুখস্থ রাখলে নতুন গাছে গুলিয়ে ফেলো। সূত্র মনে রাখো: **root কোথায়**, নাম সেখান থেকেই এসেছে।

**২. Base case ভুলে null-এ crash।**
`if (!node) return` ছাড়া `node.value` পড়তে গিয়ে TypeError। প্রতি recursive call-এর আগে null হতে পারে, এই চেকই দারোয়ান।

**৩. `out` পাস না করা।**
`inOrder(node.left)` লিখে `out` না দিলে ভেতরের call নতুন array বানায়, ফল হারায়। [Memoization](../recursion/memoization.mdx)-এর cache-এর মতোই নিঃশব্দ ভুল: চলে, কিন্তু ফল আসে না।

**৪. In-order সবসময় sorted ভাবা।**
শুধু BST-তে। সাধারণ binary tree-তে in-order মানে কিছুই না, উপরের গাছেই দেখো: app, src, components, dsarc, content — কোনো বিন্দুতেই sorted না। এই গুলানোটা interview-এ ক্লাসিক ফাঁদ।

**৫. Iterative লিখতে গিয়ে ডান-বাম উল্টানো।**
Explicit stack দিয়ে pre-order লিখলে **ডান আগে push**, তাহলে বাম আগে বের হয় (LIFO)। উল্টো push করলে ক্রম উল্টে যায়, আর টেরও পাবে না। পুরো রূপ [BFS/DFS on Tree](./bfs-dfs-on-tree.mdx)-এ।

## অনুশীলন

- **সহজ ১:** এই ছোট API প্রজেক্টের গাছে তিন ক্রম লিখো: root `api`, বামে `routes` (বামে `users.ts`, ডানে `auth.ts`), ডানে `db`। আগে অনুমান করো, তারপর নিয়ম বসিয়ে মিলাও।
- **সহজ ২:** উপরের পরীক্ষার গাছে post-order হাতে trace করো, call stack টেবিল বানিয়ে, আমার in-order-এর মতো করে।
- **মাঝারি ১:** একটা function লেখো `countNodes(root)`, post-order ভাবনায়। (হিন্ট: নিজের সংখ্যা = বাম subtree + ডান subtree + 1। কোন ক্রমে হিসাব হচ্ছে, খেয়াল করো।)
- **মাঝারি ২:** `sumTree(root)`: সব node-এর মানের যোগফল। কোন ক্রম সবচেয়ে স্বাভাবিক, কেন?
- **কঠিন:** Pre-order আর in-order দেওয়া থাকলে গাছ পুনর্গঠন করা যায় (LeetCode 105)। কীভাবে, ভাবো: pre-এর প্রথম উপাদান সবসময় কে? in-এ সেটার বামে-ডানে কী থাকে? (হিন্টের উত্তর: root; আর in-order-এ root-এর বামে বাম subtree পুরোটা। Recursion দুই ভাগে চলে যায়।)

## সারসংক্ষেপ

- তিন DFS ক্রম, পার্থক্য একটাই: root কখন পড়া হচ্ছে, আগে (pre), মাঝে (in), শেষে (post)।
- একটাই কঙ্কাল, শুধু `push`-এর জায়গা বদলায়; তিন algorithm মুখস্থের দরকার নেই।
- Recursion-এর call stack-ই গভীরতা মনে রাখে; space O(h), হেলানো গাছে O(n)।
- Pre কপিতে, in BST-তে sorted, post মোছা বা হিসাবে: কাজ দেখে ক্রম।
- In-order সবসময় sorted নয়, শুধু BST-তে: ক্লাসিক ফাঁদ।
