## কী শিখব

- database আর disk-এর জন্য বানানো বহু-চাইল্ডওয়ালা balanced tree

## ধারণা

disk থেকে ডেটা পড়া ভয়ংকর ধীর কাজ, RAM-এর তুলনায় হাজার গুণ slow। তাই database-এর কাছে গাছের height-ই সব। height কম মানে কম বার disk পড়া, মানে দ্রুত কাজ।

এই চিন্তা থেকেই **B-Tree**। binary tree-র প্রতিটা node-এ ১টা key, ২টা চাইল্ড। B-Tree-তে প্রতিটা node-এ **অনেক key আর অনেক চাইল্ড** থাকে। ফলে গাছ চওড়া হয়, গভীর হয় না। এজন্যই database index আর file system এই কাঠামোর ওপর দাঁড়িয়ে (section 15-এ এর আত্মীয় B+ Tree নিয়ে বিস্তারিত পড়বে)।

মূল ধর্ম (order m-এর B-Tree ধরো):

- প্রতিটা node-এ সর্বোচ্চ m-1 key, m চাইল্ড
- সব leaf একই স্তরে, মানে perfectly balanced
- node-এর ভিতরে key গুলো sorted

```
        [ 10 | 20 ]
       /     |     \
   [<10]  [10-20]  [>20]
```

## কোড উদাহরণ

node-এর গঠনটা দেখো (ধারণা):

```js
class BTreeNode {
  constructor(isLeaf = true) {
    this.keys = [];      // sorted key লিস্ট (একাধিক)
    this.children = [];  // চাইল্ড লিস্ট (keys+1 টা)
    this.isLeaf = isLeaf;
  }
}
const node = new BTreeNode();
node.keys = [10, 20];
console.log(node.keys, node.isLeaf); // [10, 20] true
// খোঁজা: node-এর keys-এ কোথায় fit করে দেখে সঠিক child-এ নামা
// (পূর্ণ insert/split বাস্তবায়ন advanced, section 15-এ B+ Tree বিস্তারিত)
```

## কোড ব্রেকডাউন

- অনেক key মানে অনেক চাইল্ড, অনেক চাইল্ড মানে কম height, আর কম height মানে কম disk read।
- "node full হলে split", এই এক কৌশলেই গাছ সবসময় balanced থাকে।
- বাস্তবে node-এর আকার disk-page-এর আকারের সাথে মেলানো হয়, যেন একবার পড়লেই পুরো node পাওয়া যায়।

## Complexity

- search/insert/delete সব O(log n); তবে আসল জয়টা disk-access-এ, সেখানে পার্থক্য বিশাল।
