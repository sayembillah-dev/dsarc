## কী শিখব

- BST-এর একটাই নিয়ম, আর সেখান থেকে সব শক্তি
- Search আর insert-এর পুরো dry run: প্রতি ধাপে অর্ধেক বাদ
- Delete-এর তিন কেস, কঠিনটা পর্যন্ত
- কেন in-order traversal সবসময় sorted ক্রম দেয়
- Skewed tree: কখন সব সুবিধা জলে যায়, আর তখন কী হয়

## ধারণা

[Binary Search](../searching/binary-search.mdx)-এর কথা মনে করো: sorted array-তে প্রতি ধাপে অর্ধেক বাদ। সেই একই ক্ষমতা, কিন্তু এমন কাঠামোয় যেখানে insert/delete-ও সস্তা, এই ইচ্ছা থেকেই **Binary Search Tree**।

ধরো তোমার সার্ভারে কোন কোন port খোলা আছে, সেটা track করছ। চেক করা লাগবে ঘন ঘন ("5432 খোলা তো?"), আবার নতুন সার্ভিস উঠলে port যোগও করা লাগবে। খোঁজা দ্রুত চাই, ঢোকানোও সস্তা চাই — এই দ্বৈত দাবিই BST-র পেটভাত।

নিয়ম একটাই, প্রতিটা node-এর জন্য:

```text
বাম subtree-র সব মান < node < ডান subtree-র সব মান
```

```text
              6379 (redis)
             /    \
       80 (http)   8080 (proxy)
       /    \            \
  22 (ssh)  3000 (dev)   27017 (mongo)
            /    \
     443 (https)  5432 (postgres)
```

যেকোনো node নাও, নিয়ম মিলবে। যেমন 80-এর বামে 22 (ছোট), ডানে 3000 (বড়, কিন্তু 6379-এর চেয়ে ছোট)। খেয়াল করো, নিয়ম শুধু সরাসরি child নয়, **পুরো subtree-এর** উপর। এই বিস্তৃতিটা জরুরি, ভুলগুলোতে দেখবে।

## Dry run: search(5432)

PostgreSQL চালানোর আগে চেক করছি, 5432 port-টা খোলা আছে কিনা:

| ধাপ | current | তুলনা | সিদ্ধান্ত |
|-----|---------|-------|-----------|
| 1 | 6379 | 5432 < 6379 | বামে |
| 2 | 80 | 5432 > 80 | ডানে |
| 3 | 3000 | 5432 > 3000 | ডানে |
| 4 | 5432 | সমান | **পেলে** |

৪ ধাপ। পুরো গাছে ৮টা node, অথচ বাকি কাউকে আর দেখাই হলো না: প্রতি ধাপে এক পুরো subtree বাদ পড়েছে, হুবহু binary search-এর অর্ধেক-বাদের মতো। আর 2375 (Docker) খুঁজলে? 6379 → 80 → 3000 → 443, তারপর 443-এর ডান null, মানে **খোলা নেই**, তাও নিশ্চিতভাবে, কারণ থাকলে ওই পথেই থাকত।

## কোড: নিজে বানাও BST

```js
class TreeNode {
  constructor(value) {
    this.value = value;
    this.left = null;
    this.right = null;
  }
}

class BST {
  constructor() {
    this.root = null;
  }

  search(value) {
    let current = this.root;
    while (current) {
      if (value === current.value) return true;
      current = value < current.value ? current.left : current.right;
    }
    return false;
  }

  insert(value) {
    const node = new TreeNode(value);
    if (!this.root) {
      this.root = node;
      return;
    }
    let current = this.root;
    while (true) {
      if (value < current.value) {
        if (!current.left) { current.left = node; return; }  // ফাঁকা পেলে বসে গেল
        current = current.left;
      } else {
        if (!current.right) { current.right = node; return; }
        current = current.right;
      }
    }
  }
}

const bst = new BST();
[6379, 80, 8080, 22, 3000, 27017, 443, 5432].forEach((v) => bst.insert(v));
console.log(bst.search(5432));  // true
console.log(bst.search(2375));  // false
```

Insert-ও search-এরই ভাই: খোঁজার পথ ধরেই নামো, যেখানে পথ শেষ (null), সেখানেই নতুনটা বসে। তাই insert-এর খরচও খোঁজার খরচই।

## Delete: তিন কেস

Delete-ই BST-র কঠিন অপারেশন, তিন ভাগে ভাঙো:

1. **Leaf মোছা (child নেই):** সোজা কেটে ফেলো। PostgreSQL বন্ধ করলে 5432 মোছা মানে 3000-এর ডান null হয়ে যাওয়া, ব্যস।
2. **এক child-ওয়ালা মোছা:** child-টাকে নিজের জায়গায় তুলে দাও। 8080 মুছলে ওর child 27017 ওপরে উঠে বসে।
3. **দুই child-ওয়ালা মোছা:** চালাকি এখানে। Node-টাকে সরাসরি মোছা যায় না, তাই তার **in-order successor** (ডান subtree-র সর্বনিম্ন, মানে ক্রমে পরেরটা) খুঁজে তার মান দিয়ে এই ঘর ভরো, তারপর successor-টাকে মোছো (সে তো leaf বা এক-childই হবে)। যেমন 80 মুছতে হলে successor 443: 80-এর জায়গায় 443 বসে, পুরনো 443-এর ঘর মুছে যায়। নিয়ম ভাঙে না, কারণ successor-ই ছিল ডানদিকের সবচেয়ে ছোট।

```js
delete(value) {
  this.root = this._deleteRec(this.root, value);
}

_deleteRec(node, value) {
  if (!node) return null;

  if (value < node.value) {
    node.left = this._deleteRec(node.left, value);
  } else if (value > node.value) {
    node.right = this._deleteRec(node.right, value);
  } else {
    // পেলে! তিন কেস:
    if (!node.left) return node.right;         // কেস ১+২: ডান child (বা null) উঠে আসে
    if (!node.right) return node.left;         // কেস ২: বাম child উঠে আসে

    // কেস ৩: ডান subtree-র সর্বনিম্ন দিয়ে ভরাও
    let succ = node.right;
    while (succ.left) succ = succ.left;
    node.value = succ.value;
    node.right = this._deleteRec(node.right, succ.value); // successor-টা এবার মোছো
  }
  return node;
}
```

## In-order-এর জাদু: sorted ক্রম

মনে করো [Traversal](./binary-tree-traversal.mdx)-এর in-order: বাম, root, ডান। BST-এর নিয়ম বলছে বামে ছোট, ডানে বড়, তাই in-order চালালেই ফল **ছোট থেকে বড়** এসে যায়:

```js
function inOrder(node, out = []) {
  if (!node) return out;
  inOrder(node.left, out);
  out.push(node.value);
  inOrder(node.right, out);
  return out;
}

console.log(inOrder(bst.root)); // [22, 80, 443, 2375, 3000, 5432, 6379, 8080, 27017]
```

এক লাইনে: **BST + in-order = sorted output**। কোনো sort চালানো লাগল না, কাঠামো নিজেই ক্রম ধরে রাখে। কোনো BST-কে যাচাই করতেও এটা লাগে: in-order বের করে দেখো strictly increasing কিনা।

## ভ্যারিয়েন্ট: এই গাছটা সত্যিই BST তো?

ধরো কেউ তোমাকে একটা binary tree দিল, দাবি সহকারে: "এটা BST।" যাচাই করবে কীভাবে? প্রথম ধারণা: প্রতি node-এর বামে ছোট, ডানে বড় আছে কিনা দেখো। কিন্তু এই গাছটা দেখো:

```text
    6379
    /
  3000
     \
     8080    ← নিজের parent 3000-এর ডানে, স্থানীয়ভাবে ঠিক
```

স্থানীয় চেকে সব ঠিক: 3000 < 6379, 8080 > 3000। কিন্তু 8080 বসে আছে 6379-এর **বাম** subtree-তে, অথচ 8080 > 6379 — নিয়ম ভেঙেছে। মানে parent-সন্তান চেক যথেষ্ট নয়; প্রতি node-এর জন্য একটা **অনুমোদিত পরিসর** বয়ে নামতে হবে: root-এর সব, বামে গেলে ছাদ কমে, ডানে গেলে মেঝে ওঠে।

```js
function isBST(node, lo = -Infinity, hi = Infinity) {
  if (node === null) return true;                         // খালি গাছ নির্দোষ
  if (node.value <= lo || node.value >= hi) return false; // সীমার বাইরে মানেই অপরাধ
  return isBST(node.left, lo, node.value) && isBST(node.right, node.value, hi);
}
```

Root পায় (-∞, ∞); তার বাম সন্তান পায় (-∞, 6379), সেই 8080-এর জন্য পরিসর (3000, 6379) — আর 8080 সেই ছাদ ভেঙে ফেলে, ধরা পড়ল। সময় O(n), প্রতি node একবারই; জায়গা O(h)। (এই সংস্করণ মান distinct ধরে; duplicate মেনে নিতে হলে একদিকের চিহ্ন =-সহ ঘষাখাও।)

আরেকটা রাস্তা ওপরেই শিখেছ: in-order চালিয়ে দেখো strictly increasing কিনা — সেটাও O(n), শুধু বাড়তি array লাগে। দুটোই জেনে রাখো, এটাই LeetCode 98।

## Skewed tree: সব শেষ হওয়ার দৃশ্য

Sorted ডেটাই যদি ক্রমে insert করো — যেমন সার্ভার বুটে সার্ভিসগুলো ওঠে port-ক্রমেই: 22, তারপর 80, তারপর 443, তারপর 3000, 5432 — প্রতিটা নতুন মান আগেরটার ডানেই বসতে থাকে:

```text
22 → 80 → 443 → 3000 → 5432   (সব ডানে, একদম হেলানো দণ্ড)
```

গাছ আর গাছ রইল না, হয়ে গেল linked list। Search-এ এবার প্রতি ধাপে অর্ধেক বাদ হয় না, একটা বাদ হয়: **O(n)**। BST-র সব O(log n) প্রতিশ্রুতি দাঁড়িয়ে ছিল "গাছ ভারসাম্যপূর্ণ" এই শর্তের উপর। এই বিপদ থেকে বাঁচাতেই [AVL Tree](./avl-tree.mdx) জন্ম নিয়েছে, যেখানে গাছ নিজে ঘুরে ভারসাম্য রাখে।

## Complexity

| অপারেশন | Average | Worst (skewed) | কেন |
|---------|---------|----------------|-----|
| search | O(log n) | O(n) | খরচ = গাছের height; ভরা গাছে log n, হেলানোয় n |
| insert | O(log n) | O(n) | খোঁজার পথই হাঁটা |
| delete | O(log n) | O(n) | খোঁজা + সর্বোচ্চ একটা successor-খোঁজা |
| in-order (sorted পাওয়া) | O(n) | O(n) | সবাই একবার |

## সাধারণ ভুল আর edge case

**১. নিয়মটা শুধু child-এর উপর যাচাই করা।**
`node.left.value < node.value` চেক করলেই BST হয় না। বাম subtree-এর **সবাইকে** ছোট হতে হবে, গভীরের কেউ বড় হলেই নিয়ম ভাঙে। যাচাই করতে in-order নাও, সেটা increasing কিনা দেখো।

**২. Delete-এ দুই-child কেসে successor না খুঁজে আধখোড়া মোছা।**
ডান subtree-র যেকোনো node দিয়ে ভরালে নিয়ম ভাঙে; লাগে সর্বনিম্নটা (in-order successor)। বাম subtree-র সর্বোচ্চও চলে, দুটোই বৈধ, কিন্তু একটা ধরো আর পাকা থাকো।

**৩. Search-এ দিক ভুলে যাওয়া।**
ছোট বামে, বড় ডানে। চাপে পড়ে উল্টো লিখলে নেই-এমন জিনিসও "আছে" দেখাবে। ছোট একটা গাছ হাতে বানিয়ে দুইটা search-ই dry run করো।

**৪. Sorted ডেটা insert করে O(log n) আশা করা।**
উপরের skewed দৃশ্যটাই। ডেটা আগে থেকে sorted হলে shuffle করে insert করো, নয়তো self-balancing গাছ (AVL) নাও।

**৫. Duplicate-এর নীতি না ঠিক করা।**
সমান মান এলে কোথায় যাবে? আমাদের কোডে ডানে (`else` পড়ে)। তুমি চাইলে count রাখতে পারো, কিন্তু না ভেবে লিখলে duplicate হারিয়ে যায় বা দুইবার যায়। নীতি আগে ঠিক করো।

- **মাঝারি ১:** `findMin` আর `findMax` লেখো। (হিন্ট: একটায় শুধু বামে, আরেকটায় শুধু ডানে, যতক্ষণ পারো। কেন এটা কাজ করে, নিয়ম দিয়ে ব্যাখ্যা করো।)
- **মাঝারি ২:** `isValidBST(root)` লেখো। (হিন্ট: শুধু parent-এর সঙ্গে তুলনা যথেষ্ট না; প্রতি node-এর একটা বৈধ পরিসর (min, max) থাকে, recursion-এ নিচে নামার সঙ্গে পরিসর সরু হয়। অথবা in-order নিয়ে increasing চেক।)
- **কঠিন:** k-তম ছোট উপাদান BST থেকে (LeetCode 230), গাছ sort না করে। (হিন্ট: in-order ঘুরে k-তমটা থামাও। Early exit লাগলে কোথায় রাখবে, ভাবো। Extra: প্রতি node-এ subtree-র size রাখলে O(h)-এও হয়, সেটা order-statistics tree-এর বীজ।)

## সারসংক্ষেপ

- BST-এর এক নিয়ম: বামে ছোট, ডানে বড়, পুরো subtree জুড়ে।
- Search/insert/delete গড়ে O(log n), কারণ প্রতি ধাপে অর্ধেক বাদ; খরচ আসলে O(height)।
- Delete-এর কঠিন কেসে in-order successor দিয়ে ভরাও, নিয়ম অক্ষত থাকে।
- In-order চালালেই sorted output: এটাই BST-র পরিচয়পত্র আর যাচাই-যন্ত্র।
- Sorted ডেটা insert মানে দণ্ড-গাছ আর O(n): এখান থেকেই AVL-এর অস্তিত্ব।
