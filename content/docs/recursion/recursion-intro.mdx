## কী শিখব

- Recursion আসলে কী: বড় সমস্যা নিজের ছোট রূপকে ডাকে পাঠানো
- দুই অংশ ছাড়া কোনো recursion চলে না: base case আর recursive case
- একটা পুরো recursive call-এর dry run: নিচে নামা, থামা, ফিরে আসা
- Print-এর জায়গা বদলে দিলেই ক্রম উল্টে যায়: call-এর আগে না পরে
- নিজে recursive function লেখার তিন ধাপের সূত্র
- প্রথম দিককার সব ভুল: infinite recursion থেকে ভুল দিকে এগোনো

## ধারণা

ভাবো তো, দুটো আয়না মুখোমুখি রেখে মাঝে দাঁড়ালে কী হয়? একটা প্রতিফলনের ভেতরে আরেকটা ছোট প্রতিফলন, তার ভেতরে আরও ছোট, চলতেই থাকে। আরেকটা উদাহরণ, রুশ পুতুল (matryoshka): খুললে ভেতরে ছোট পুতুল, সেটা খুললে আরও ছোট, শেষে সবচেয়ে ছোটটা আর খোলে না।

Recursion ঠিক এই ব্যাপারটাই। একটা function নিজের ভেতরেই নিজেকে ডাকে, তবে প্রতিবার একটু **ছোট সমস্যা** নিয়ে, যতক্ষণ না সমস্যাটা এত ছোট হয় যে সরাসরি উত্তরটা জানা। সেই থামার জায়গাটার নাম **base case**, আর নিজেকে ডাকার অংশটার নাম **recursive case**।

কেন এমন করি? কারণ অনেক সমস্যার গঠনই এমন: "বড় সমস্যা = ছোট একই সমস্যা + একটু কাজ"। 5 পর্যন্ত যোগফল মানে 4 পর্যন্ত যোগফল + 5। এই চোখটা একবার খুলে গেলে Tree, Graph, Sorting, Dynamic Programming সব সহজ লাগবে, কারণ ওগুলোর ভাষাই এই।

## প্রথম উদাহরণ: countdown

```js
function countdown(n) {
  if (n === 0) {                 // base case: থামার জায়গা
    console.log("শেষ!");
    return;
  }
  console.log(n);                // এবারের কাজ
  countdown(n - 1);              // recursive case: ছোট সমস্যা
}

countdown(3);
```

আউটপুট: `3, 2, 1, শেষ!`। ঠিক আছে, কিন্তু **ভেতরে** কী ঘটল, সেটা না দেখলে recursion কখনওই আসলে বোঝা যায় না।

## Dry run: নিচে নামা, থামা, ফিরে আসা

`countdown(3)` ধাপে ধাপে। প্রতিটা call-কে একটা পুতুল ভাবো: নতুন পুতুল খুললে আগেরটা **অপেক্ষা করে**, খোলা থাকে:

| ধাপ | কী হচ্ছে | খোলা call-গুলো (ডানে নতুন) |
|-----|----------|------------------------------|
| 1 | countdown(3) ডাকা হলো, ছাপে 3 | `countdown(3)` |
| 2 | countdown(2) ডাকা হলো, ছাপে 2 | `countdown(3) → countdown(2)` |
| 3 | countdown(1) ডাকা হলো, ছাপে 1 | `countdown(3) → countdown(2) → countdown(1)` |
| 4 | countdown(0) ডাকা হলো, base case, ছাপে "শেষ!", return | চারটা খোলা |
| 5 | countdown(1) ফিরে এসে শেষ হয়, return | `countdown(3) → countdown(2)` |
| 6 | countdown(2) শেষ, return | `countdown(3)` |
| 7 | countdown(3) শেষ, return | খালি |

দুটো জিনিস চোখে পড়ো। এক, প্রথমে পুরো **নিচে নামা** (call জমতে থাকে), তারপর base case-এ পৌঁছে **উপরে ফেরা** (call শেষ হতে থাকে), একদম পুতুলের মতো। দুই, প্রতিটা call নিজের `n` মনে রেখে অপেক্ষা করছিল, countdown(3)-এর n=3, countdown(2)-এর n=2, আলাদা আলাদা। প্রতিটা call-এর নিজস্ব জগত থাকে, এই কথাটা [Call Stack](./call-stack.mdx)-এ গিয়ে পুরোদস্তুর হবে।

## Variant: জায়গা বদলালেই উল্টো ক্রম

একটাই ছোট পরিবর্তন, print-টা call-এর **পরে** সরিয়ে দাও:

```js
function countup(n) {
  if (n === 0) return;       // base case
  countup(n - 1);            // আগে ছোটদের সারাও
  console.log(n);            // তারপর নিজের ছাপা
}

countup(3);                  // 1, 2, 3
```

কেন উল্টো গেল? কারণ এবার নিচে নামার পথে কেউ কিছু ছাপে না; ছাপা হয় **ফিরে আসার পথে**, সবচেয়ে ছোটটা আগে। "কাজটা call-এর আগে না পরে" এই সিদ্ধান্তটাই recursion-এর অর্ধেক ডিজাইন। Tree traversal-এ preorder বনাম postorder-এর পার্থক্যও হুবহু এটাই, মনে রেখো [Binary Tree Traversal](../trees/binary-tree-traversal.mdx)-এ গেলে।

## নিজে লেখার সূত্র: তিন প্রশ্ন

নতুন সমস্যা দেখলে recursion লেখার আগে নিজেকে তিনটা প্রশ্ন করো:

1. **ছোট রূপ কী?** (সমস্যাটার একই, শুধু ছোট: `n` → `n-1`, array → এক ঘর কম)
2. **বড় সমস্যার উত্তর ছোটটার উত্তর দিয়ে কীভাবে বানায়?** (যোগফল = প্রথমটা + বাকির যোগফল)
3. **কখন থামবে?** (base case: n = 0, array খালি, string এক অক্ষরের)

তিনটার উত্তর মিললে কোড নিজে থেকেই বেরিয়ে আসে। যেমন "1 থেকে n পর্যন্ত যোগফল": ছোট রূপ `sumTo(n-1)`, বড় উত্তর `n + sumTo(n-1)`, থামবে `n === 0`-এ 0 দিয়ে। লিখে ফেলো:

```js
function sumTo(n) {
  if (n === 0) return 0;         // base: 0 পর্যন্ত যোগফল 0
  return n + sumTo(n - 1);       // n + (n-1 পর্যন্ত যোগফল)
}

console.log(sumTo(4)); // 10 = 4 + 3 + 2 + 1
```

## কোড ব্রেকডাউন: countdown, লাইনে লাইনে

1. `if (n === 0)` : base case সবার আগে। এটা পরে লিখলে কিছু পথে আগে কাজ ঘটে যেত; আগে রাখলে থামার শর্ত সবসময় প্রথম দারোয়ান।
2. `console.log("শেষ!"); return;` : base case-এ কাজ করে থেমে যাওয়া। `return` জরুরি, না থাকলে নিচের কোডে পড়ে আবার নিজেকে ডেকে বসত।
3. `console.log(n)` : এবারের call-এর নিজের কাজ। কাজটা call-এর আগে বলে নিচে নামার পথেই হয়।
4. `countdown(n - 1)` : ছোট সমস্যায় ডাক। `n - 1` না দিয়ে `n` দিলে সমস্যা কমত না, চিরকাল ঘুরত: এটাই সবচেয়ে বিপজ্জনক ভুল।

## Complexity

| দিক | খরচ | কেন |
|-----|------|-----|
| Time | O(n) | n-বার call, প্রতি call-এ O(1) কাজ |
| Space | O(n) | একই সঙ্গে n-টা call খোলা থাকে, প্রতিটার নিজের জায়গা call stack-এ |

Space-টা নতুনরা মিস করে। Loop-এ countdown লিখলে জায়গা লাগে O(1), recursion-এ O(n), কারণ ফিরে আসার আগ পর্যন্ত প্রতিটা call জীবিত। এই হিসাবটা [Recursion vs Iteration](./recursion-vs-iteration.mdx)-এ মূল ইস্যু।

## সাধারণ ভুল আর edge case

**১. Base case লেখাই ভুলে যাওয়া।**
Base case ছাড়া call থামে না: `n` কমতে কমতে ঋণাত্মক হয়ে অসীম পর্যন্ত, শেষে `Maximum call stack size exceeded`। Recursion লেখার প্রথম নিয়ম: আগে base case লেখো, তারপর বাকি সব।

**২. Base case আছে, কিন্তু সেখানে পৌঁছায়ই না।**
`countdown(n - 2)` দিলে 3 থেকে 1, তারপর -1, base case 0 লাফিয়ে চলে যায়। Recursive case-এ সমস্যা যে সত্যিই base case-এর **দিকে** এগোচ্ছে, ছোট পদক্ষেপে মিলিয়ে দেখো।

**৩. Recursive case-এ সমস্যা ছোট না করা।**
`countdown(n)` লিখে ভেতরে আবার `countdown(n)` ডাকলে সমস্যা একই থাকে, অনন্ত call। প্রতি ডাকায় input-এর কিছু না কিছু কমতেই হবে, এটাই অগ্রগতির গ্যারান্টি।

**৪. ফিরে আসার পথের কথা ভুলে যাওয়া।**
নতুনরা ভাবে call শেষ হলেই প্রোগ্রাম শেষ। আসলে ভেতরের call শেষ হলে বাইরেরটা **ঠিক যেখানে ছেড়েছিল সেখান থেকে** চলতে থাকে। এই "ফিরে আসা"-টা না বুঝলে countup-এর উল্টো ক্রম কখনও ব্যাখ্যা করতে পারবে না।

**৫. Return value না ফেরানো।**
`return n + sumTo(n - 1)` থেকে `return` ফেলে দিলে ভেতরের call ঠিকই চলে, কিন্তু ফল কেউ পায় না, `undefined` জমা হয়। যে call থেকে ফল চাইবে, সেখানে ফেরাতেও হবে, চেইনের প্রতি ধাপে।

## অনুশীলন

- **সহজ ১:** কাগজে dry run করো `countdown(4)`: কোন ধাপে কোন call খোলা, কোনটা বন্ধ হলো, পুরো সাত-আট ধাপের টেবিল বানাও।
- **সহজ ২:** `sumTo` দিয়ে না ভেবে এবার লেখো `factDown(n)`: n থেকে 1 পর্যন্ত সংখ্যাগুলোর গুণফল recursion-এ। তিন প্রশ্নের উত্তর আগে লিখো, তারপর কোড।
- **মাঝারি ১:** Print-এর জায়গা না বদলিয়ে, `countdown`-এ এমন ব্যবস্থা করো যাতে 3, 2, 1 ছাপার **পর** আবার 2, 3 ছাপে (ঢেউয়ের মতো)। (হিন্ট: call-এর আগে একবার, পরে আরেকবার ছাপালেই হয়। ফিরে আসার পথটা কাজে লাগছে দেখো।)
- **মাঝারি ২:** recursion দিয়ে একটা সংখ্যার অঙ্কগুলোর যোগফল বের করো: `digitSum(407)` → 11। (হিন্ট: ছোট রূপ `digitSum(Math.floor(n / 10))`, আর এবারের কাজ `% 10`; base case কোথায়?)
- **কঠিন:** একটা nested array-র সব সংখ্যার যোগফল: `sumNested([1, [2, [3, 4]], 5])` → 15। (হিন্ট: প্রতি উপাদানের জন্য ভাবো, সংখ্যা হলে যোগ, array হলে তার যোগফল কে বের করবে? `Array.isArray` দিয়ে চেক। Base case কোনটা, recursive case কোনটা, আলাদা করে লিখে নাও।)

## সারসংক্ষেপ

- Recursion = নিজেকে ছোট সমস্যায় ডাকা, যতক্ষণ না উত্তর সরাসরি জানা।
- Base case (থামার জায়গা) আর recursive case (ছোটে ডাকা): দুটো ছাড়া কিছুই চলে না।
- প্রতি call আলাদা জগত: নিচে নামা, base-এ থামা, ফিরে আসা, এই তিন পর্ব।
- কাজ call-এর আগে না পরে, এই এক সিদ্ধান্ত ক্রম উল্টে দেয়।
- লেখার সূত্র: ছোট রূপ কী, বড় উত্তর কীভাবে বানায়, কখন থামবে।
